# Архитектура базы данных RAG-системы BusiVerse

## Обзор

База данных спроектирована для хранения и поиска по мультинишевой документации BusiVerse. Ключевая особенность — **гибридный поиск** (векторный + полнотекстовый) с фильтрацией по нише бизнеса.

**Версия документа:** 1.0  
**Дата:** 26 октября 2026  
**Статус:** Реализовано

---

## Проблема

Как эффективно искать информацию в документе, который:
- Охватывает **10 ниш бизнеса** (кофейня, ПВЗ, пекарня, маникюр, автосервис, селлер, онлайн-школа, SMM, интернет-магазин, бухгалтерия)
- Содержит **сквозные разделы** (налоги, регуляторика), применимые ко всем нишам
- Включает **точные термины** (ст. 14.5 КоАП, 152-ФЗ, Правила № 2463)
- Имеет **структурную иерархию** (ниша → секция → блок)
- Содержит **внутренние ссылки** между разделами

**Проблемы, которые решаем:**
1. Чистый векторный поиск путает номера статей и точные термины
2. Полнотекстовый поиск не понимает семантику
3. Без фильтрации по нише смешиваются ответы для разных бизнесов
4. Без контекста чанк теряет смысл (таблица без шапки, кейс без вывода)

---

## Решение

### Архитектурные принципы

1. **Гибридный поиск:** Векторный (семантика) + Полнотекстовый (точные термины)
2. **Фильтрация по нише:** `WHERE business_type = $1 OR scope = 'global'`
3. **Small-to-Big retrieval:** Ищем по мелким блокам, отдаём родительскую секцию
4. **Contextual embeddings:** `heading_path + text` для контекста
5. **Внутренние ссылки:** Автоматическое разрешение "см. раздел B0"

## Схема БД

### Таблица `sources` — Исходные документы

Метаданные документов, которые разбиты на чанки.

```sql
CREATE TABLE sources (
  source_id     TEXT PRIMARY KEY,
  title         TEXT NOT NULL,
  doc_version   TEXT NOT NULL,
  valid_from    DATE NOT NULL,
  content_hash  TEXT NOT NULL
);
```

**Пример записи:**
```json
{
  "source_id": "busiverse-2026-10-13",
  "title": "RAG-документация BusiVerse",
  "doc_version": "2026-10-13",
  "valid_from": "2026-10-13",
  "content_hash": "sha256_abc123..."
}
```

**Зачем:**
- Версионирование документации
- Идемпотентный ре-ингест (по `content_hash`)
- Отслеживание актуальности

---

### Таблица `chunks` — Чанки с эмбеддингами

Главная таблица. Фрагменты текста с метаданными и векторными представлениями.

```sql
CREATE TABLE chunks (
  -- Идентификация
  chunk_id      TEXT PRIMARY KEY,
  source_id     TEXT NOT NULL REFERENCES sources(source_id),
  
  -- Категоризация
  business_type TEXT NOT NULL,  -- 'coffee_shop', 'pickup_point', etc.
  block         TEXT NOT NULL,  -- 'offline', 'online', 'global'
  scope         TEXT NOT NULL DEFAULT 'business',  -- 'global' | 'business'
  
  -- Иерархия
  section_code  TEXT,           -- '1.3', 'B0.2', '0', '11'
  section_title TEXT,           -- 'Финансовая модель'
  block_title   TEXT,           -- 'Лист «Кофейня (Москва)»'
  heading_path  TEXT[] NOT NULL DEFAULT '{}',  -- ['1. ОФЛАЙН — КОФЕЙНЯ', '1.3. Финансовая модель', ...]
  
  -- Тип контента
  chunk_type    TEXT NOT NULL,  -- 'case', 'sop', 'table', 'checklist', 'prose'
  topics        TEXT[] NOT NULL DEFAULT '{}',  -- ['НПД', 'налоги', 'самозанятость']
  
  -- Small-to-Big
  parent_id     TEXT,           -- ID родительского чанка (секции)
  chunk_index   INT NOT NULL DEFAULT 0,  -- Порядковый номер внутри секции
  
  -- Трассировка
  line_start    INT,
  line_end      INT,
  token_count   INT NOT NULL,
  content_hash  TEXT NOT NULL,
  
  -- Контент
  text          TEXT NOT NULL,
  
  -- Поиск
  tsv           TSVECTOR GENERATED ALWAYS AS (to_tsvector('russian', text)) STORED,
  embedding     VECTOR(1024)
);
```

#### Ключевые поля

**`business_type`** — Ниша бизнеса:
- `coffee_shop` — Кофейня «кофе с собой»
- `pickup_point` — ПВЗ маркетплейса
- `mini_bakery` — Мини-пекарня
- `manicure_studio` — Маникюрная студия
- `auto_service` — Автосервис, 2 поста
- `marketplace_seller` — Селлер на маркетплейсе
- `online_school` — Онлайн-школа
- `smm_agency` — SMM / маркетинговое агентство
- `own_online_store` — Интернет-магазин на своём сайте
- `remote_accounting` — Удалённая бухгалтерия
- `global` — Сквозные разделы

**`scope`** — Область применения:
- `global` — Применимо ко всем нишам (налоги, регуляторика)
- `business` — Специфично для одной ниши

**`chunk_type`** — Тип контента:
- `case` — Кейс (никогда не резать!)
- `sop` — Standard Operating Procedure (никогда не резать!)
- `table` — Таблица (атомарна, резать только если не влезает)
- `checklist` — Чек-лист
- `prose` — Текст (можно резать с перекрытием 15%)

**`heading_path`** — Иерархический путь:
```json
[
  "1. ОФЛАЙН — КОФЕЙНЯ",
  "1.3. Финансовая модель",
  "Лист «Кофейня (Москва)»"
]
```

**Зачем:**
1. Контекст для эмбеддингов (contextual retrieval)
2. Показывать пользователю источник цитаты
3. Даёт модели понять контекст чанка

**`parent_id`** — Small-to-Big:
- Дочерние чанки (блоки) ссылаются на родительский (секцию)
- Ищем по блокам, отдаём секцию для контекста

**`tsv`** — Generated column для полнотекстового поиска:
```sql
GENERATED ALWAYS AS (to_tsvector('russian', text)) STORED
```
- Автоматически обновляется при изменении `text`
- Конфигурация `russian`: стемминг, стоп-слова
- Не требует ручной синхронизации

**`embedding`** — Векторное представление (1024 измерения):
- Генерируется моделью эмбеддингов (выбирается позже)
- Для семантического поиска
- Cosine distance для похожести

---

### Таблица `chunk_links` — Внутренние ссылки

Связи между чанками для разрешения ссылок типа "см. раздел B0".

```sql
CREATE TABLE chunk_links (
  from_chunk_id TEXT NOT NULL REFERENCES chunks(chunk_id),
  to_section    TEXT NOT NULL,
  PRIMARY KEY (from_chunk_id, to_section)
);
```

**Пример:**
```json
{
  "from_chunk_id": "marketplace_seller-6.3",
  "to_section": "B0"
}
```

Значит: в чанке про селлеров есть ссылка на сквозной раздел B0 (регуляторика).

## Индексы

### 1. `chunks_embedding_idx` — Векторный поиск (HNSW)

```sql
CREATE INDEX chunks_embedding_idx 
ON chunks USING hnsw (embedding vector_cosine_ops);
```

**Назначение:** Approximate Nearest Neighbor search по косинусному расстоянию.

**Параметры:**
- Алгоритм: HNSW (Hierarchical Navigable Small World)
- Метрика: cosine distance
- На 600 чанках: мгновенный поиск

**Запрос:**
```sql
SELECT chunk_id, text, 1 - (embedding <=> $1) AS similarity
FROM chunks
WHERE business_type = 'coffee_shop' OR scope = 'global'
ORDER BY embedding <=> $1
LIMIT 50;
```

---

### 2. `chunks_tsv_idx` — Полнотекстовый поиск (GIN)

```sql
CREATE INDEX chunks_tsv_idx 
ON chunks USING gin (tsv);
```

**Назначение:** Поиск по точным терминам и русским словам.

**Что индексирует:**
- Generated column `tsv` (автоматически синхронизируется с `text`)
- Стемминг: "налог", "налога", "налогам" → одна основа
- Стоп-слова: "и", "в", "на" игнорируются

**Запрос:**
```sql
SELECT chunk_id, text, ts_rank(tsv, query) AS rank
FROM chunks, to_tsquery('russian', 'НПД & 2026') AS query
WHERE tsv @@ query 
  AND (business_type = 'coffee_shop' OR scope = 'global')
ORDER BY rank DESC
LIMIT 50;
```

**Примеры терминов, которые ловит:**
- "ст. 14.5 КоАП"
- "152-ФЗ"
- "Правила № 2463"
- "НПД в 2026 году"

---

### 3. `chunks_filter_idx` — Фильтрация по нише

```sql
CREATE INDEX chunks_filter_idx 
ON chunks (business_type, section_code);
```

**Назначение:** Быстрая фильтрация перед поиском.

**Типичный запрос:**
```sql
WHERE business_type = 'coffee_shop' OR scope = 'global'
```

**Зачем:** Без фильтра "сколько стоит открыть кофейню" и "сколько стоит открыть ПВЗ" смешаются в выдаче.

---

### 4. `chunks_scope_idx` — Глобальные чанки

```sql
CREATE INDEX chunks_scope_idx 
ON chunks (scope);
```

**Назначение:** Быстро находить сквозные разделы.

**Сквозные разделы:**
- `0` — Общие положения (налоги 2026)
- `B0` — Регуляторика для онлайн-бизнеса
- `B0.1`–`B0.6` — Подразделы B0
- `11` — Сводка финансовых моделей

---

### 5. `chunks_parent_idx` — Small-to-Big

```sql
CREATE INDEX chunks_parent_idx 
ON chunks (parent_id);
```

**Назначение:** Быстро подтягивать родительский чанк.

**Запрос:**
```sql
-- Нашли блок
SELECT * FROM chunks WHERE chunk_id = 'coffee_shop-1.3-moscow';

-- Подтягиваем родительскую секцию для контекста
SELECT * FROM chunks WHERE chunk_id = (
  SELECT parent_id FROM chunks WHERE chunk_id = 'coffee_shop-1.3-moscow'
);
```

## Детальное описание шагов

### Шаг 1. Запрос пользователя

**Вход:** Текст вопроса
```
"Какая выручка у кофейни в Москве?"
```

**Что происходит:**
- Пользователь вводит вопрос в UI
- Система определяет, нужен ли поиск по БД или достаточно общих знаний модели

---

### Шаг 2. Определение ниши (`business_type`)

**Два пути:**

#### Путь A: Селектор в UI (основной)

```typescript
// Пользователь выбрал нишу в UI
const businessType = userSelectedNiche; // 'coffee_shop'
const filter = `business_type = '${businessType}' OR scope = 'global'`;
```

**Преимущества:**
- ✅ Точно, без ошибок
- ✅ Быстро
- ✅ Бесплатный сигнал: видим несоответствие вопроса и выбранной ниши

**Когда использовать:** Всегда, когда пользователь выбрал нишу.

#### Путь B: Классификатор (fallback)

```typescript
// Ниша не выбрана, классифицируем вопрос
const classification = await classifyQuestion(question);

if (classification.confidence > 0.8) {
  const businessType = classification.businessType;
  const filter = `business_type = '${businessType}' OR scope = 'global'`;
} else {
  // Не уверены — ищем без фильтра
  const filter = `1=1`; // поиск по всему корпусу
}
```

**Когда использовать:** Когда ниша не выбрана.

**Важно:** Лучше вернуть результаты из нескольких ниш, чем отфильтровать правильную.

---

### Шаг 3. SQL-фильтр

**SQL:**
```sql
WHERE business_type = 'coffee_shop' OR scope = 'global'
```

**Что происходит:**
- Фильтруем только чанки кофейни
- **Плюс** сквозные разделы (`scope = 'global'`):
  - Налоги (раздел 0)
  - Регуляторика (раздел B0)
  - Сводка финмоделей (раздел 11)

**Результат:** ~80 чанков кофейни + ~50 сквозных = **~130 чанков для поиска**

**Зачем:** Без фильтра выдача смешает разные ниши:
```
Вопрос: "Сколько стоит открыть точку?"
Без фильтра: кофейня (250K), ПВЗ (180K), пекарня (320K) → путаница
С фильтром: только кофейня → чёткий ответ
```

---

### Шаг 4. Параллельный поиск

#### Vector Search

**SQL:**
```sql
SELECT 
  chunk_id,
  text,
  heading_path,
  1 - (embedding <=> $1::vector) AS similarity,
  ROW_NUMBER() OVER (ORDER BY embedding <=> $1::vector) AS rank_vector
FROM chunks
WHERE business_type = 'coffee_shop' OR scope = 'global'
ORDER BY embedding <=> $1::vector
LIMIT 50;
```

**Параметры:**
- `$1` — эмбеддинг запроса (vector(1024))
- `<=>` — оператор cosine distance
- Index: `chunks_embedding_idx` (HNSW)

**Что ловит:**
- Семантически похожие чанки
- Синонимы ("выручка" ≈ "доход" ≈ "прибыль")
- Перефразирования

**Что НЕ ловит:**
- Точные номера статей ("ст. 14.5" vs "ст. 14.8")
- Названия документов ("152-ФЗ" vs "161-ФЗ")

---

#### Fulltext Search

**SQL:**
```sql
SELECT 
  chunk_id,
  text,
  heading_path,
  ts_rank(tsv, query) AS rank_fulltext,
  ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, query) DESC) AS rank_fulltext_pos
FROM chunks, 
  to_tsquery('russian', 'выручка & кофейня & Москва') AS query
WHERE tsv @@ query
  AND (business_type = 'coffee_shop' OR scope = 'global')
ORDER BY ts_rank(tsv, query) DESC
LIMIT 50;
```

**Параметры:**
- `to_tsquery('russian', ...)` — парсинг запроса с русским стеммингом
- `@@` — оператор полнотекстового поиска
- `ts_rank` — ранжирование по TF-IDF
- Index: `chunks_tsv_idx` (GIN)

**Что ловит:**
- Точные термины
- Словоформы ("выручка", "выручки", "выручке" → одна основа)
- Числа и коды ("2026", "14.5", "B0.2")

**Операторы запроса:**
```sql
'НПД & 2026'              -- И (оба слова)
'кофейня | пекарня'       -- ИЛИ (любое слово)
'налог & !самозанятость'  -- И НЕ (налог, но не самозанятость)
'"точные слова"'          -- Фраза (exact match)
```

---

### Шаг 5. RRF слияние (Reciprocal Rank Fusion)

**Алгоритм:**
```python
def rrf_score(rank_vector: int, rank_fulltext: int, k: int = 60) -> float:
    """
    Reciprocal Rank Fusion
    k=60 — стандартное значение из оригинальной статьи (2009)
    """
    score_vector = 1 / (k + rank_vector) if rank_vector else 0
    score_fulltext = 1 / (k + rank_fulltext) if rank_fulltext else 0
    return score_vector + score_fulltext

# Для каждого чанка
for chunk in all_chunks:
    chunk.rrf_score = rrf_score(chunk.rank_vector, chunk.rank_fulltext)

# Сортировка
sorted_chunks = sorted(all_chunks, key=lambda x: x.rrf_score, reverse=True)
top_20 = sorted_chunks[:20]
```

**SQL реализация:**
```sql
WITH vector_results AS (
  -- Vector search top-50
  SELECT chunk_id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank_vector
  FROM chunks
  WHERE business_type = 'coffee_shop' OR scope = 'global'
  ORDER BY embedding <=> $1
  LIMIT 50
),
fulltext_results AS (
  -- Fulltext search top-50
  SELECT chunk_id, ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, query) DESC) AS rank_fulltext
  FROM chunks, to_tsquery('russian', $2) AS query
  WHERE tsv @@ query AND (business_type = 'coffee_shop' OR scope = 'global')
  ORDER BY ts_rank(tsv, query) DESC
  LIMIT 50
),
rrf_scores AS (
  -- RRF слияние
  SELECT 
    COALESCE(v.chunk_id, f.chunk_id) AS chunk_id,
    COALESCE(1.0 / (60 + v.rank_vector), 0) +
    COALESCE(1.0 / (60 + f.rank_fulltext), 0) AS rrf_score
  FROM vector_results v
  FULL OUTER JOIN fulltext_results f ON v.chunk_id = f.chunk_id
)
SELECT c.*, r.rrf_score
FROM chunks c
JOIN rrf_scores r ON c.chunk_id = r.chunk_id
ORDER BY r.rrf_score DESC
LIMIT 20;
```

**Почему RRF, а не веса?**
- ✅ Не надо подбирать коэффициенты α и β
- ✅ Работает out-of-the-box
- ✅ Стандарт с 2009 года (Cormack, Clarke, Buettcher)
- ✅ Устойчив к разным шкалам (cosine 0..1 vs ts_rank произвольное)

**Результат:** top-20 чанков

---

### Шаг 6. Reranking

**Назначение:** Переранжировать top-20 с учётом полного контекста запроса.

**Модель reranker'а:** Выбирается позже (не влияет на схему БД).

**Псевдокод:**
```python
# Reranker модель (например, cross-encoder)
reranker = load_reranker_model()

# Для каждого из top-20
for chunk in top_20:
    # Оценка релевантности: query + chunk.text
    relevance_score = reranker.predict(
        query=user_question,
        document=chunk.text
    )
    chunk.rerank_score = relevance_score

# Сортировка по rerank_score
sorted_chunks = sorted(top_20, key=lambda x: x.rerank_score, reverse=True)
top_5_8 = sorted_chunks[:8]  # берём top-5..8
```

**Популярные reranker'ы:**
- Cohere Rerank
- Jina Reranker
- BGE Reranker
- Cross-encoders (BERT-based)

**Результат:** top-5..8 наиболее релевантных чанков

---

### Шаг 7. Small-to-Big

**Назначение:** Подтянуть родительский чанк (секцию) для контекста.

**SQL:**
```sql
-- Нашли блок (дочерний чанк)
SELECT * FROM chunks 
WHERE chunk_id = 'coffee_shop-1.3-moscow'
  AND parent_id IS NOT NULL;

-- Подтягиваем родителя (секцию)
SELECT * FROM chunks 
WHERE chunk_id IN (
  SELECT DISTINCT parent_id 
  FROM chunks 
  WHERE chunk_id = ANY($1::text[])  -- массив найденных chunk_id
    AND parent_id IS NOT NULL
);
```

**Пример:**

**Найден:** Блок `coffee_shop-1.3-moscow` (таблица)
```json
{
  "chunk_id": "coffee_shop-1.3-moscow",
  "parent_id": "coffee_shop-1.3",
  "block_title": "Лист «Кофейня (Москва)»",
  "text": "| Параметр | Значение |\n| Выручка | 750K |\n..."
}
```

**Подтягиваем:** Секцию `coffee_shop-1.3` (родитель)
```json
{
  "chunk_id": "coffee_shop-1.3",
  "parent_id": null,
  "section_title": "Финансовая модель",
  "text": "Финансовая модель кофейни включает расчёт выручки, затрат...\n\nВнутри этой секции:\n- Лист «Кофейня (Москва)»\n- Лист «Кофейня (регион)»\n- Скрытые расходы\n- Отраслевые бенчмарки"
}
```

**Зачем:**
- Таблица без введения непонятна
- Родитель даёт контекст: что это за таблица, откуда данные
- Модель видит полную картину

**Результат:** top-5..8 + их родители (если есть)

---

### Шаг 8. Разрешение ссылок

**Назначение:** Добавить чанки, на которые есть ссылки в найденных результатах.

**SQL:**
```sql
-- Находим все ссылки из найденных чанков
SELECT DISTINCT to_section
FROM chunk_links
WHERE from_chunk_id = ANY($1::text[]);  -- массив найденных chunk_id

-- Для каждой to_section подтягиваем чанк
SELECT * FROM chunks
WHERE section_code IN (
  SELECT DISTINCT to_section
  FROM chunk_links
  WHERE from_chunk_id = ANY($1::text[])
);
```

**Пример:**

**Найден:** Чанк `marketplace_seller-6.3` про селлеров
```json
{
  "chunk_id": "marketplace_seller-6.3",
  "text": "Для маркировки рекламы селлеры должны соблюдать требования... (см. раздел B0.2)"
}
```

**Ссылка в `chunk_links`:**
```json
{
  "from_chunk_id": "marketplace_seller-6.3",
  "to_section": "B0.2"
}
```

**Подтягиваем:** Чанк раздела B0.2
```json
{
  "chunk_id": "global-B0.2",
  "section_code": "B0.2",
  "section_title": "Маркировка интернет-рекламы",
  "text": "С 1 сентября 2026 года вся интернет-реклама должна быть промаркирована..."
}
```

**Зачем:**
- Ответ без связанного раздела будет неполным
- Ссылки часто указывают на ключевой контекст
- Автоматическое разрешение снижает hallucinations

**Результат:** top-5..8 + родители + связанные чанки

## Примеры использования

### Пример 1: Вопрос по конкретной нише

**Вопрос:** "Какие налоги платит онлайн-школа?"

**Шаги:**
1. Селектор UI: `business_type = 'online_school'`
2. Фильтр: `WHERE business_type = 'online_school' OR scope = 'global'`
3. Vector search: семантически похожие на "налоги онлайн-школа"
4. Fulltext search: слова "налог*", "онлайн", "школа"
5. RRF: top-20
6. Rerank: top-5
7. Small-to-big: подтянуть родительские секции
8. Разрешить ссылки: найти ссылки на раздел 0 (Общие положения)
9. Промпт: источники из раздела 7 (онлайн-школа) + раздела 0 (налоги)

**Результат:** Точный ответ про налогообложение онлайн-школы + сквозные положения.

---

### Пример 2: Вопрос с точным термином

**Вопрос:** "Что грозит за нарушение ст. 14.5 КоАП?"

**Шаги:**
1. Классификатор: не может определить нишу → фильтр `1=1` (все ниши)
2. Vector search: семантика "штраф", "нарушение", "административный"
3. **Fulltext search: точное совпадение "14.5 КоАП"** ← ключевой момент
4. RRF: fulltext находит точный термин, vector даёт контекст
5. Rerank: top-5
6. Small-to-big: подтянуть описание статьи
7. Промпт: текст статьи + примеры нарушений

**Результат:** Точный ответ про конкретную статью КоАП.

---

### Пример 3: Вопрос без выбранной ниши

**Вопрос:** "Как открыть точку?"

**Шаги:**
1. Классификатор: уверенность низкая (может быть любая ниша)
2. Фильтр: `1=1` (поиск по всем нишам)
3. Vector + Fulltext поиск
4. RRF: top-20 включают кофейню, ПВЗ, пекарню
5. Rerank: отбирает наиболее универсальные чанки
6. Промпт: общие шаги + примеры из разных ниш

**Результат:** Общий ответ с предложением уточнить нишу.

## Метрики и оптимизация

### Eval-набор

**Цель:** Выбрать модель эмбеддингов и настроить параметры поиска.

**Состав:**
- 40 вопросов: 30 по нишам + 10 по сквозным разделам
- Для каждого вопроса размечены ожидаемые `chunk_id`

**Метрики:**
- `recall@5` — доля вопросов, где нужный чанк попал в топ-5
- `recall@10` — то же для топ-10
- `MRR` (Mean Reciprocal Rank) — насколько высоко стоит первый правильный чанк
- `nDCG@10` — качество ранжирования с учётом порядка

**Целевые значения:**
- `recall@5 ≥ 0.85`
- `MRR ≥ 0.7`

**Что тестировать:**
1. Модель эмбеддингов (2-3 кандидата)
2. Размер чанка (500 / 700 / 1000 токенов)
3. Перекрытие для prose (0% / 15% / 25%)
4. Наличие rerank (с ним vs без него)
5. Top-k на каждом этапе (50→20→5 vs 100→50→10)

---

### Параметры для настройки

| Параметр | Текущее значение | Как влияет |
|----------|------------------|------------|
| Vector search limit | 50 | Больше → лучше recall, медленнее |
| Fulltext search limit | 50 | Больше → лучше recall, медленнее |
| RRF k | 60 | Меньше → больше вес topранга |
| RRF output limit | 20 | Компромисс между качеством и скоростью rerank |
| Rerank output limit | 5-8 | Баланс: контекст vs шум |
| Small-to-big | Включено | Даёт контекст, увеличивает размер промпта |
| Разрешение ссылок | Включено | Даёт полноту, увеличивает размер промпта |

---

## Требования

### Функциональные

1. Поиск должен находить нужные чанки для 85%+ вопросов (recall@5 ≥ 0.85)
2. Фильтрация по нише обязательна (без неё смешиваются ответы)
3. Гибридный поиск (vector + fulltext) обязателен для точных терминов
4. Small-to-big даёт контекст без раздувания индекса
5. Разрешение ссылок автоматическое

### Нефункциональные

1. **Скорость:**
   - Vector search на 600 чанках: <50ms
   - Fulltext search: <50ms
   - Общее время retrieval: <200ms
   
2. **Масштабируемость:**
   - Текущий корпус: ~600 чанков
   - Ожидаемый рост: до 2000 чанков при добавлении новых ниш
   - HNSW и GIN индексы масштабируются линейно

3. **Обслуживание:**
   - Ре-ингест по `content_hash`: идемпотентно
   - Смена модели эмбеддингов: переэмбеддить ~600 чанков (минуты)
   - Обновление документации: перегенерировать изменённые чанки

## Риски и ограничения

### Риск 1: Модель эмбеддингов не синхронизирована

**Описание:** Проект ассистента использует другую модель эмбеддингов → векторный поиск возвращает мусор без ошибок.

**Митигация:**
- Зафиксировать модель в README обоих проектов
- Версионировать эмбеддинги (поле `embedding_model_version`)
- CI-проверка: тест, что модели совпадают

---

### Риск 2: Классификатор ниши ошибается

**Описание:** LLM определил "кофейня" вместо "пекарня" → фильтр отсёк правильные чанки.

**Митигация:**
- Селектор в UI — основной путь (точность 100%)
- Классификатор — только fallback
- Порог уверенности: если <0.8, не фильтровать вообще
- Логирование: видим несоответствие вопроса и выбранной ниши

---

### Риск 3: Таблица разрезана, потеряла смысл

**Описание:** Большая таблица не влезла в 700 токенов, разрезали без шапки → кусок бессмысленен.

**Митигация:**
- Правило: в каждом куске **повторяем шапку**
- Для кейсов и SOP: **никогда не резать**
- Атрибут `chunk_type` помогает соблюдать правила

---

### Риск 4: Ссылка не разрешилась

**Описание:** В чанке написано "см. раздел B0", но запись в `chunk_links` отсутствует → ответ неполный.

**Митигация:**
- Парсинг ссылок при нарезке (регулярка: `см\. раздел ([A-Z0-9\.]+)`)
- Проверка целостности: все ссылки в `chunk_links` должны существовать в `chunks`
- Логирование: warning при недостающей ссылке
