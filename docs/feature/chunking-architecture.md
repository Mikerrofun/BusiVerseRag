# Чанкование: как это работает

Полное описание этапа чанкования — от исходного файла до БД. Дополняет `docs/plan/03-chunking-plan.md` (план) и `docs/plan/04-chunking-commands.md` (команды). Здесь — «как устроено и почему», чтобы можно было ориентироваться в коде и переиспользовать функции.

## Общая картина

```
RAG-документация_BusiVerse.raw.md   (исходник, не трогаем)
        │  этап очистки (план 2): валидация исходника, стирание повторов,
        │  тегов, дублей и мусора
        ▼
RAG-документация_BusiVerse.md       (очищенный markdown)
        │  npm run chunk
        ▼
data/chunks/<группа>/<раздел>/<chunk_id>.json   (дерево папок, правится руками)
data/chunking-report.md
        │  npm run chunk:validate   (проверка всех чанков)
        │  npm run chunk:load --apply   (запись в БД, вручную)
        ▼
Postgres: sources / chunks / chunk_links
```

Важно: `npm run chunk` БД не трогает вообще — он только режет и пишет файлы. Запись в БД — отдельная команда, отдельным шагом, вручную.

## Структура документа и три уровня чанков

Парсер (`lib/parse.ts`) разбирает очищенный файл в дерево: **группы → секции → блоки**.

- **Группа** — крупная часть документа (ниша: бухгалтерия, склад, ...; плюс B0 и краевые группы).
- **Секция** — раздел с кодом вида `10.1` (заголовок H2 внутри группы).
- **Блок** — подраздел внутри секции (заголовок H3, `###`). Если у секции нет дочерних H3 — всё её тело считается одним **неявным блоком** без заголовка.

`buildChunks` (lib/emit.ts) превращает это дерево в чанки трёх уровней:

### Уровень 1 — родительские чанки секций

На каждую секцию — один чанк-оглавление:

- `chunk_id = {business_type}-{section_code}`, например `accounting-10.1`;
- `parent_id = null` — это вершина своей ветки;
- текст собирается, а не копируется: `## {название секции}` + интро-абзацы секции + список «Содержит блоки:» с названиями всех дочерних блоков.

Родитель — навигационная карточка: по нему видно, что есть в разделе и куда идти за деталями. При поиске он служит «якорем» контекста (см. раздел про ссылки и сборку ниже).

### Уровень 2 — блочные чанки

Каждый блок секции — чанк (или несколько кусков):

- `chunk_id = {parent_id}-b{NN}` — `accounting-10.1-b01`, `b02`, ...;
- `parent_id` = id родителя секции;
- `block_title` = заголовок H3 блока (см. ниже);
- если блок влезает в бюджет — один чанк без суффикса; если нет — куски `-p1`, `-p2`, ... с заполненными `part_index` / `part_total` и тем же `parent_id`.

### Уровень 0 — глобальные чанки

Два служебных: `global-preamble` (шапка документа) и `global-B0` (список всех ниш). У них нет ни секции, ни блока.

### Покрытие строк

После сборки чанки сортируются по `line_start`, и каждому проставляется `line_end = line_start следующего чанка − 1`. Итог: чанки покрывают файл подряд, без дыр и перекрытий — это проверяет валидатор.

## Идентификаторы: как читать `accounting-10.1-b03-p2`

```
accounting  — бизнес-тип (ниша)
10.1        — код секции
b03         — номер блока внутри секции
p2          — второй кусок дроблёного блока (нет суффикса = блок целиком)
```

Все куски одного блока имеют одинаковый `parent_id` и упорядочены по `part_index` — поэтому «достать соседей куска» это один запрос `where parent_id = ... order by part_index`, а не парсинг id.

## Поля чанка: `block_title` и зачем он нужен

`block_title` — заголовок H3-блока. Заполнен только у блочных чанков; `null` у:

- **родительских чанков секций** — у них вместо него `section_title` (родитель описывает секцию целиком, своего H3 у него нет);
- **глобальных чанков** — нет ни секции, ни блока;
- **неявных блоков** — тело секции без дочерних H3 не имеет заголовка.

Зачем поле нужно:

1. **Цитаты в ответах RAG.** `heading_path` + `section_title` + `block_title` + `line_start/line_end` — набор полей для ссылки на источник: «Раздел 10.2 → Кейс: клиент требует возврат, строки 512–540».
2. **Классификация типа.** Тип чанка определяется по заголовку блока и коду секции (см. ниже).

## Типы чанков и стратегии дробления

Тип (`chunk_type`) определяет, КАК блок режется — это главное назначение поля. Пять типов:

| Тип | Что это | Правило определения | Дробление |
|---|---|---|---|
| `prose` | обычный текст: интро, регламенты, описания | секции N.1 и N.7; блоки с таблицей вне типовых секций → по содержимому | по абзацам, бюджет 500–700 |
| `table` | блок с markdown-таблицей | секции N.3, N.4, N.5, N.8; «Матрица сбоев» в N.6; неявные блоки с таблицей | по строкам таблицы, шапка в каждом куске |
| `case` | кейсы в N.2 (разбор ситуаций) | секция N.2, заголовок не из `serviceN2Headers` | **не дробится никогда** |
| `sop` | SOP-XX в N.6 | заголовок `SOP-\d` | не дробится |
| `checklist` | чек-листы в N.6 | заголовок содержит «Чек-лист» | не дробится |

Логика в `chunkTypeFor` (emit.ts): сначала смотрит код секции (N.2 → кейсы, N.6 → SOP/чек-лист/матрица, N.1/N.7 → prose, остальное → table), для нетиповых секций — по наличию таблицы в теле. Неявные блоки тоже классифицируются по содержимому: в фактическом файле тела N.7 — таблицы, поэтому тип по содержимому, а не «prose по плану» — иначе таблицу не дробить по строкам.

Кейс/SOP/чек-лист не режутся даже при превышении бюджета: их ценность в целостности — разорванный чек-лист или SOP в двух кусках бесполезен. Валидатор это знает и не ругается на их превышение.

## Дробление таблиц: шапка в каждом куске

Ключевое правило: **строки таблицы никогда не существуют отдельно от своей шапки**.

Механика (`tableSegments` в lib/split.ts):

1. Тело блока разбирается на плоский список сегментов в порядке документа: строки таблиц, текстовые абзацы между ними.
2. Шапка (строка заголовков + строка-разделитель `|---|`) выделяется в объект с её токенами. Каждая строка данных — сегмент `kind: 'row'` со ссылкой на объект шапки **своей** таблицы. У строк второй таблицы в блоке — другой объект шапки.
3. Жадная упаковка собирает сегменты в бюджет 700. Стоимость строки считается **вместе с шапкой**, если шапки этой таблицы в текущей группе ещё нет (`segCost`) — бюджет честно учитывает будущую вставку шапки. Стоимость считается **после** возможного сброса группы: первая строка новой группы платит за шапку (иначе кусок вылезал бы за бюджет — на этом уже ловили баг).
4. При сборке куска: когда встречается строка, чья шапка отличается от текущей в куске, перед ней вставляются обе строки шапки (заголовки + разделитель).

Что это даёт:

- кусок, начинающийся с продолжения таблицы, автоматически получает шапку в начале — таблица читается сама по себе;
- если в куске строки двух разных таблиц (блок содержит несколько таблиц), каждая идёт со своей шапкой — смешивание возможно, потому что резка идёт только по бюджету, но кусок всё равно самодостаточен;
- «целая нужная таблица» получается естественно: строки одной таблицы идут в документе подряд, значит и по кускам они подряд, и перед ними всегда её шапка.

Компромисс: кусок с двумя полутаблицами чуть «размыт» по смыслу для эмбеддинга. Ужесточить можно одной строкой (сброс группы при смене шапки), но ценой недозаполненных кусков-карликов. На текущем документе таблицы разнесены текстом, таких кусков мало.

## Ссылки между разделами: что это и полный жизненный цикл

**Что это.** Внутренние перекрёстные ссылки документа: в тексте написано «см. раздел 6.2», «подробнее в разделе 3.4». Они нужны, чтобы при ответе RAG мог подтянуть связанный раздел, а не только текст найденного чанка.

**Как извлекаются** (`extractLinks`, lib/links.ts) — чистый регэксп, без LLM:

- шаблон ловит слово «раздел» в любых падежах («раздела», «разделе») и следующий за ним код;
- код проверяется по **белому списку** реально существующих кодов секций — поэтому «раздел 115-ФЗ» или «раздел 6–10» отфильтровываются, а «см. раздел 6.2» становится ссылкой;
- дубли схлопываются по паре `chunk_id | код` — одна ссылка на раздел считается один раз на чанк;
- для каждой ссылки запоминается `first_line` — реальный номер строки упоминания в исходном файле.

**Как хранятся.** `_links.json` на диске → таблица `chunk_links` в БД. Привязка однонаправленная: `from_chunk_id` — чанк, **в котором** написана ссылка; `to_section` — код секции-цели. Цель хранится кодом секции, а не id чанка, потому что «раздел 6.2» — это секция целиком, а не один чанк.

**Как используются при поиске.** Эмбеддинг ссылки не видит — они не для поиска, а для обхода графа после поиска:

1. векторный поиск → хит-чанк;
2. `select * from chunk_links where from_chunk_id = хит`;
3. для каждой цели достаём родительский чанк той секции (`chunk_id = '{business_type}-{to_section}'`) или её дочерние чанки — подкладываем в контекст модели.

Без этого модель ответила бы только по тексту хита и пропустила связанную информацию из соседнего раздела.

## Валидация: что и как проверяется

`npm run chunk:validate` (lib/validate.ts) — это **другой** валидатор, не тот, что проверял исходник на этапе очистки. Он рекурсивно обходит всё дерево `data/chunks` и проверяет **каждый** JSON-файл (служебные с префиксом `_` пропускает). Проверки:

1. обязательные поля заполнены;
2. `chunk_id` уникальны;
3. `parent_id` указывает на существующий чанк;
4. целостность частей: `part_index` образует ряд 1..part_total без дыр;
5. бюджет токенов с пересчётом (500–700; кейсы/SOP/чек-листы могут превышать);
6. у куска таблицы шапка стоит непосредственно перед первой строкой данных (шапка опознаётся по разделителю следом за ней — иначе сама шапка подходит под шаблон «строки данных» и ломает проверку);
7. куски одного блока не перекрываются по строкам;
8. ссылки указывают на существующие секции;
9. чанки покрывают строки файла без дыр и перекрытий.

Плюс `checkSourceStructure`: структура исходника не изменилась с прошлого прогона (сравнение с `parseDocument`). Итог — «OK — все проверки зелёные» или список проблем с exit-кодом 1. Режим `--after-edit` — для проверки после ручных правок JSON (пропускает только проверку покрытия строк).

## Запись в БД: dry-run, upsert, retry

`npm run chunk:load` (lib/load.ts) — запускается только вручную, требует `DATABASE_URL`.

- **Без флага** — dry-run: читает `data/chunks`, печатает план (сколько чанков и ссылок будет записано), ничего не пишет.
- **С `--apply`**:
  1. upsert источника в `sources` (id, название, версия, хеш содержимого);
  2. upsert каждого чанка в `chunks` по `chunk_id`; при изменении текста `embedding` сбрасывается в `NULL` — его пересчитает следующий этап;
  3. вставка ссылок в `chunk_links` (`on conflict do nothing`).
- **Retry**: каждый запрос обёрнут в `withRetry` — до 3 попыток с паузой 1с → 2с → 4с; каждая неудачная попытка логируется с id чанка. После 3 неудач — падение с ошибкой вида `chunk <id>: не удалось после 3 попыток — <причина>`.
- **Идемпотентность**: все записи — upsert, поэтому после сбоя на середине повторный `--apply` спокойно докатывает остаток, дублей не будет.

## Сборка контекста при поиске (как это будет работать)

Эмбеддинг считается по каждому куску отдельно — в этом смысл дробления: строка «Контент-менеджер» лежит в куске, где она не размыта 1900 токенами соседних строк. Схема расширения контекста:

1. векторный поиск → хит-кусок (например `...-b03-p2`);
2. добавляем его родителя (чанк-оглавление секции);
3. и только если вопрос требует полноты («перечисли все роли», «сравни варианты») — докатываем остальные куски блока по `parent_id` + `part_index` и собираем таблицу/блок целиком.

Куски одного блока покрывают его подряд без дыр, так что склейка по `part_index` — это просто конкатенация `text`. Пихать полную таблицу в контекст на каждый чих не нужно: каждый кусок самодостаточен (шапка внутри).

## Переиспользуемые функции

Функции чистые, БД и файловую систему не знают — можно дёргать из будущих этапов (topics, эмбеддинги, поиск):

| Функция | Файл | Сигнатура / суть |
|---|---|---|
| `parseDocument` | lib/parse.ts | `(lines: string[]) → ParsedDoc` — дерево групп/секций/блоков |
| `assertStructure` | lib/parse.ts | проверка структуры исходника по ожиданиям |
| `splitBlock` | lib/split.ts | `(block, type, countTokens) → Part[]` — диспетчер дробления по типу |
| `countTokens` | lib/tokens.ts | подсчёт токенов (js-tiktoken) |
| `buildChunks` | lib/emit.ts | `(doc) → InternalChunk[]` — три уровня чанков + родители |
| `extractLinks` | lib/links.ts | `(chunks) → ChunkLink[]` — регэксп + белый список |
| `writeTree` | lib/emit.ts | запись дерева папок + `_links.json` + отчёт |
