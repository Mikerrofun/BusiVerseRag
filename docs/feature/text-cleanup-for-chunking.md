## 1. Зачем

`RAG-документация_BusiVerse.md` — сырой markdown после конвертации PDF. В нём 11 262 тега `<br>`, 11 расплющенных OCR-блоков, 15 заголовков SOP без `##`, 387 склеек кириллицы с латиницей, 2 символа замены `U+FFFD`.

Нарезать это нельзя. Чанкер структурный: он идёт по файлу сверху вниз и режет по `^## `. Всё, что между заголовками, становится телом чанка. Значит нарезку ломают три вещи:

- нет `##` — нет границы, SOP склеивается с предыдущей таблицей;
- расплющенная таблица — чанк типа `table` с одной строкой перемешанных данных;
- `<br>` внутри ячейки — разметка попадает в текст чанка и в эмбеддинг.

Задача: привести файл к виду, где структура однозначна, и доказать это проверкой, а не на глаз.

## 2. Где/что уже было

План `docs/plan/02-text-cleanup-plan.md` уже описывал шаги 1–8 и критерии приёмки. Сырой файл уже лежал: `docs/source/RAG-документация_BusiVerse.raw.md`.

Задача была не писать новое, а использовать существующее: план как ТЗ, сырой файл как вход. Логика очистки не изобреталась — она взята из плана построчно.

## 3. Реализация

Три скрипта. Два обязательны по плану (шаги 1–4, 8 — «скрипт»), третий вспомогательный.

### 3.1. `scripts/cleanup_text.py` — сама очистка

```python
# scripts/cleanup_text.py
SOURCE = ROOT / "docs" / "source" / "RAG-документация_BusiVerse.raw.md"
DOC    = ROOT / "RAG-документация_BusiVerse.md"
```

Читает **сырой** файл, перезаписывает очищенный. Прогон повторяем: результат не зависит от текущего состояния `DOC`.

Два примитива, на которых держится вся безопасность:

```python
# scripts/cleanup_text.py
def sub_once(text, old, new, label):   # ровно 1 вхождение, иначе fail()
def sub_all(text, old, new, label, expect=None):  # все вхождения + сверка количества
```

Если шаблон не найден или найден не там, где ожидалось, — скрипт падает и файл **не перезаписывается**. Молчаливой порчи не бывает.

Основные функции по шагам плана:

| Функция | Принимает | Отдаёт | Что делает |
|---|---|---|---|
| `mechanical_cleanup(text)` | весь текст | текст | шаги 1–2: снимает `<br>`/`<u>`, схлопывает пробелы |
| `fix_point_defects(text)` | текст | текст | шаг 3: `разделB0`, сломанный разделитель, OCR-склейки |
| `normalize_headings(text)` | текст | текст | шаг 4: 15 SOP без `##` → с `##` |
| `repair_tables(text)` | текст | текст | шаги 5–7: сборка разъехавшихся строк |
| `replace_picture_blocks(text)` | текст | текст | 11 расплющенных OCR-блоков → нормальные таблицы |
| `separate_adjacent_tables(text)` | текст | текст | 13 склеенных пар таблиц → пустая строка между ними |
| `fix_cyr_lat_glue(text)` | текст | текст | 387 склеек `месяазатем`, `наCAC` |
| `fix_spacing(text)` | текст | текст | пробел после слэша (145 мест), перед пунктуацией |
| `swap_matrix_columns(table)` | одна таблица | таблица | меняет колонки 5 и 6 в кадровой матрице |

Эвристики сборки таблиц — отдельный слой, потому что именно они решают, продолжает ли строка предыдущую:

```python
# scripts/cleanup_text.py
def ends_cont(cells) -> bool:      # обрывается ли строка на полуслове
def starts_cont(cells) -> bool:    # начинается ли со строчной буквы
def merge_table_rows(rows):        # склеивает продолжения
def split_into_tables(block):      # режет блок на отдельные таблицы
```

Здесь был баг, который я нашёл и исправил: правило «строка с пустой первой ячейкой продолжает предыдущую, если ячейка начинается со строчной буквы» срабатывало на `hh.ru` — домен начинается со строчной. Продолжение приклеивалось к **предыдущей** строке, текст уезжал не туда. Пострадало 5 строк. Домены исключены из проверки.

### 3.2. `scripts/validate_cleanup.py` — гейт

```python
# scripts/validate_cleanup.py
DOC = ROOT / "RAG-документация_BusiVerse.md"
NICHE_HEADINGS = [...]        # 10 ниш
SCRAMBLED_FRAGMENTS = [...]   # известные OCR-обрывки
```

Ничего не меняет, только читает и проверяет. Exit code 0 = вход для чанкера чистый. Проверяет 0 тегов разметки, 0 хвостовых пробелов, 0 `U+FFFD`, 0 SOP без `##`, 0 висячих предлогов, 0 пробелов после слэша, 0 расхождений колонок, 346 таблиц, 10 ниш по 8 подразделов.

### 3.3. `scripts/pdf_verify.py` — вспомогательный, не часть пайплайна

```python
# scripts/pdf_verify.py
def load_pdf() -> bytes:   # достаёт PDF из истории git (в дереве его нет)
def extract(page_num) -> list[tuple[float, float, str]]:  # текст + координаты x,y
```

Понадобился один раз: в двух кадровых матрицах порядок колонок отличался от остальных 13, и надо было решить, какой порядок верный. PDF в рабочем дереве нет — он был удалён при конвертации, поэтому скрипт достаёт его из истории git и выводит текст с координатами. По x видно, что «Переменная часть» (x=472.2) стоит левее «Ключевые KPI» (x=592.6) — канонический порядок верный.

**Этот скрипт план не требовал.** Он не участвует в очистке и не нужен для нарезки. Оставлен как инструмент для спорных мест: если позже возникнет вопрос «а как было в исходнике?», ответ достаётся одной командой, а не пересказом.

## 6. Почему так, а не иначе

1. **Скрипт, а не ручная правка.** План (раздел 6) прямо помечает шаги 1–4 и 8 как «скрипт». Ручная правка 11 262 тегов невоспроизводима: при переконвертации PDF всё придётся повторять заново. Скрипт прогоняется одной командой.

2. **Проверка внутри каждой правки, а не после.** `sub_once`/`sub_all` падают, если шаблон не найден или найден не там. Это ловит ошибку в момент правки, а не через 300 строк, когда непонятно, что сломалось.

3. **Валидатор отдельно от очистки.** Один скрипт меняет, другой проверяет. Если бы проверка была внутри очистки, она проверяла бы то, что сама только что сделала, — и не поймала бы ошибку в собственной логике. Именно так нашлись 6 символов `U+FFFD`, которые попали в документ **из самого скрипта**.

4. **`pdf_verify.py` не встроен в пайплайн.** Он нужен для разовых вопросов к исходнику, а не для каждой очистки. Держать его в основном прогоне — лишняя зависимость от git-истории.
