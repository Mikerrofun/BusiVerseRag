# Retrieval-конвейер (план 06)

Документ описывает, как запрос пользователя превращается в готовый контекст для модели. Конвейер живёт в папке `retrieval/` — это самодостаточный модуль (микросервис): наружу торчит одна функция `retrieve()` из `retrieval/index.ts`, всё остальное — внутреннее устройство.

```
запрос "как открыть кофейню и какие налоги платить"
   │
   ▼
┌──────────────────────────────────────────────────────────────────┐
│ 1. валидация → 2. ниша → 3. эмбеддинг → 4. vector ∥ FTS (40+40)  │
│ → 5. RRF (20) → 6. rerank (8) → 7-8. small-to-big + ссылки       │
│ → 9. сборка контекста (бюджет 12k токенов) → 10. RetrievalResult │
└──────────────────────────────────────────────────────────────────┘
```

Сквозной пример на весь документ: запрос **«как открыть кофейню и какие налоги платить»**, ниша определена как `coffee_shop`. Все числа ниже — реальные просчёты формул на этом примере.

## Структура папки

```
retrieval/
  index.ts                  ← оркестратор: собирает все шаги, публичный API
  run.ts                    ← CLI для ручной проверки (npm run retrieve)
  config/                   ← общие конфиги: модели+env, словарь ниш
  types/retrieval.types.ts  ← контракт и общие типы (ChunkRow, ScoredChunk, ...)
  lib/                      ← retry, подключение к Neon, коннектор z.ai
  steps/                    ← 7 шагов, каждый в своей подпапке:
    classification/  embedding/  search/  fusion/  rerank/  expand/  assemble/
```

Каждый шаг — подпапка с функцией, своим конфигом и своими типами. Шаги не импортируют друг друга: оркестратор знает порядок, шаги знают только входы/выходы.

---

## Шаг 1. Валидация входа

**Файл:** `index.ts` (внутри `retrieve`).

**Вход:** `RetrieveInput { query: string; niche?: NicheCode }`.
**Выход:** либо очищенный `query` + валидная `niche`, либо исключение с понятным текстом.

```ts
const query = typeof input.query === 'string' ? input.query.trim() : '';
if (!query) throw new Error('query: обязательна непустая строка');
if (input.niche !== undefined && !isNicheCode(input.niche)) {
  throw new Error(`niche: неизвестный код «${String(input.niche)}»`);
}
```

Пустая/не-строковая query → ошибка. Переданная ниша сверяется со словарём 10 кодов — неизвестный код → ошибка с самим кодом в тексте. Смысл: пользователь получает внятную ошибку сразу, а не «undefined где-то в глубине SQL» на шаге 4.

## Шаг 2. Определение ниши

**Файлы:** `steps/classification/` — `classify.ts` + `classification.config.ts` (порог, промпт) + `classification.types.ts`.

**Вход:** `query`, опциональная `uiNiche`.
**Выход:** `NicheDecision { niche: NicheCode | null; source: 'ui' | 'fulltext-probe' | 'llm' | 'none'; confidence: number | null }`.

Три уровня по возрастанию стоимости — каждый следующий вызывается, только если предыдущий не дал ответа:

**Уровень 1 — `ui`.** Ниша пришла из селектора интерфейса. Классификатор не вызывается вообще:

```ts
if (uiNiche) return { niche: uiNiche, source: 'ui', confidence: null };
```

**Уровень 2 — `fulltext-probe`.** Запрос в нижнем регистре сверяется со словарём ключевых слов ниш (`config/niches.config.ts`):

```ts
function fulltextProbe(query: string): NicheCode[] {
  const q = query.toLowerCase();
  return NICHE_CODES.filter((code) => NICHES[code].keywords.some((kw) => q.includes(kw)));
}
```

Для нашего примера: «кофейню» содержит ключевое слово «кофейн» ниши `coffee_shop` → `matched = ['coffee_shop']`. Ровно одно совпадение → ниша найдена, LLM не тратится. Если совпадений 0 или ≥ 2 («кофейня с маникюром») — проба неубедительна, идём на уровень 3.

**Уровень 3 — `llm`.** `glm-5.3-flash` получает системный промпт со списком ниш и возвращает строго JSON `{"niche": "...", "confidence": 0..1}`. Ответ парсится defensively:

```ts
function parseAnswer(text: string): ClassifierAnswer | null {
  const jsonMatch = text.match(/\{[\s\S]*\}/);        // вырезать первый {...} из ответа
  if (!jsonMatch) return null;                        // JSON нет вообще
  try {
    const raw = JSON.parse(jsonMatch[0]) as { niche?: unknown; confidence?: unknown };
    if (typeof raw.niche !== 'string' || typeof raw.confidence !== 'number') return null;
    return { niche: raw.niche, confidence: Math.min(1, Math.max(0, raw.confidence)) };
  } catch { return null; }                            // битый JSON
}
```

Три защиты: JSON вырезается регуляркой (LLM любит добавить «Вот ответ:» перед JSON), типы полей проверяются, confidence зажимается в `[0, 1]` (LLM может вернуть 1.2 или -0.1). Дальше код ниши сверяется со словарём (`isNicheCode`) и порогом:

```ts
if (parsed && isNicheCode(parsed.niche) && parsed.confidence >= CLASSIFICATION_CONFIG.threshold) {
  return { niche: parsed.niche, source: 'llm', confidence: parsed.confidence };
}
```

Порог `0.6`: ниже — модель сама не уверена, фильтровать корпус по такому ответу опаснее, чем не фильтровать.

Если LLM недоступен, вернул мусор или confidence ниже порога — `niche: null`, поиск идёт **по всему корпусу**. Это осознанное решение: лучше чанки из нескольких ниш, чем отфильтрованная правильная. Падение классификатора — единственная ошибка, которая **не** роняет конвейер (другой провайдер, z.ai, а не Jina).

## Шаг 3. Эмбеддинг запроса

**Файлы:** `steps/embedding/` — `embed-query.ts` + `embedding.config.ts` + `embedding.types.ts`.

**Вход:** строка запроса.
**Выход:** `number[]` — вектор из 1024 чисел, например `[0.021, -0.113, 0.004, ...]` (1024 элемента).

Тот же вызов Jina, что при ингесте (`scripts/embeddings/embed.ts`), с телом запроса:

```json
{
  "model": "jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "dimensions": 1024,
  "normalized": true,
  "input": ["как открыть кофейню и какие налоги платить"]
}
```

Три параметра критичны и обязаны совпадать с ингестом:

- **`model`** — разные модели проецируют текст в разные пространства. Вектор запроса из модели A против вектора чанка из модели B — сравнение бессмысленных чисел.
- **`dimensions`** — та же причина: 1024-мерный вектор не сравнивается с 768-мерным на уровне БД (pgvector просто отклонит запрос).
- **`task`** — у запроса `retrieval.query`, у документов при ингесте `retrieval.passage`. Jina обучалась так, что вектор запроса и вектор документа сближаются именно в паре «запрос-задача vs документ-задача». Перепутать задачи — потерять качество поиска без единой ошибки.

`normalized: true` — Jina возвращает вектор единичной длины (`|v| = 1`). Это важно для шага 4: косинусное сходство нормализованных векторов считается без деления на длины.

Ошибка API после 3 попыток retry роняет конвейер: без вектора vector-поиск невозможен, а FTS в одиночку — намеренное ухудшение, а не fallback.

## Шаг 4. Два поиска параллельно

**Файлы:** `steps/search/` — `vector-search.ts`, `fts.ts` + `search.config.ts` (`topK: 40`, `ftsPrefixMinLength: 3`).

**Вход:** вектор (для vector), строка запроса (для FTS), ниша, лимит.
**Выход:** два независимых списка `ScoredChunk[]` — `{ chunk: ChunkRow, score: number }`, по 40 кандидатов каждый.

Оба запроса идут через `Promise.all` — они независимы и каждый ходит в свою индексную структуру. Фильтр ниши одинаковый: `business_type = $ниша OR scope = 'global'` (сквозные чанки видны всегда); при `niche: null` фильтра нет.

### 4a. Vector-поиск

```ts
const vecLiteral = `[${vector.join(',')}]`;
const sql = `select ${CHUNK_COLUMNS}, 1 - (embedding <=> $1::vector) as score
  from chunks
  where embedding is not null ${filter}
  order by embedding <=> $1::vector
  limit $${limitIdx}`;
```

Вектор из JS нельзя передать как массив — pgvector принимает текстовый литерал `[0.021,-0.113,...]` с явным кастом `::vector`. Параметр `$1` (не склейка строк) — защита от SQL-инъекций.

**Как считается score.** Оператор `<=>` в pgvector — косинусное **расстояние**:

```
cosine_distance(A, B) = 1 - (A·B) / (|A| · |B|)
```

где `A·B` — скалярное произведение (сумма произведений координат), `|A|` — длина вектора (корень из суммы квадратов). Мы берём `1 - расстояние` и получаем **косинусное сходство**:

```
score = 1 - cosine_distance = (A·B) / (|A| · |B|)
```

Оба вектора нормализованы (`|A| = |B| = 1`), поэтому формула вырождается в обычное скалярное произведение. Мини-пример на 2-мерных векторах: запрос `A = [1, 0]`, чанк `B = [0.7, 0.7]` → `A·B = 0.7`, `|A||B| = 1 · 0.98 ≈ 0.98` → `score ≈ 0.71`. В реальном 1024-мерном пространстве скоры осмысленных пар лежат примерно в `0.5–0.9`; наш хит `coffee_shop-1.3-b02-p2` получил `0.87`.

**Индекс HNSW.** `order by embedding <=> $1` по 443 строкам Postgres мог бы посчитать честно (полный перебор), но по таблице в сотни тысяч строк это уже секунды. HNSW — графовый индекс приблизительного поиска: чанки связаны в многослойный граф «ближайшие соседи», поиск идёт сверху вниз по слоям, с каждым слоем уточняясь. Даёт ответ за миллисекунды, платя малой долей ложных пропусков (recall ~95–99%). Индекс построен при ингесте (`create index ... using hnsw (embedding vector_cosine_ops)`).

### 4b. FTS-поиск

Строка запроса сначала превращается в tsquery на стороне приложения:

```ts
function buildTsQuery(query: string): string | null {
  const terms = query.toLowerCase().match(/[a-zа-яё0-9]+/g) ?? [];
  const parts = terms.map((t) =>
    /^[а-яё]+$/.test(t) && t.length >= SEARCH_CONFIG.ftsPrefixMinLength ? `${t}:*` : t,
  );
  return parts.length > 0 ? parts.join(' & ') : null;
}
```

Пошагово на нашем запросе:

1. `toLowerCase()` → `«как открыть кофейню и какие налоги платить»`.
2. Регулярка `[a-zа-яё0-9]+` режет на термы, выбрасывая всё небуквенно-цифровое: `[как, открыть, кофейню, и, какие, налоги, платить]`. Знаки препинания выбрасываются обязательно — сырой текст сломал бы `to_tsquery` синтаксической ошибкой.
3. Кириллические термы длиной ≥ 3 получают суффикс `:*` (префикс-матчинг): `кофейню:*`, `налоги:*`. Термы `и` (длина 1) остаются без префикса — короткие слова префиксовать бессмысленно и дорого. Числа и латиница не префиксуются никогда («152-фз», «smm») — точные термины, префикс им только навредит.
4. Склейка через ` & ` (логическое И): `как:* & открыть:* & кофейню:* & и & какие:* & налоги:* & платить`.

Как работает `:*` внутри Postgres: токен сначала прогоняется через русский словарь (стемминг — «кофейню» → основа «кофейн»), затем `:*` означает «любая лексема, начинающаяся с этой основы». Поэтому префикс ловит все словоформы: «кофейня», «кофейням», «кофейнями» — пользователь почти никогда не пишет слово в той форме, что в тексте.

```sql
select ${CHUNK_COLUMNS}, ts_rank(tsv, q) as score
from chunks, to_tsquery('russian', $1) q
where tsv @@ q ${filter}
order by score desc
limit $${limitIdx}
```

- `tsv` — tsvector-колонка: при ингесте каждый чанк был прогнан через `to_tsvector('russian', text)` и сохранён как набор лексем (`'кофейн':3 'налог':7 ...` с позициями). По ней построен GIN-индекс.
- `@@` — оператор соответствия «tsvector содержит все лексемы tsquery».
- `ts_rank(tsv, q)` — ранг соответствия. Внутри: сумма весов совпавших лексем, где вес зависит от частоты термина в документе (чем чаще — тем выше вклад, но с насыщением) и от позиционного веса (A/B/C/D — заголовки весят больше тела; наши чанки попадают в дефолтные веса). Дефолтная нормализация — 0, то есть **без** поправки на длину документа: длинный чанк не штрафуется.

**Шкала ts_rank:** обычно `0.01–0.1`. Это важно для шага 5: скоры FTS и vector несравнимы между собой. Пример наших хитов: `coffee_shop-1.3-b02-p1` → `0.089`, `coffee_shop-10.4` → `0.062`.

Пустой tsquery (в запросе нет букв/цифр, например «???») → `buildTsQuery` вернёт `null`, FTS пропускается и возвращает `[]` — RRF в шаге 5 спокойно работает с одним списком.

### Зачем два поиска

Эмбеддинг понимает смысл, но размывает точные термины («152-фз» для него — просто «какой-то закон»); FTS точен по словам, но слеп к синонимам («деньги на старт» не найдёт «источники финансирования»). Пересечение двух независимых сигналов надёжнее любого из них по отдельности — это и эксплуатирует следующий шаг.

## Шаг 5. RRF — слияние двух списков

**Файлы:** `steps/fusion/` — `rrf.ts` + `fusion.config.ts` (`k: 60`, `topK: 20`).

**Вход:** `[vectorHits, ftsHits]` — два списка по 40.
**Выход:** один список `ScoredChunk[]` топ-20.

**Проблема, которую решает:** скоры двух поисков несравнимы. Косинусное сходство живёт около 0.6–0.9, `ts_rank` — около 0.01–0.1. Нельзя сложить, усреднить или нормализовать — распределения разные, и один список всегда задавил бы другой.

**Решение — Reciprocal Rank Fusion:** работают только **позиции** в списках, сырые скоры выбрасываются целиком. Каждый чанк получает вклад от каждого списка, где он встретился:

```
score = Σ 1 / (k + rank)     rank = позиция в списке, начиная с 1; k = 60
```

Код в точности повторяет формулу:

```ts
list.forEach((item, i) => {
  const contribution = 1 / (FUSION_CONFIG.k + i + 1);   // i — индекс с 0, rank = i + 1
  const existing = fused.get(item.chunk.chunk_id);
  if (existing) existing.score += contribution;         // чанк в обоих списках — вклады суммируются
  else fused.set(item.chunk.chunk_id, { chunk: item.chunk, score: contribution });
});
```

**Просчёт на нашем примере** (взяты топ-3 каждого списка):

| Чанк | В vector | Вклад vector | В FTS | Вклад FTS | Итоговый RRF-скор |
|---|---|---|---|---|---|
| `coffee_shop-1.3-b02-p2` | ранг 1 | 1/61 = 0.01639 | ранг 2 | 1/62 = 0.01613 | **0.03252** |
| `coffee_shop-10.4` | ранг 2 | 1/62 = 0.01613 | ранг 3 | 1/63 = 0.01587 | **0.03200** |
| `coffee_shop-1.3-b02-p1` | — | 0 | ранг 1 | 1/61 = 0.01639 | **0.01639** |
| `coffee_shop-1.3-b03` | ранг 3 | 1/63 = 0.01587 | — | 0 | **0.01587** |

Ключевое наблюдение из таблицы: `b02-p1` — **лидер FTS** (ранг 1), но в итоге он на третьем месте, проигрывая чанкам, которые попали в **оба** списка. Совпадение в двух независимых поисках бьёт одиночное лидерство — в этом весь смысл RRF. Дубликат при этом остаётся в списке один раз (дедуп по `chunk_id`, вклады суммируются, а не удваивают запись).

**Почему k = 60.** Константа сглаживает разницу рангов внутри одного списка. Без неё (k=0) вклад ранга 1 — `1.0`, ранга 2 — `0.5`: первая позиция одного списка перевешивала бы попадание в оба списка сразу. С k=60 вклады соседних позиций почти равны (1/61 = 0.01639 против 1/62 = 0.01613, разница 1.6%), поэтому доминирует сам факт попадания в оба списка, а не точная позиция. Значение 60 — эмпирический стандарт из оригинальной работы (Cormack et al., 2009).

После слияния список сортируется по убыванию и режется до `topK: 20` — это **окончательная** отрезка: rerank на следующем шаге видит только эти 20.

## Шаг 6. Rerank

**Файлы:** `steps/rerank/` — `rerank.ts` + `rerank.config.ts` (`model: 'jina-reranker-v3.5'`, `topK: 8`) + `rerank.types.ts`.

**Вход:** `query` + 20 кандидатов из RRF.
**Выход:** те же чанки, топ-8, пересортированные по `relevance_score` (0..1 от Jina).

### Почему rerank нужен, если уже есть эмбеддинги

Эмбеддинг-поиск — это **bi-encoder**: запрос и документ превращаются в вектора **независимо друг от друга**, потом сравнивается геометрия двух точек. Модель при этом никогда не видит текст запроса и текст чанка вместе — она видит только два набора чисел. Это быстро (один проход по индексу, миллисекунды) и позволяет проиндексировать весь корпус заранее, но грубо: тонкие взаимодействия «запрос ↔ документ» теряются.

Reranker — **cross-encoder**: он получает пару «запрос + документ» **целиком** и прогоняет через трансформер, где внимание (attention) работает между токенами запроса и токенами документа одновременно. Модель видит, что слово «налоги» из запроса стоит в предложении про УСН, и оценивает релевантность этой конкретной пары. Результат — один скаляр `relevance_score`. Это качественно точнее, но дорого: один полный проход трансформера на каждую пару. Поэтому классическая воронка:

```
443 чанка корпуса
  → vector + FTS: дешёвый широкий отбор, 40 + 40 кандидатов   (индексы, миллисекунды)
  → RRF: 20 кандидатов                                        (чистая арифметика)
  → rerank: точный дожим до 8                                 (20 проходов cross-encoder'а)
```

Rerank применяется к 20, а не к 443, потому что 443 прохода cross-encoder'а — секунды и деньги за каждый запрос. Дешёвые этапы сужают поле, дорогой работает по нему точно.

### Код построчно

```ts
function apiKey(): string {
  const override = process.env[MODELS_CONFIG.env.jinaRerankKey];   // RERANKER_API_JINA
  if (override) return override;
  const shared = process.env[MODELS_CONFIG.env.jinaEmbedKey];      // EMBEDING_API_JINA
  if (!shared) throw new Error(`Ни ${...jinaRerankKey}, ни ${...jinaEmbedKey} не заданы`);
  return shared;
}
```

Ключ: отдельный `RERANKER_API_JINA`, если задан; иначе общий с эмбеддингами `EMBEDING_API_JINA` (у Jina один ключ на оба API). Если нет ни одного — ошибка с именами обеих переменных.

```ts
return withRetry('jina rerank', async () => {
  const res = await fetch(MODELS_CONFIG.jinaRerankUrl, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${key}` },
    body: JSON.stringify({
      model: RERANK_CONFIG.model,
      query,
      documents: items.map((item) => item.chunk.text),   // только тексты, без метаданных
    }),
  });
```

На вход Jina уходят `query` и массив **текстов** 20 кандидатов. Метаданные (заголовки, ниша) не отправляются — reranker оценивает только пару «запрос ↔ текст».

```json
// запрос
{ "model": "jina-reranker-v3.5", "query": "как открыть кофейню и какие налоги платить",
  "documents": ["<текст b02-p2>", "<текст b02-p1>", "<текст 10.4>", "... ещё 17"] }

// ответ
{ "results": [
    { "index": 0, "relevance_score": 0.93 },
    { "index": 2, "relevance_score": 0.88 },
    { "index": 1, "relevance_score": 0.91 },
    ...
  ] }
```

```ts
  if (!res.ok) {
    const body = await res.text().catch(() => '');
    throw new Error(`Jina Rerank API ${res.status}: ${body.slice(0, 300)}`);
  }
  const json = (await res.json()) as JinaRerankResponse;
  return json.results
    .map((r) => ({ chunk: items[r.index]?.chunk, score: r.relevance_score }))
    .filter((r): r is ScoredChunk => !!r.chunk)
    .sort((a, b) => b.score - a.score)
    .slice(0, RERANK_CONFIG.topK);
});
```

Построчно:

- **Ошибка HTTP → исключение.** Не `return []`, не лог и продолжение — именно throw. После 3 попыток `withRetry` ошибка уходит наружу и роняет весь `retrieve()`. Логика: rerank и эмбеддинг — один провайдер (Jina); если недоступен rerank, эмбеддинг тоже бы упал, а отдавать неотранжированный контекст (порядок от RRF) — намеренно худший результат под видом нормального.
- **`items[r.index]?.chunk`** — Jina возвращает `results` **не в порядке отправки** (в примере выше `index: 0, 2, 1`). `index` — это позиция документа в отправленном массиве, по ней чанк восстанавливается из `items`. `?.` + `filter` отсекают гипотетический мусорный index (вне диапазона).
- **`sort` по убыванию** — `relevance_score` живёт в `0..1` (Jina нормирует через сигмоиду). Это **третья** несовместимая шкала в конвейере: с косинусом и ts_rank сравнивать нельзя, как и их друг с другом. Важен только порядок внутри этого шага.
- **`slice(0, 8)`** — финальная отрезка внутри самого rerank: дальше в small-to-big идут ровно 8 хитов.

**Просчёт на нашем примере** (из 20 кандидатов RRF):

| Чанк | RRF-скор (было) | relevance_score | Итог |
|---|---|---|---|
| `coffee_shop-1.3-b02-p2` | 0.03252 (1-й) | 0.93 | 1-й |
| `coffee_shop-1.3-b02-p1` | 0.01639 (3-й) | 0.91 | 2-й |
| `coffee_shop-10.4` | 0.03200 (2-й) | 0.88 | 3-й |
| `coffee_shop-1.3` | 0.01561 (5-й) | 0.55 | 5-й |
| `coffee_shop-1.3-b03` | 0.01587 (4-й) | 0.41 | 7-й |
| остальные 14 | ... | < 0.35 | отрезаны |

Rerank поменял порядок: `b02-p1` (лидер FTS) поднялся с 3-го места на 2-е, потому что cross-encoder увидел в его тексте и «открытие кофейни», и «налоги» одновременно. `b03` опустился: текст про выбор помещения, налоги там ни при чём. Именно эта способность «прочитать пару» и есть ценность шага.

## Шаги 7–8. Small-to-big и ссылки (expand)

**Файлы:** `steps/expand/` — `expand.ts` + `expand.types.ts` (`ContextUnit`, `ExpandedGroup`).

**Вход:** 8 хитов после rerank.
**Выход:** `ExpandedGroup[]` — группы «блок целиком + родитель + ссылки».

Это самое хитрое место конвейера. Разберём по слоям.

### Зачем это всё

Хит — это маленький кусок текста (дроблёный блок, ~200 токенов), который **ранжируется** хорошо, но **читается** плохо: обрывок без начала мысли. Small-to-big = «ищем маленьким, отдаём большим». У каждого хита достраивается окружение:

- **блок целиком** — все куски дроблёного блока склеиваются в один сплошной текст;
- **родительская секция** — чанк-секция, к которой принадлежит блок (компактное резюме ~300–500 токенов);
- **связанные разделы** — явные ссылки из таблицы `chunk_links` («см. также раздел 10.4»).

### Как в БД устроены куски (важно для понимания запросов)

Дерево чанков: `секция → блоки → куски`. В DDL нет колонки `part_index`, зато есть два поля, которых хватает:

- у **всех** блоков секции (и целых, и кусков) `parent_id` = id чанка-секции;
- у всех кусков **одного** блока `chunk_index` совпадает — это номер блока внутри секции.

То есть пара `(parent_id, chunk_index)` однозначно идентифицирует блок. Пример:

```
coffee_shop-1.3            ← чанк-секция (parent_id = null, chunk_index = 0)
├─ coffee_shop-1.3-b01     ← блок целиком,        parent_id = coffee_shop-1.3, chunk_index = 0
├─ coffee_shop-1.3-b02-p1  ← кусок 1 блока 2,     parent_id = coffee_shop-1.3, chunk_index = 1
├─ coffee_shop-1.3-b02-p2  ← кусок 2 того же блока, parent_id = coffee_shop-1.3, chunk_index = 1
└─ coffee_shop-1.3-b03     ← блок целиком,        parent_id = coffee_shop-1.3, chunk_index = 2
```

### Ход запросов — их всего четыре на все 8 хитов

Никаких запросов на каждый хит — всё множество достаётся пакетно:

```ts
// 1. Все блоки всех задействованных секций — ОДИН запрос
select ${CHUNK_COLUMNS} from chunks where parent_id = any($1::text[])
// parentIds = уникальные parent_id всех хитов

// 2. Родительские секции — ОДИН запрос (те же parentIds)
select ${CHUNK_COLUMNS} from chunks where chunk_id = any($1::text[])

// 3. Ссылки всех хитов — ОДИН запрос
select from_chunk_id, to_section from chunk_links where from_chunk_id = any($1::text[])

// 4. Секции-цели ссылок — ОДИН запрос
select ${CHUNK_COLUMNS} from chunks
 where section_code = any($1::text[]) and parent_id is null
```

Первый запрос возвращает **все блоки секций** (например, 8 секций × ~6 блоков = ~50 строк), а не только нужные — фильтрация до нужных блоков происходит в JS на следующем шаге. Это осознанный размен: один запрос на 50 строк дешевле и проще, чем 8 точечных. Запросы 1–2 идут через `Promise.all` (независимы), запрос 4 — после 3 (ему нужны её результаты). Каждый обёрнут в `withRetry`.

Результаты раскладываются в словари для O(1)-доступа:

```ts
const parentsById = new Map(parentRows.map((c) => [c.chunk_id, c]));
const blocksByParent = new Map<string, ChunkRow[]>();   // parent_id → все его блоки
const sectionsByCode = new Map<string, ChunkRow[]>();   // section_code → все секции с этим кодом
```

### Группировка и склейка в JS

Основной цикл идёт по хитам; для каждого строится ключ блока:

```ts
const key = `${chunk.parent_id ?? ''}|${chunk.chunk_index}`;
```

Для `b02-p2`: `"coffee_shop-1.3|1"`. Для чанка-секции (`parent_id = null`): `"|0"` — секция группируется сама с собой.

**Блок целиком.** Из словаря `blocksByParent` берутся все блоки родителя и фильтруются по `chunk_index` — остаются куски **только этого** блока:

```ts
const siblings = (blocksByParent.get(chunk.parent_id ?? '') ?? []).filter(
  (c) => c.chunk_index === chunk.chunk_index,
);
siblings.sort((a, b) => (a.line_start ?? 0) - (b.line_start ?? 0));
const blockUnit = {
  kind: 'block' as const,
  text: siblings.map((c) => c.text).join('\n\n'),
  heading: headingOf(chunk),          // heading_path, склеенный через " > "
  score: hit.score,
  parts: siblings.length > 0 ? siblings : [chunk],
};
```

Три случая:

- **Кусков несколько** (`b02-p1`, `b02-p2`): сортировка по `line_start` (строка начала куска в исходном markdown) даёт правильный порядок кусков — надёжнее любого разбора суффиксов `-pN`; склейка конкатенацией текстов через пустую строку. `parts` — список склеенных кусков (нужен для ролей на шаге 9).
- **Кусок один** (`b01`, `b03` — блок не дробился): это уже блок целиком, склеивать нечего.
- **`siblings` пуст** (у хита `parent_id = null`, а сам он секция): fallback `parts: [chunk]` — блок-юнит это сам хит.

**Родитель.** Если `parent_id` есть, из `parentsById` достаётся чанк-секция:

```ts
const parent = chunk.parent_id ? (parentsById.get(chunk.parent_id) ?? null) : null;
```

У секционного хита (`10.4`) родителя нет — `parentUnit = null`.

### Дедуп: почему групп, а не хитов

Несколько хитов могут указать на один блок. В нашем примере хиты 1 и 2 — `b02-p2` и `b02-p1`, куски одного блока:

```ts
let group = groups.get(key);
if (!group) { /* создать группу: block, parent, links: [], hits: [] */ }
```

Первый хит (`b02-p2`, скор 0.93) создаёт группу `"coffee_shop-1.3|1"`. Второй хит (`b02-p1`, скор 0.91) находит существующую группу по тому же ключу и просто дописывается в `group.hits` — блок и родитель второй раз не создаются. Блок склеится из обоих кусков независимо от того, какой хит пришёл первым: `siblings` собираются из полного списка блоков родителя, а не из хитов.

**Скор группы — максимум по хитам:**

```ts
if (hit.score > group.score) {
  group.score = hit.score;
  group.block.score = hit.score;
  if (group.parent) group.parent.score = hit.score;
}
```

Группа `b02` получает `0.93` (лучший из 0.93 и 0.91). Скор проталкивается в block- и parent-юниты — на шаге 9 группы сортируются именно по нему.

**Ссылки.** Собираются с **каждого** хита группы (у разных кусков могут быть разные ссылки), с тремя фильтрами:

```ts
for (const link of links.filter((l) => l.from_chunk_id === chunk.chunk_id)) {
  const section = resolveSection(link.to_section, chunk.business_type);
  if (!section) continue;                                                    // цель не найдена в БД
  if (group.links.some((u) => u.parts[0]?.chunk_id === section.chunk_id)) continue;  // дедуп внутри группы
  if (group.parent && section.chunk_id === group.parent.parts[0]?.chunk_id) continue; // ссылка на своего родителя
  group.links.push({ kind: 'link', text: section.text, heading: headingOf(section), score: hit.score, parts: [section] });
}
```

В примере: `b02-p1` ссылается на `10.4`, `b02-p2` тоже ссылается на `10.4` → дедуп по `chunk_id`, ссылка одна. Ссылка на `7.2` добавляется второй.

**Приоритет цели ссылки.** `to_section` в `chunk_links` — просто код («10.4»). Секция с таким кодом может существовать в нескольких нишах и в global. Выбор:

```ts
const resolveSection = (code: string, hitType: string): ChunkRow | null => {
  const candidates = sectionsByCode.get(code) ?? [];
  return (
    candidates.find((c) => c.business_type === hitType) ??   // 1. та же ниша, что у хита
    candidates.find((c) => c.scope === 'global') ??          // 2. сквозная
    candidates[0] ??                                          // 3. первая попавшаяся
    null
  );
};
```

Логика: читателю кофейни полезна налоговая секция для кофейни; если её нет — общая; если и её нет — любая (лучше что-то, чем пустая ссылка).

### Итоговая структура

```ts
ExpandedGroup {
  key: string              // "coffee_shop-1.3|1" — ключ блока
  score: number            // max rerank-скор хитов группы (0.93)
  block: ContextUnit       // блок целиком: склеенный text + parts
  parent: ContextUnit|null // чанк-секция (для секционных хитов — null)
  links: ContextUnit[]     // связанные секции после дедупа
  hits: ScoredChunk[]      // какие хиты сюда попали
}
```

Результат на нашем примере — 3 группы из 8 хитов:

```
g1 "coffee_shop-1.3|1"  score 0.93  hits: [b02-p2, b02-p1]  links: [10.4, 7.2]
g2 "|0" (секция 10.4)   score 0.88  hits: [10.4]            parent: null
g3 "coffee_shop-1.3|2"  score 0.41  hits: [b03]             links: [...]
```

## Шаг 9. Сборка контекста (assemble)

**Файлы:** `steps/assemble/` — `assemble.ts` + `assemble.config.ts` (`tokenBudget: 12000`, `encoderModel: 'gpt-4o'`) + `assemble.types.ts`.

**Вход:** `ExpandedGroup[]`.
**Выход:** `AssembledContext { context: string; chunks: ContextChunk[]; truncated: boolean; usedCount: number }`.

### Подсчёт токенов

```ts
const encoder = encodingForModel(ASSEMBLE_CONFIG.encoderModel);   // 'gpt-4o'
const countTokens = (text: string): number => encoder.encode(text).length;
```

`js-tiktoken` с энкодером gpt-4o — это BPE-токенизация, совместимая с большинством современных моделей (GPT/Claude/Gemini в этой зоне отличаются на проценты). Бюджет 12 000 считается в **токенах**, не в символах: у русского ~2–3 символа на токен, поэтому 12k токенов ≈ 25–35k символов. Считать по символам нельзя — промпт ограничен именно токенами.

### Правило 1. Порядок блоков — по релевантности

```ts
const ordered = [...groups].sort((a, b) => b.score - a.score);
```

Группы выстраиваются по убыванию лучшего rerank-скора: `g1 (0.93) → g2 (0.88) → g3 (0.41)`. Самое релевантное — в начало контекста: модели внимательнее к началу промпта, и при обрезке сверху (если потребитель контекста урежет его сам) отрежется хвост.

### Правило 2. Формат единицы — заголовок-источник + маркер

```ts
const MARKERS = { block: 'Источник', parent: 'Контекст секции', link: 'Связанный раздел' };
function renderUnit(kind, heading, text) {
  return `## ${MARKERS[kind]}: ${heading}\n\n${text}`;
}
```

Что получается для блока `g1`:

```markdown
## Источник: Открытие > Регистрация > 1.3 Выбор системы налогообложения

<текст b02-p1>

<текст b02-p2>
```

Заголовок — `heading_path` через ` > `: модель видит, из какого места документа текст, даже если сам текст об этом не говорит. Маркеры отделяют основной материал от фонового: «Источник» — то, за что голосовал rerank; «Контекст секции» и «Связанный раздел» — добор.

### Правило 3. Атомарность блока

```ts
const blockText = renderUnit('block', group.block.heading, group.block.text);
const blockTokens = countTokens(blockText);
if (used + blockTokens > ASSEMBLE_CONFIG.tokenBudget) {
  truncated = true;
  continue;                       // вся группа пропускается целиком
}
used += blockTokens;
sections.push(blockText);
```

Блок не режется посреди: если блок целиком не влезает в остаток бюджета — пропускается **вся его группа** (родитель и ссылки вместе с ним), конвейер идёт к следующей, возможно более короткой, группе. Лучше потерять один блок, чем отдать модели обрывок без конца мысли. Обратите внимание: `continue`, а не `break` — после слишком большой группы более короткие всё ещё могут влезть.

### Правило 4. Добор не гарантирован

После блока в контекст добавляются хиты группы (для ролей) и добор — родитель, затем ссылки:

```ts
const extras = [
  ...(group.parent ? [{ kind: 'parent' as const, unit: group.parent }] : []),
  ...group.links.map((unit) => ({ kind: 'link' as const, unit })),
];
for (const { kind, unit } of extras) {
  const text = renderUnit(kind, unit.heading, unit.text);
  const tokens = countTokens(text);
  if (used + tokens > ASSEMBLE_CONFIG.tokenBudget) {
    truncated = true;
    continue;                     // этот добор пропускается, следующие пробуются
  }
  used += tokens;
  sections.push(text);
  for (const part of unit.parts) pushChunk(part.chunk_id, kind, unit.score, part);
}
```

Если блок влез, а родитель — нет: блок остаётся, родитель пропускается, `truncated = true`, ссылки всё равно пробуются (каждая independently). Бюджет важнее полноты добора.

### Просчёт бюджета на нашем примере

Бюджет 12 000, счётчик `used` стартует с 0:

| Шаг | Единица | Токены | used после | Решение |
|---|---|---|---|---|
| g1 блок | `b02` целиком | 640 | 640 | влез |
| g1 родитель | секция `1.3` | 210 | 850 | влез |
| g1 ссылка | секция `10.4` | 450 | 1300 | влез |
| g1 ссылка | секция `7.2` | 380 | 1680 | влез |
| g2 блок | секция `10.4` | 450 | 2130 | влез |
| g3 блок | `b03` | 520 | 2650 | влез |
| g4 блок (гипотетич.) | большой блок | 9500 | 12150 > 12000 | **пропущен**, truncated = true |
| g5 блок (гипотетич.) | короткий блок | 700 | 3350 | влез — `continue`, не `break` |

Итог: `context = sections.join('\n\n')`, `truncated = true`, `usedCount = chunks.length` — число **уникальных чанков** в списке ролей (не токены и не группы).

### Правило 5. Список chunks и роли

Каждый использованный чанк регистрируется через `pushChunk` с ролью:

```ts
const rolePriority: Record<ChunkRole, number> = { hit: 0, part: 1, parent: 2, link: 3 };
const pushChunk = (chunkId, role, score, meta) => {
  const existing = chunks.find((c) => c.chunk_id === chunkId);
  if (existing) {
    if (rolePriority[role] < rolePriority[existing.role]) existing.role = role;  // апгрейд
    return;                                                                       // дедуп
  }
  chunks.push({ chunk_id: chunkId, ..., score, role });
};
```

Порядок регистрации внутри группы: сначала все хиты (`hit`), потом куски блока (`part`), потом добор (`parent`, `link`). Число = приоритет: меньше — главнее; роль перезаписывается только на более главную.

## Роли чанков и их приоритет

Каждый чанк в итоговом `chunks` несёт роль — откуда он взялся в контексте:

| Роль | Откуда | Смысл |
|---|---|---|
| `hit` | нашёл поиск, прошёл rerank | главный материал, за него голосовал rerank |
| `part` | соседний кусок того же блока | добор до целого блока, сам хитом не был |
| `parent` | родительская секция блока | фон сверху: заголовок и резюме секции |
| `link` | запись в `chunk_links` | смежный раздел, на который автор ссылался явно |

**Почему приоритет именно `hit > part > parent > link`:** роль отражает **причину попадания** чанка в контекст, а причины не равнозначны. `hit` — первоисточник: rerank прочитал пару «запрос ↔ текст» и сказал «это релевантно». `part` — чанк попал в контекст только потому, что его сосед оказался хитом; сам он релевантность не доказывал. `parent` и `link` — фоновые надстройки: их включили по структурной связи, а не по релевантности (родитель чуть важнее — он непосредственный контекст хита, ссылка — опосредованный).

**Зачем приоритет технически:** один чанк может попасть в контекст несколькими путями сразу. Пример на нашем запросе — секция `coffee_shop-1.3`:

1. она — родитель блока `b02` (группа g1) → путь `parent`;
2. она сама оказалась хитом (rerank дал ей 0.55, группа `|0`) → путь `hit`.

В списке `chunks` она должна остаться **один раз**. Порядок обработки решает это автоматически: внутри g1 хиты регистрируются первыми — `1.3` получает `hit`; попытка зарегистрировать её же как `parent` отклоняется (2 > 0). Если бы она не была хитом, осталась бы `parent`. Апгрейд работает и между группами: чанк, попавший как `link` в группу A (обработалась раньше), но как `hit` в группу B, получит `hit` — роль upgraded, скор при этом остаётся от первой регистрации.

Скор в `chunks` — всегда шкала rerank: у хитов их собственный `relevance_score`, у частей и добора — скор группы (лучший хит группы). Все три предыдущие шкалы (косинус, ts_rank, RRF) в финальный результат не попадают.

## Шаг 10. Контракт результата

**Файл:** `types/retrieval.types.ts`. Наружу отдаётся ровно это:

```ts
interface RetrievalResult {
  context: string;          // готовый текст для промпта модели
  chunks: ContextChunk[];   // какие чанки использованы: id, заголовки, тип, score, роль
  meta: {
    niche: NicheCode | null;
    niche_source: 'ui' | 'fulltext-probe' | 'llm' | 'none';
    confidence: number | null;
    counters: { vector: number; fts: number; rrf: number; rerank: number; context: number };
    truncated: boolean;     // контекст обрезан по бюджету
  };
}
```

`counters` — след воронки на каждом этапе; на нашем примере: `vector: 40, fts: 38, rrf: 20, rerank: 8, context: 11`. По ним видно, где поиск теряет кандидатов. `meta` — для отладки и будущего UI («поиск шёл в нише X, определён автоматически»).

## Отказоустойчивость

- Все сетевые вызовы (Jina embed, Jina rerank, z.ai) и все SQL-запросы обёрнуты в `withRetry` (`lib/retry.ts`): 3 попытки, паузы 1с → 2с → 4с.
- Падение rerank, эмбеддинга или БД **роняет весь `retrieve()`** — частичный результат не отдаётся.
- Падение классификатора — не роняет: поиск продолжается без фильтра ниши.
- Отсутствующая env-переменная даёт ошибку с именем переменной и пояснением, зачем она нужна.
