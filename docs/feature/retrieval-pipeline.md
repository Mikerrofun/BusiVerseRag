# Retrieval-конвейер (план 06)

Документ описывает, как запрос пользователя превращается в готовый контекст для модели. Конвейер живёт в папке `retrieval/` — это самодостаточный модуль (микросервис): наружу торчит одна функция `retrieve()` из `retrieval/index.ts`, всё остальное — внутреннее устройство.

```
запрос "как открыть кофейню"
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. валидация → 2. ниша → 3. эмбеддинг → 4. vector ∥ FTS     │
│ → 5. RRF → 6. rerank → 7-8. small-to-big + ссылки           │
│ → 9. сборка контекста → 10. RetrievalResult                 │
└─────────────────────────────────────────────────────────────┘
```

## Структура папки

```
retrieval/
  index.ts                  ← оркестратор: собирает все шаги, публичный API
  run.ts                    ← CLI для ручной проверки (npm run retrieve)
  config/                   ← общие конфиги: модели+env, словарь ниш
  types/retrieval.types.ts  ← контракт и общие типы (ChunkRow, ScoredChunk, ...)
  lib/                      ← retry, подключение к Neon, коннектор z.ai
  steps/                    ← 7 шагов, каждый в своей подпапке:
    classification/  embedding/  search/  fusion/  rerank/  expand/  assemble/
```

Каждый шаг — подпапка с функцией, своим конфигом и своими типами. Шаги не импортируют друг друга: оркестратор знает порядок, шаги знают только входы/выходы.

---

## Шаг 1. Валидация входа

**Файл:** `index.ts` (внутри `retrieve`).

**Вход:** `RetrieveInput { query: string; niche?: NicheCode }`.
**Выход:** либо очищенный `query` + валидная `niche`, либо исключение с понятным текстом.

Пустая/не-строковая query → ошибка «обязательна непустая строка». Переданная ниша сверяется со словарём 10 кодов — неизвестный код → ошибка с перечислением доступных. Смысл: пользователь получает внятную ошибку сразу, а не «undefined где-то в глубине SQL» на шаге 4.

## Шаг 2. Определение ниши

**Файлы:** `steps/classification/` — `classify.ts` + `classification.config.ts` (порог, промпт) + `classification.types.ts` (`NicheDecision`, `ClassifierAnswer`).

**Вход:** `query`, опциональная `uiNiche`.
**Выход:** `NicheDecision { niche: NicheCode | null; source: 'ui' | 'fulltext-probe' | 'llm' | 'none'; confidence: number | null }`.

Три уровня по возрастанию стоимости — каждый следующий вызывается, только если предыдущий не дал ответа:

1. **`ui`** — ниша пришла из селектора интерфейса. Классификатор не вызывается вообще, `confidence: null`.
2. **`fulltext-probe`** — запрос в нижнем регистре сверяется со словарём ключевых слов ниш (`config/niches.config.ts`: «кофейн» → coffee_shop, «пвз» → pickup_point, ...). Ровно одно совпадение → ниша найдена, LLM не тратится.
3. **`llm`** — `glm-5.3-flash` получает системный промпт со списком ниш и возвращает строго JSON `{"niche": "...", "confidence": 0..1}`. Ответ парсится (мусор → null), код сверяется со словарём, и если `confidence >= 0.6` — ниша принята.

Если LLM недоступен, вернул мусор или confidence ниже порога — `niche: null`, поиск идёт **по всему корпусу**. Это осознанное решение: лучше чанки из нескольких ниш, чем отфильтрованная правильная. Падение классификатора — единственная ошибка, которая **не** роняет конвейер (другой провайдер, z.ai, а не Jina).

## Шаг 3. Эмбеддинг запроса

**Файлы:** `steps/embedding/` — `embed-query.ts` + `embedding.config.ts` + `embedding.types.ts`.

**Вход:** строка запроса.
**Выход:** `number[]` — вектор из 1024 чисел.

Тот же вызов Jina, что при ингесте (`scripts/embeddings/embed.ts`), с двумя отличиями: `task: 'retrieval.query'` (у запроса и документов разные задачи — Jina так обучалась) и один вход вместо батча. Модель, размерность и `normalized: true` обязаны совпадать с ингестом — иначе вектора запроса и чанков живут в разных пространствах и поиск вернёт мусор **без единой ошибки** (просто нерелевантные результаты). Это самое коварное место фичи.

## Шаг 4. Два поиска параллельно

**Файлы:** `steps/search/` — `vector-search.ts`, `fts.ts` + `search.config.ts` (`topK: 40`, `ftsPrefixMinLength: 3`).

**Вход:** вектор (для vector), строка запроса (для FTS), ниша, лимит.
**Выход:** два независимых списка `ScoredChunk[]` — `{ chunk: ChunkRow, score: number }`, по 40 кандидатов каждый.

Оба запроса идут через `Promise.all` — они независимы и каждый ходит в свою индексную структуру. Фильтр ниши одинаковый: `business_type = $ниша OR scope = 'global'` (сквозные чанки видны всегда); при `niche: null` фильтра нет.

### Vector-поиск

```sql
select ..., 1 - (embedding <=> $1::vector) as score
from chunks
where embedding is not null and (business_type = $2 or scope = 'global')
order by embedding <=> $1::vector
limit 40
```

`<=>` в pgvector — косинусное **расстояние** (0 = одинаковые вектора, 2 = противоположные). `1 - расстояние` = **сходство** (1 = идеал). Поиск идёт по HNSW-индексу, построенному при загрузке эмбеддингов. Ловит смысл: «где взять деньги на старт» найдёт чанк про «источники финансирования», хотя общих слов нет.

### FTS-поиск

Строка запроса сначала превращается в tsquery на стороне приложения (`buildTsQuery`):

1. Нижний регистр, разрез на термы `[a-zа-яё0-9]+` — знаки препинания выбрасываются (сырой текст сломал бы `to_tsquery` синтаксической ошибкой).
2. Кириллические термы длиной ≥ 3 получают `:*` — префикс-матчинг: `кофейн:*` найдёт «кофейню», «кофейни», «кофейням». Пользователь почти никогда не пишет слово в той форме, что в тексте.
3. Числа и латиница не префиксуются («152-фз», «smm») — точные термины.
4. Склейка через ` & `: `кофейн:* & открыть`.

```sql
select ..., ts_rank(tsv, q) as score
from chunks, to_tsquery('russian', $1) q
where tsv @@ q and (business_type = $2 or scope = 'global')
order by score desc
limit 40
```

Русский конфиг сам приводит словоформы к леммам и сравнивает с tsvector-колонкой `tsv` (GIN-индекс). Ловит точные слова и артикулы, которые эмбеддинг размывает. Пустой tsquery (в запросе нет букв/цифр) → FTS пропускается, возвращается `[]`.

Зачем два поиска: эмбеддинг понимает смысл, но размывает точные термины; FTS точен по словам, но слеп к синонимам. Пересечение двух независимых сигналов надёжнее любого из них по отдельности — это и эксплуатирует следующий шаг.

## Шаг 5. RRF — слияние двух списков

**Файлы:** `steps/fusion/` — `rrf.ts` + `fusion.config.ts` (`k: 60`, `topK: 20`).

**Вход:** `[vectorHits, ftsHits]` — два списка по 40.
**Выход:** один список `ScoredChunk[]` топ-20.

**Проблема, которую решает:** скоры двух поисков несравнимы. Косинусное сходство живёт около 0.6–0.9, `ts_rank` — около 0.01–0.1. Нельзя просто сложить или вычесть — один список всегда задавит другой.

**Решение — Reciprocal Rank Fusion:** работают только **позиции**, сырые скоры выбрасываются. Каждый чанк получает вклад по формуле:

```
score = Σ 1 / (k + rank),   rank начинается с 1, k = 60
```

Пример. Чанк `coffee_shop-1.3-b01`:
- в vector-списке на позиции 1 → вклад `1/61 ≈ 0.0164`
- в FTS-списке на позиции 4 → вклад `1/64 ≈ 0.0156`
- итог: `0.0320`

Чанк `coffee_shop-2.1-b02` — только в vector-списке на позиции 2 → `1/62 ≈ 0.0161`. Несмотря на высокую позицию в одном списке, он проигрывает первому чанку: **совпадение в двух независимых поисках бьёт одиночное лидерство**. В этом весь смысл RRF — консенсус бустится, дубликат при этом остаётся в списке один раз (дедуп по `chunk_id`, вклады суммируются).

Константа `k = 60` сглаживает разницу рангов внутри одного списка: без неё позиция 1 vs 2 давала бы слишком большой перекос, с ней вклады позиций 1 и 7 отличаются в разы, а не на порядок. После слияния список режется до 20 — это **окончательная** отрезка: rerank на следующем шаге видит только эти 20.

## Шаг 6. Rerank

**Файлы:** `steps/rerank/` — `rerank.ts` + `rerank.config.ts` (`model`, `topK: 8`) + `rerank.types.ts`.

**Вход:** `query` + 20 кандидатов из RRF.
**Выход:** те же чанки, топ-8, пересортированные по `relevance_score` (0..1 от Jina).

**Зачем нужен вообще, если есть эмбеддинги.** Эмбеддинг — это *bi-encoder*: запрос и документ превращаются в вектора **независимо**, потом сравнивается геометрия. Это быстро (индекс, миллисекунды), но грубо — модель не видит текст запроса и текст чанка вместе. Reranker — *cross-encoder*: он читает пару «запрос + документ» целиком и выносит вердикт релевантности. Медленно (один запрос к API на каждый документ), поэтому применяется только к 20 кандидатам, а не к 443 чанкам корпуса. Классическая воронка: дешёвый широкий поиск → дорогой точный дожим.

Пайплайн отправляет в Jina `query` + массив текстов 20 кандидатов, получает `results: [{ index, relevance_score }]`. Jina может вернуть results не по порядку — порядок восстанавливается по `index`, сортировка по убыванию скора, отрезка до 8. Итоговые 8 хитов — то, что пойдёт в small-to-big.

**Отказоустойчивость:** ошибка API роняет весь `retrieve()` (3 попытки retry внутри, потом исключение наружу). Логика: rerank и эмбеддинг — один провайдер (Jina); если недоступен rerank, эмбеддинг тоже бы упал, а отдавать неотранжированный контекст смысла нет.

## Шаги 7–8. Small-to-big и ссылки (expand)

**Файлы:** `steps/expand/` — `expand.ts` + `expand.types.ts` (`ContextUnit`, `ExpandedGroup`).

**Вход:** 8 хитов после rerank.
**Выход:** `ExpandedGroup[]` — группы «блок целиком + родитель + ссылки».

Это самое хитрое место конвейера. Разберём по слоям.

### Зачем это всё

Хит — это маленький кусок текста (дроблёный блок, ~200 токенов), который **ранжируется** хорошо, но **читается** плохо: обрывок без начала мысли. Small-to-big = «ищем маленьким, отдаём большим». У каждого хита достраивается окружение:

- **блок целиком** — все куски дроблёного блока склеиваются в один сплошной текст;
- **родительская секция** — чанк-секция, к которой принадлежит блок (компактное резюме ~300–500 токенов);
- **связанные разделы** — явные ссылки из таблицы `chunk_links` («см. также раздел 10.4»).

### Как в БД устроены куски (важно для понимания запросов)

Дерево чанков: `секция → блоки → куски`. В DDL нет колонки `part_index`, зато есть два поля, которых хватает:

- у **всех** блоков секции (и целых, и кусков) `parent_id` = id чанка-секции;
- у всех кусков **одного** блока `chunk_index` совпадает — это номер блока внутри секции.

То есть пара `(parent_id, chunk_index)` однозначно identifies блок. Пример:

```
coffee_shop-1.3            ← чанк-секция (parent_id = null)
├─ coffee_shop-1.3-b01     ← блок целиком,        parent_id = coffee_shop-1.3, chunk_index = 0
├─ coffee_shop-1.3-b02-p1  ← кусок 1 блока 2,     parent_id = coffee_shop-1.3, chunk_index = 1
├─ coffee_shop-1.3-b02-p2  ← кусок 2 того же блока, parent_id = coffee_shop-1.3, chunk_index = 1
└─ coffee_shop-1.3-b03     ← блок целиком,        parent_id = coffee_shop-1.3, chunk_index = 2
```

### Ход запросов — их всего четыре на все 8 хитов

Никаких запросов на каждый хит — всё множество достаётся пакетно:

```ts
// 1. Все блоки всех задействованных секций — ОДИН запрос
select ... from chunks where parent_id = any($1::text[])   // parentIds = уникальные parent_id хитов

// 2. Родительские секции — ОДИН запрос
select ... from chunks where chunk_id = any($1::text[])    // те же parentIds

// 3. Ссылки всех хитов — ОДИН запрос
select from_chunk_id, to_section from chunk_links where from_chunk_id = any($1::text[])

// 4. Секции-цели ссылок — ОДИН запрос
select ... from chunks where section_code = any($1::text[]) and parent_id is null
```

Первый запрос возвращает **все блоки секций** (например, 8 секций × ~6 блоков = ~50 строк), а не только нужные — фильтрация до нужных блоков происходит в JS на следующем шаге. Это осознанный размен: один запрос на 50 строк дешевле и проще, чем 8 точечных запросов.

### Группировка и склейка в JS

```ts
const key = `${chunk.parent_id}|${chunk.chunk_index}`;   // ключ блока
const siblings = blocksByParent.get(parent_id)
                   .filter(c => c.chunk_index === chunk.chunk_index);  // куски ТОЛЬКО этого блока
siblings.sort((a, b) => a.line_start - b.line_start);     // порядок кусков = порядок строк в исходнике
const text = siblings.map(c => c.text).join('\n\n');      // склейка
```

- Если у блока один чанк — это блок целиком, склеивать нечего.
- Если несколько — это куски, они склеиваются конкатенацией `text` по порядку. Порядок даёт `line_start` (строка начала куска в исходном markdown) — надёжнее любого разбора суффиксов `-pN`.
- Если у хита `parent_id = null` — сам хит является чанком-секцией; блок-юнит это он сам, родителя нет.

### Дедуп: почему групп, а не хитов

Несколько хитов могут указать на один блок (например, `-b02-p1` и `-b02-p2` оба в топ-8). Блок и родитель включаются **один раз** — группа keyed по `parent_id|chunk_index`, первый хит создаёт группу, остальные просто дописываются в `group.hits`. Ссылки при этом собираются с **каждого** хита группы (у разных кусков могут быть разные ссылки) с дедупом по id секции-цели; ссылка на собственного родителя группы отбрасывается — родитель и так включён.

### Приоритет цели ссылки

`to_section` в `chunk_links` — просто код («10.4»). Секция с таким кодом может существовать в нескольких нишах и в global. Выбор цели:

1. секция **той же ниши, что хит** (`business_type` хита);
2. иначе сквозная (`scope = 'global'`);
3. иначе первая попавшаяся.

### Итоговая структура

```ts
ExpandedGroup {
  key: string              // "coffee_shop-1.3|1" — ключ блока
  score: number            // лучший rerank-скор хитов группы
  block: ContextUnit       // блок целиком: склеенный text + все parts
  parent: ContextUnit|null // чанк-секция
  links: ContextUnit[]     // связанные секции
  hits: ScoredChunk[]      // какие хиты сюда попали
}
```

## Шаг 9. Сборка контекста (assemble)

**Файлы:** `steps/assemble/` — `assemble.ts` + `assemble.config.ts` (`tokenBudget: 12000`, `encoderModel: 'gpt-4o'`) + `assemble.types.ts`.

**Вход:** `ExpandedGroup[]`.
**Выход:** `AssembledContext { context: string; chunks: ContextChunk[]; truncated: boolean; usedCount: number }`.

Правила сборки, по порядку:

1. **Порядок блоков** — по убыванию rerank-скора лучшего хита группы. Самое релевантное — в начало контекста (модели внимательнее к началу).
2. **Формат каждой единицы** — заголовок-источник + маркер:

   ```markdown
   ## Источник: Открытие > Регистрация > 1.3 Выбор системы налогообложения

   {текст блока целиком}

   ## Контекст секции: Открытие > Регистрация

   {текст родительской секции}

   ## Связанный раздел: 10.4 Налоговые вычеты

   {текст связанной секции}
   ```

   Маркеры («Контекст секции», «Связанный раздел») отделяют основной материал от фонового — модель понимает, что хит важнее, чем добор.
3. **Токен-бюджет 12 000** — каждая единица считается `js-tiktoken` (энкодер gpt-4o) и добавляется, только если влезает.
4. **Атомарность блока.** Блок не режется посреди: если блок целиком не влезает в остаток бюджета — пропускается **вся его группа** (родитель и ссылки вместе с ним), конвейер идёт к следующей, возможно более короткой, группе. Лучше потерять один блок, чем отдать модели обрывок. `truncated = true`.
5. **Добор не гарантирован.** Если блок влез, а родитель — нет: блок остаётся, родитель пропускается, `truncated = true`. Бюджет важнее полноты добора.
6. **Список `chunks`** — все использованные чанки с ролями (см. ниже), дедуп по `chunk_id`.

## Роли чанков и их приоритет

Каждый чанк в итоговом `chunks` несёт роль — откуда он взялся в контексте:

| Роль | Откуда | Смысл |
|---|---|---|
| `hit` | нашёл поиск, прошёл rerank | главный материал, за него голосовал rerank |
| `part` | соседний кусок того же блока | добор до целого блока, сам хитом не был |
| `parent` | родительская секция блока | фон сверху: заголовок и резюме секции |
| `link` | запись в `chunk_links` | смежный раздел, на который автор ссылался явно |

**Приоритет `hit > part > parent > link`** нужен для одного случая: чанк попадает в контекст несколькими путями сразу. Например, чанк-секция `coffee_shop-1.3` — и родитель блока-хита, и сама оказалась хитом (поиск нашёл её текст), и цель чьей-то ссылки. В списке `chunks` она должна остаться **один раз** — с самой «главной» ролью. Главная = та, что ближе к причине попадания контекста: `hit` — первоисточник (ранжирование), `part` — добор к хиту, `parent`/`link` — фоновые надстройки. Скор при этом берётся от хита, который привёл чанк в контекст.

## Шаг 10. Контракт результата

**Файл:** `types/retrieval.types.ts`. Наружу отдаётся ровно это:

```ts
interface RetrievalResult {
  context: string;          // готовый текст для промпта модели
  chunks: ContextChunk[];   // какие чанки использованы: id, заголовки, тип, score, роль
  meta: {
    niche: NicheCode | null;
    niche_source: 'ui' | 'fulltext-probe' | 'llm' | 'none';
    confidence: number | null;
    counters: { vector: number; fts: number; rrf: number; rerank: number; context: number };
    truncated: boolean;     // контекст обрезан по бюджету
  };
}
```

`counters` — след воронки на каждом этапе (40 → 40 → 20 → 8 → N чанков в контексте); по ним видно, где поиск теряет кандидатов. `meta` — для отладки и будущего UI («поиск шёл в нише X, определён автоматически»).

## Отказоустойчивость

- Все сетевые вызовы (Jina embed, Jina rerank, z.ai) и все SQL-запросы обёрнуты в `withRetry` (`lib/retry.ts`): 3 попытки, паузы 1с → 2с → 4с.
- Падение rerank, эмбеддинга или БД **роняет весь `retrieve()`** — частичный результат не отдаётся.
- Падение классификатора — не роняет: поиск продолжается без фильтра ниши.
- Отсутствующая env-переменная даёт ошибку с именем переменной и пояснением, зачем она нужна.
