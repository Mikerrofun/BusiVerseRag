# План: переработка eval-системы retrieval (ветка evalImprove-plan)

## Контекст и цель

Текущий прогон (`docs/eval/fullEvalRun-08112026.json`) показал: recall 0.91, precision 0.18, perfect_matches 0/34, прогналось только 34 вопроса из 45. Разбор показал три корневые причины:

1. **Баг**: все вопросы с `business_type: null` (10 бывших global + q-hard-03) молча выпадают из прогона — валидация ниши в `eval.ts` не пропускает `null` и раннер пропускает вопрос с ошибкой.
2. **Метрика измеряет не то**: сравнение идёт на уровне отдельных чанков, а pipeline после rerank возвращает все части (`block.parts`) найденных блоков — это осознанный дизайн (обрывок таблицы бесполезен), но метрика считает части того же блока ложными срабатываниями. Даже идеальный поиск упирается в потолок F1 ≈ 0.33.
3. **Датасет не соответствует системе**: дубли expected-чанков, составные вопросы с завышенным тегом easy, global-блок, который решено убрать.

Цель: честные метрики на уровне блоков, датасет из 30 вопросов (15 easy / 10 medium / 5 hard) без global-блока, baseline-прогон.

**Вне скоупа (делается позже, отдельно):** rerankMax с порогом отсечения нерелевантных запросов (контекст пуст, если максимальный скор ниже порога ~0.4) и метрика abstain_correct на его основе; оценка стоимости контекста; оптимизация ссылок в expand.

## Файлы для изучения (начать отсюда)

Изучать в этом порядке — первые четыре это рабочая зона, остальные дают контекст:

1. `retrieval/eval/evalFunction/eval.ts` — ядро оценки: валидация входа (именно здесь баг с null-нишей), `extractChunkIds`, `evalRetrieve` (полный флоу: embed → FTS → RRF → rerank → expand → сравнение с expected).
2. `retrieval/eval/runner/runner.ts` — оркестрация прогона: чтение `questions.jsonl`, вызов `evalRetrieve`, сборка per-question результата, вызов агрегации метрик.
3. `retrieval/eval/runner/metrics.ts` — текущая агрегация (chunk-level P/R/F1, perfect_match) — её заменяем.
4. `retrieval/eval/questions.jsonl` — датасет из 45 вопросов: структура вопроса (id, difficulty, business_type, expected_chunk_ids, expected_sections).
5. `retrieval/steps/expand/expand.ts` — что именно попадает в retrieved: группы после rerank, из которых eval берёт только `block.parts` (parent и links в eval не считаются).
6. `docs/feature/eval-kit.md` — замысел eval-кита и известные упрощения.
7. `docs/feature/retrieval-pipeline.md` — полный пайплайн retrieval.
8. `docs/eval/fullEvalRun-08112026.json` — baseline-прогон: по нему видно, какие вопросы как искались (retrieved/expected по каждому qid).

## Правила реализации (обязательные)

- **Типизация по FSD**: все новые типы/интерфейсы (структуры результата прогона, метрик, флагов датасета) выносятся в отдельные файлы типов, не лежат рядом с логикой. Конфиги (пороги и константы, например `PERFECT_THRESHOLD`) — тоже в отдельных конфиг-файлах, не в коде логики.
- **Комментарии**: только для действительно важных и неочевидных с первого взгляда мест (например, почему null считается валидной нишей). Не комментировать каждый шаг.
- **Документацию не писать и не запрашивать** — она будет делаться после полного рефакторинга отдельно.
- **Тесты — в конце, минимальные** (см. последний раздел), не перегружать ими работу.
- Задачи ниже описаны флоу без кода — опираться на указанные файлы и функции.

## Задачи

### Задача 1. Фикс валидации ниши (null — легитимное значение)

**Проблема.** В `eval.ts` перед `evalRetrieve` стоит проверка: если `niche` не undefined и не проходит `isNicheCode` — бросается исключение, раннер молча пропускает вопрос. Для вопросов с `business_type: null` каст даёт `null`, проверка падает, вопрос выпадает. Так потерялись 11 из 45 вопросов последнего прогона.

**Флоу.** В `eval.ts` найти валидацию ниши и сделать `null` валидным значением, означающим «ниша не задана». Дальше по цепочке менять ничего не нужно: в `evalRetrieve` уже стоит выбор «ниша из входа или классификатор» через nullish-коалесцию, и `null` трактуется как отсутствие значения — то есть для безнишевых вопросов автоматически запустится `detectNiche(query)`. Проверить вручную, что вопрос с `business_type: null` проходит весь `evalRetrieve` без исключения и классификатор срабатывает.

### Задача 2. Датасет → 30 вопросов (15 easy / 10 medium / 5 hard)

Работа с `retrieval/eval/questions.jsonl`, по одному вопросу за раз, с опорой на baseline-прогон (файл из списка изучения №8).

**Флоу.**

- Убрать все 10 вопросов `q-global-*` — global-блок исключён из системы оценки решением владельца (мало чанков, контент — описания/сводки законов, реальные запросы нишевые или безнишевые).
- Убрать дубли: несколько вопросов, указывающих на один и тот же expected-чанк/блок, оставлять по одному (смотреть по `expected_chunk_ids` в датасете).
- Убрать шаблонные повторы внутри ниш: однотипные кейс-вопросы («как развивалась X») — оставить по одному на нишу.
- Для каждого оставшегося вопроса переписать `expected_chunk_ids`: вместо одной части блока перечислить **все части** каждого expected-блока (части одного блока = один смысловой кусок, обрывок таблицы бесполезен). Состав частей смотреть в БД/чанкинге, а не выдумывать.
- Вопросу без ответа в корпусе (`q-hard-05`) добавить явный флаг `unanswerable: true`.
- Перетеговать difficulty: составные вопросы («сколько стоит X и когда выходит в плюс» — два факта в разных местах) → medium; однофактные разговорные → easy.
- Итоговая структура: **15 easy / 10 medium / 5 hard**. Пятёрка hard: (1) кросс-секционный внутри ниши — факты из двух разных секций; (2) безнишевый (`business_type: null`) — классификатор обязан сам попасть в нишу; (3) терминология/точная норма закона (стиль существующего q-hard-01, статья КоАП — проверка FTS-плеча); (4) мульти-факт — два expected-блока; (5) unanswerable.
- qid переносимых вопросов сохранять без изменений (на них завязаны прошлые прогоны).
- Итог: ровно 30 строк в `questions.jsonl`.

### Задача 3. Метрики на уровне блоков

Заменить первичные метрики в `runner/metrics.ts` (и в per-question подсчёте в `eval.ts`, если он там). Ключевое правило: **block id = id чанка без суффикса части** (отрезать `-pN`).

**Новые метрики.**

- `block_recall` — доля expected-блоков, чьи части найдены среди retrieved. Главная метрика поиска: «система нашла правильное место в документе».
- `hit` (бинарный, на вопрос) — найден хотя бы один expected-блок. Агрегат `hit_rate` — доля вопросов без полного промаха.
- `precision_parts` — доля retrieved-частей, принадлежащих expected-блокам. После задачи 2 (expected = все части блока) метрика честная: части того же блока больше не FP.
- `perfect_match` — вопрос идеален, если `block_recall ≥ 0.9`. Порог вынести в конфиг как `PERFECT_THRESHOLD = 0.9`.
- `MRR` — средняя обратная позиция первого expected-блока в порядке rerank (см. задачу 4).
- Вопросы с флагом `unanswerable` **исключаются из всех средних** и выводятся отдельной строкой отчёта (сейчас они ломают precision: любой найденный чанк для них FP).

**Чего НЕ делать.** Не добавлять `context_size` (eval не формирует контекст и не оценивает его), не добавлять `block_f1` (решено: дублирующая сводная). Старые chunk-level P/R/F1 можно оставить вторичными в отчёте для сравнения со старыми прогонами, но первичными становятся метрики выше.

### Задача 4. Сохранение порядка rerank для MRR

**Проблема.** Раннер пишет в per-question результат только итоговый список retrieved-чанков — порядка групп после rerank нет, MRR посчитать не из чего.

**Флоу.** В `runner.ts` (или в результате, который возвращает `evalRetrieve`) добавить сохранение упорядоченного списка block id после rerank — в том порядке, в котором rerank отдал группы. Типы результата расширить в файле типов (не инлайн). Порядок должен сохраняться до expand, чтобы он не зависел от сортировки итогового списка чанков.

### Задача 5. Baseline-прогон

Прогнать eval на новом датасете из 30 вопросов, результат сохранить в `docs/eval/` в формате существующих прогонов (например `fullEvalRun-<дата>-v3-block-metrics.json`).

**Проверки перед сохранением:** обработано ровно 30 из 30 вопросов, ни одного молча пропущенного; unanswerable-вопрос не влияет на средние; в отчёте присутствуют все новые метрики. Этот файл — точка отсчёта для всей дальнейшей тюнинг-работы (topK rerank, пороги).

## Тесты (минимальные, в конце)

1. **Синтетическая проверка метрик**: на фиксированном наборе expected/retrieved (2–3 блока, известный заранее результат) убедиться, что block_recall, precision_parts, perfect_match и MRR считаются как ожидается — включая краевой случай «найдена только часть expected-блока» (засчитывается как найденный блок).
2. **Прогон без пропусков**: полный прогон на 30 вопросах — ноль пропущенных, включая безнишевые с `business_type: null`.
3. **Изоляция unanswerable**: убедиться, что средние метрики с unanswerable-вопросом и без него не отличаются (он исключён), и что он виден в отчёте отдельной строкой.
