# План: переработка eval-системы retrieval (ветка evalImprove-plan)

## Контекст и цель

Текущий eval показывает recall 0.91 при precision 0.18 и 0 perfect_matches из 34. Диагноз (обсуждён с владельцем проекта):

1. **Метрика измеряет не то.** `calculateMetrics` сравнивает retrieved и expected на уровне отдельных чанков, а expected в датасете размечен слишком узко (1–2 конкретных части блока). При этом pipeline после rerank возвращает **все части блока** (`block.parts`) для каждого из 5 rerank-хитов — то есть 5–10 чанков на вопрос. Части того же блока, что и expected, засчитываются как FP. Даже идеальный поиск на этой метрике даёт F1 ≈ 0.33.
2. **11 из 45 вопросов молча выпадают.** У вопросов с `business_type: null` (бывшие global + q-hard-03) значение `null` не проходит валидацию `isNicheCode` в `evalRetrieve` → throw → runner ловит ошибку и молча пропускает вопрос. В прогоне `fullEvalRun-08112026.json` группа global отсутствует целиком.
3. **Датасет избыточен и нерелевантен системе**: 10 global-вопросов (решено убрать — блок global это описания/сводки законов, реальные запросы нишевые или безнишевые), дубли expected-чанков, double-barrel формулировки, устаревшая разметка частей.

Цель: перевести оценку на уровень блоков, сократить датасет до 30 вопросов (15 easy / 10 medium / 5 hard), починить null-нишу. **Baseline-прогон выполняет владелец проекта сам после завершения работ — в план не входит.**

Вне скоупа (будущие итерации владельца, не трогать): rerankMax с порогом ~0.4 и abstain-логика, оценка контекста/context_size, оптимизация links (топ-3 + score ≥ 0.7 — уже сделана владельцем в expand).

## Задача 1. Фикс валидации ниши: `null` — легитимное значение

**Проблема.** В `eval.ts` валидация входа: если `input.niche !== undefined` и `!isNicheCode(input.niche)` — throw. Для вопросов без ниши `business_type = null`, runner передаёт его как есть, `null !== undefined` → true, `isNicheCode(null)` → false → throw «неизвестный код "null"». Runner глотает ошибку — вопрос молча пропадает из прогона.

**Принцип (решение владельца):** в системе для ниши не существует `undefined`. Ниша — либо валидный `NicheCode`, либо `null` («ниша неизвестна»). `undefined` из типов и кода eval убирается полностью; источник истины — датасет, где `business_type: null` уже означает «ниши нет».

**Флоу исправления:**

1. В `eval.types.ts` тип поля `niche` в `EvalRetrieveInput` сделать `NicheCode | null` (сейчас `NicheCode | undefined`). Никакого `undefined` в типе быть не должно.
2. В `eval.ts` изменить валидацию: throw только если значение не `null` и не проходит `isNicheCode`. `null` проходит дальше как «ниши нет».
3. В `runner.ts` убрать каст на `NicheCode | undefined` — передавать `q.business_type` как есть: тип `EvalQuestion.business_type` уже `NicheCode | null` и совпадает с новым типом входа без преобразований.
4. Проверить по цепочке, что дальше всё уже работает: в `evalRetrieve` вызов `detectNiche(query, input.niche)` — оператор `??` трактует `null` как отсутствие значения, поэтому для null-вопросов запустится классификатор `detectNiche(query)` сам. В результате `decision.niche` станет выбранной классификатором нишей, `niche_source` — не `'ui'`. Это ожидаемое поведение, ничего доп��лнительно менять не нужно.
5. Проверка: взять из текущего questions.jsonl любой вопрос с `business_type: null` и прогнать через `evalRetrieve` — не должно быть throw, должен отработать классификатор.

## Задача 2. Датасет: 45 → 30 вопросов (15 easy / 10 medium / 5 hard)

Работа с `retrieval/eval/questions.jsonl`. Файл заменяется на месте (история в git сохранится).

**2.1. Убрать global-блок.** Все 10 вопросов `q-global-*` удаляются. Решение владельца: global-чанки — описания и своды законов, запросы по ним нецелевы; безнишевые запросы покрываются hard-вопросом №2.

**2.2. Убрать дубли.** Несколько вопросов указывают на одни и те же expected-чанки (в текущем датасете: три вопроса на `global-0-b01`, два на `global-11-b01-p2` — все уходят вместе с global). Внутри ниш есть шаблонные повторы вида «Как развивалась X» — на нишу оставлять один такой вопрос, остальные удалять. При равной ценности оставлять вопрос с более естественной разговорной формулировкой.

**2.3. Переразметить expected на уровне блоков.** Для каждого оставшегося вопроса:

1. Из текущих `expected_chunk_ids` получить множество блочных id (отрезать суффикс `-pN`).
2. Для каждого блочного id запросить в БД все его части: таблица `chunks`, части одного блока имеют одинаковый `parent_id` и `chunk_index`; по id — выборка всех `chunk_id` с префиксом `<section>-b<NN>-`. Использовать существующее подключение проекта (lib/db), можно одноразовым скриптом.
3. Записать в `expected_chunk_ids` **все части всех expected-блоков** (это решение владельца: частичный кусок таблицы сам по себе бесполезен, поэтому expected = блок целиком). Благодаря этому метрики (задача 3) сравнивают множества частей напрямую, без разбора структуры id.
4. Заодно сверить, что каждый expected-блок реально существует в БД. Если блока нет — разметка устарела: либо найти актуальный блок по `expected_sections` и содержанию вопроса, либо вынести вопрос владельцу на решение (не молча удалять и не молча подменять).
5. Поля `expected_section` / `expected_sections` оставить как есть — они остаются в датасете для будущего использования, в метрики текущей итерации не входят.

**2.4. Пометить unanswerable.** Вопрос `q-hard-05` (ответа в корпусе нет) — флаг `unanswerable: true`. Поле уже есть в типе `EvalQuestion` и в датасете, достаточно проставить значение. Такой вопрос исключается из всех средних (см. задачу 3), поэтому его присутствие не искажает метрики.

**2.5. Перетеговать difficulty.** Целевое распределение: 15 easy / 10 medium / 5 hard. Критерии владельца:

- **easy** — однофактный вопрос, разговорная формулировка, один expected-блок («Сколько стоит открыть X?»).
- **medium** — однофактный, но с точной терминологией (названия законов, ФЗ, ОРД, erid — проверка FTS-плеча), либо сравнительный (Москва/регион), либо double-barrel («сколько стоит X и когда окупится» — два факта, два expected-блока).

## Задача 3. Новая система метрик (сравнение на уровне частей)

Это самая крупная задача — меняет контракт данных между всеми файлами eval. Полностью заменяет чанковую P/R/F1 из `metrics.ts`. **Не добавлять** `context_size` и `block_f1` — владелец решил, что eval не оценивает контекст, а block_f1 дублирует остальные метрики.

**3.1. Принцип сравнения (решение владельца):** id нигде не парсятся и суффиксы `-pN` не отрезаются. Так как expected содержит **все части** expected-блоков (задача 2.3), метрики считаются прямым сравнением множеств частей. Оговорка: если чанкинг изменится и у блока появятся новые части, expected перегенерируется — это уже покрыто сверкой с БД в задаче 2.3.

**Определения (без кода, только формулы):**

- `expected` — множество id из `expected_chunk_ids` (все части expected-блоков).
- `retrieved` — множество id из `retrieved_chunk_ids`.
- **`recall`** = |expected ∩ retrieved| / |expected|. Главная метрика: так как expected = блок целиком, recall 1.0 означает «блок пришёл целиком», а частичное попадание даёт дробное значение — гранулярнее, чем бинарное «блок найден/не найден».
- **`hit`** — булево на вопрос: recall > 0, т.е. найдена хотя бы одна expected-часть. Агрегат **`hit_rate`** = доля вопросов с hit.
- **`precision`** = |expected ∩ retrieved| / |retrieved|. Части того же блока, что и expected, больше не FP — метрика честна.
- **`perfect_match`** = recall ≥ 0.9. Порог — константа `PERFECT_THRESHOLD = 0.9` в конфиг-файле eval (не в логике).
- **`mrr`** — см. задачу 4.
- Счётчики для прозрачности: |expected|, |retrieved|, |expected ∩ retrieved|.

**3.2. Unanswerable.** Вопрос с флагом `unanswerable: true`:

- метрики для него считаются и сохраняются в per-question результате (прозрачность), но **исключаются из всех агрегатов** — средних, by_difficulty, by_group, hit_rate, perfect_matches;
- в агрегированном отчёте — отдельная строка: сколько unanswerable-вопросов было, сколько обработано (исключено из средних). Полноценная метрика abstain_correct появится позже у владельца вместе с rerankMax — сейчас не реализовывать.

**3.3. Затрагиваемые файлы и поток данных:**

1. `runner.types.ts` — новый shape `EvalMetrics` (вместо precision/recall/f1/TP/FP/FN): перечисленные в 3.1 поля + qid/question/difficulty + флаг unanswerable. Типы — только здесь.
2. `metrics.ts` — переписать `calculateMetrics`: вход — expected_chunk_ids, retrieved_chunk_ids, retrieved_chunk_ids_ordered (из задачи 4), флаг unanswerable. Внутри — только операции над множествами id, без разбора структуры id.
3. `aggregation.ts` — `aggregateMetrics`: фильтрация unanswerable до агрегации; новые средние (avg recall, avg precision, avg mrr), hit_rate, perfect_matches; группировки by_difficulty / by_group с теми же полями; отдельный блок unanswerable.
4. `formatters.ts` — `printAggregatedMetrics` под новые поля; строка про unanswerable.
5. `runner.ts` — передача новых аргументов в `calculateMetrics`; JSON-выгрузка (`--json`) включает новые поля per-question: retrieved_chunk_ids_ordered, метрики нового shape. Формат файла результата сохранять совместимым по духу (timestamp, aggregated, results).
6. Конфиг-файл eval — `PERFECT_THRESHOLD = 0.9`.

**3.4. Чего не делать:** не трогать `extractChunkIds` (он уже правильный — только block.parts), не добавлять parent/links в eval, не считать контекст, не менять сам pipeline.

## Задача 4. Порядок rerank в результате eval (основа для MRR)

**Зачем.** MRR показывает, на какой позиции rerank нашлась первая правильная часть — это главная метрика для сравнения rerank-моделей и настройки topK. Сейчас порядок после rerank теряется: `extractChunkIds` собирает Set (порядок не гарантирован), в JSON уходит только плоский список.

**Флоу:**

1. **Источник порядка.** `expandHits` возвращает группы в порядке первых вхождений хитов после rerank (Map в `expand.ts` сохраняет порядок вставки; группа создаётся при первом хите этого блока). Значит, итерация по массиву групп сверху вниз = порядок rerank от лучшего к худшему. Это неочевидный факт — здесь уместен один комментарий в коде.
2. **Извлечение в `eval.ts`.** Новая функция рядом с `extractChunkIds` (по её образцу): идёт по группам по порядку, из каждой группы берёт `block.parts` в порядке их следования, собирает плоский список chunk_id с сохранением порядка и без дубликатов (часть может появиться в нескольких группах — брать первое вхождение). Результат — упорядоченный список retrieved-частей от лучшего rerank-хита к худшему. Никакой нормализации id — части сравниваются с expected как есть.
3. **Дополнительно сохранить топ-скор rerank** (скор первой группы) в результат eval. Причина: владелец планирует rerankMax с порогом ~0.4 — наличие распределения топ-скоров в eval-результатах позволит откалибровать порог по данным без отдельного исследования. Это пассивное поле, на метрики не влияет.
4. **Типы** (`eval.types.ts`): новые поля `EvalRetrievalResult` — упорядоченный список retrieved-частей и топ-скор. Типы — в файле типов.
5. **Прокинуть в метрики**: `calculateMetrics` получает упорядоченный список (задача 3.3) и считает mrr: позиция (1-based) первого элемента expected в упорядоченном списке, mrr = 1/позиция; если ни одна expected-часть не найдена — mrr = 0. Так как expected содержит все части блока, первая найденная expected-часть = первое попадание в нужный блок. Агрегат — среднее mrr по не-unanswerable вопросам.
6. **JSON-выгрузка** (runner.ts): упорядоченный список попадает в per-question результат — по нему вручную можно видеть, на каком месте rerank оказалась правильная часть.

**Влияние на систему:** это единственная задача, добавляющая новые данные в контракт между expand → eval → runner → metrics → JSON. Все изменения полей — только через файлы типов; логика expand.ts не меняется.

## Тесты (минимальные, в конце; не перегружать)

Образец организации тестов в проекте — `test:chunking` (`tsx --test`). Новый тестовый файл рядом с runner (по структуре проекта), запуск добавлением скрипта в package.json по образцу.

## Критерии готовности
