## Контекст изменений

Этот прогон выполнен после завершения рефакторинга eval-системы (ветка evalImprove, план `docs/plan/evalImprove-plan.md`). Главные изменения:

1. **Expected на уровне блоков** — разметка датасета переработана: теперь `expected_chunk_ids` содержат все части блоков (раньше — одну часть). Метрики сравнивают множества честно: части того же блока больше не считаются false positives.

2. **Новая система метрик:**
   - **Recall** — главная метрика: доля найденного из нужного (0.883 = 88.3%)
   - **Hit rate** — доля вопросов, по которым найдена хотя бы одна expected-часть (0.967 = 96.7%)
   - **Precision** — доля правильного среди найденного (0.213 = 21.3%, низкая за счёт expand-контекста)
   - **MRR** (Mean Reciprocal Rank) — ранговая метрика: насколько высоко в rerank первая правильная часть (0.770)
   - **Perfect match** — recall ≥ 0.9 (порог из конфига): 25 из 30 вопросов (83.3%)

3. **Датасет 30 вопросов** (было 45): удалены 10 global (вне скоупа нишевого retrieval), 5 дублирующих easy. Структура: 15 easy / 10 medium / 5 hard. Группы: 25 niche + 5 hard.

4. **Фикс null-ниши:** вопросы с `business_type: null` теперь легитимны — классификатор определяет нишу сам. `q-hard-03` тестирует именно это, но сейчас падает из-за отсутствия `ZAI_API_KEY` (классификатор недоступен).

5. **Порядок rerank сохранён:** `retrieved_chunk_ids_ordered` + `top_rerank_score` — основа для будущей калибровки maxRerank-гейта.

### 🔴 q-hard-03: Miss (recall 0%, MRR 0)

```
Query: "Сколько нужно вложить, чтобы открыть бизнес с нуля, и какие форматы самые дешёвые по старту?"
Business type: null → классификатор недоступен (ZAI_API_KEY not set)
Niche detected: none (source: none)

Expected (2): global-11-b01-p1, global-11-b01-p2
Retrieved (11): own_online_store-9.3-b01-p1/p2, pickup_point-2.3-b03-p1/p2,
                marketplace_seller-6.3-b03-p1/p2, remote_accounting-10.3-b03-p1/p2,
                coffee_shop-1.3-b01-p1/p2, coffee_shop-1.3-moscow

✅ Expected — сводная таблица стартовых вложений по всем нишам (блок global-11-b01).
❌ Retrieved — куски финмоделей отдельных ниш (секции X.3), но не сводка.
```

**Причина:** классификатор не сработал (нет ключа), ниша не определена → поиск шёл без фильтра ниши → vector и FTS нашли отдельные нишевые таблицы финмоделей, но не глобальную сводку. Global-чанки (сводные таблицы) без фильтра ниши тонут в нишевых результатах.

**Что это значит:** вопрос проверяет два сценария:
1. Классификатор должен определить, что вопрос безнишевый (сравнение всех форматов) → вернуть `niche: null` → retrieval ищет в global.
2. Если классификатор недоступен, поиск идёт по всей БД без фильтра — этот сценарий сейчас провалился.

**Действие:** запустить с `ZAI_API_KEY` — проверить, определит ли классификатор запрос как безнишевый и найдёт ли global-чанк.


## Выводы и следующие шаги

### ✅ Что работает хорошо

1. **Easy-вопросы решаются идеально:** recall 100%, все 15 perfect match. Базовый retrieval (ниша + однофактный запрос) работает безупречно.

2. **Нишевые вопросы стабильны:** recall 94.7%, 23 из 25 perfect. Классификация ниши + фильтрация vector/FTS работают надёжно.

3. **Hit rate 96.7%:** из 30 вопросов только 1 (q-hard-03) не нашёл ни одной expected-части — и то из-за недоступности классификатора.

4. **Average MRR 0.77:** правильное обычно в топ-2 rerank. Система не только находит нужное, но и ставит его высоко.

### ⚠️ Что требует внимания

1. **Hard-вопросы проседают (recall 56.7%, MRR 0.3):**
   - **Кросс-секционные** (q-hard-01, q-hard-06): вопрос охватывает две разные микросекции → rerank находит одну, вторая выпадает.
   - **Мультифактные** (q-hard-02): два независимых факта из разных секций → находится только один.
   - **Сравнительные** (q-hard-04, q-niche-07): «Москва vs регион» → rerank находит одну таблицу, вторую пропускает.
   - **Безнишевые при отсутствии классификатора** (q-hard-03): global-чанки тонут в нишевых результатах без фильтра.

2. **Double-barrel вопросы** (q-niche-04): «сколько стоит И когда окупается» → rerank фокусируется на одной части, вторая выпадает.

3. **MRR проседает на edge cases:** даже при recall 100% правильное может быть на 4–7 месте (q-niche-21, q-niche-25, q-niche-16). Rerank поднимает близкие, но не те блоки секции.

### 🔧 Возможные улучшения (roadmap владельца)

1. **Query decomposition для multi-fact вопросов:** «налоги + санкции» → два параллельных retrieval-прохода → объединение результатов. Покроет q-hard-02, q-hard-06, q-niche-04.

2. **Калибровка maxRerank-порога:** по данным `top_rerank_score` из JSON видно распределение скоров. Если скор < 0.3 — возможно, правильного нет в топ-5 → не передавать контекст в LLM (abstain). Покроет q-hard-03 (recall 0%, top_score низкий).

3. **Промпт rerank-модели:** добавить инструкцию «при сравнительном вопросе (Москва vs регион) ранжировать оба блока высоко». Может улучшить q-hard-04, q-niche-07.

4. **Расширение topK rerank:** 5 → 8 хитов. Увеличит recall на hard-вопросах, но снизит precision (больше шума в контексте). Требует A/B на полном датасете.

5. **Классификатор fallback:** если ZAI_API_KEY недоступен, пробовать fulltext-probe по словарям ниш (уже реализован в detectNiche) → если не матчится ни одна ниша, трактовать как безнишевый запрос → искать в global. Покроет q-hard-03.
