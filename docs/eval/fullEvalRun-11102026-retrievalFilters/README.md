## Контекст изменений

Этот прогон выполнен после внедрения системы фильтрации rerank-результатов. Главные изменения:

1. **Новый шаг filter-rerank** — между rerank и expand добавлен фильтр, который отсеивает хиты с низким rerank-скором (порог 0.25). Это предотвращает попадание нерелевантного контента в final context.

2. **Изменения в pipeline:**
   ```
   До:  vector → FTS → RRF → rerank (topK=5) → expand → context
   После: vector → FTS → RRF → rerank (topK=5) → filter (score≥0.25) → expand → context
   ```

3. **Новые счетчики:** в результатах eval появилось поле `filtered` — количество хитов, прошедших фильтр (≤5).

4. **Expected изменен для тестирования:** в нескольких вопросах в expected добавлены global-чанки (сводные таблицы), чтобы проверить, как фильтр влияет на мультифактные и кросс-секционные запросы.

## Выводы

### ✅ Что работает хорошо

1. **Precision вырос почти втрое (21% → 61%)** — фильтр эффективно отсекает нерелевантный контекст. В 17 вопросах из 29 precision = 100%.

2. **Токен-эффективность улучшилась** — в контекст попадает меньше чанков (в среднем 1–3 вместо 5–8), что экономит ~50–70% бюджета токенов для LLM.

3. **Easy и medium вопросы решаются стабильно** — hit rate 87–90%, majority perfect matches. Базовый retrieval с фильтром работает.

### ⚠️ Критические проблемы

1. **Recall упал на 22% (88% → 66%)** — фильтр отсекает не только шум, но и нужный контекст. Каждый четвёртый нужный блок теряется.

2. **Hit rate упал на 17% (97% → 79%)** — 6 вопросов из 29 не нашли **ничего** (filtered=0). В eval-improve таких был только 1.

3. **Hard-вопросы ломаются полностью** — recall 8%, hit rate 25%, 0 perfect matches. Edge cases (кросс-секционные, мультифактные, безнишевые) не решаются с фильтром.

4. **Double-barrel и сравнительные вопросы проседают** — фильтр оставляет 1–2 хита, недостаточно для покрытия обеих частей вопроса.

### 🔧 Рекомендации

#### Критические (необходимо для production):

1. **Понизить порог фильтра: 0.25 → 0.15–0.20**
   - Текущий порог 0.25 слишком агрессивен.
   - Провести A/B прогоны с порогами 0.15, 0.18, 0.20 → найти sweet spot между recall и precision.
   - Цель: recall ≥ 80%, precision ≥ 40%.

2. **Адаптивный порог по типу вопроса:**
   - Easy/medium: порог 0.22 (высокая уверенность rerank).
   - Hard/multi-fact: порог 0.15 (больше tolerance к uncertain кандидатам).
   - Определение типа — через классификатор или эвристики (длина запроса, наличие «и», «vs», «отличия»).

3. **Fallback для filtered=0:**
   - Если фильтр отсёк все 5 хитов → вернуть топ-1 из rerank независимо от скора.
   - Логика: лучше дать LLM хоть что-то, чем пустой контекст. LLM сам скажет «недостаточно данных», если контекст плох.

4. **Логировать filtered counts:**
   - В production писать в метрики: сколько хитов прошло фильтр по каждому запросу.
   - Alert если `filtered=0` чаще чем 5% запросов → порог слишком высок.

#### Желательные (оптимизация):

5. **Query decomposition для multi-fact:**
   - «налоги + санкции» → два независимых retrieval-прохода → объединение после rerank → фильтр отдельно к каждому набору хитов.
   - Покроет q-hard-02, q-hard-06, q-niche-04.

6. **Расширить topK rerank до 8:**
   - Больше кандидатов для фильтра → выше шанс, что хотя бы 2–3 пройдут порог.
   - Trade-off: дороже rerank API, но меньше риска filtered=0.

7. **Калибровка порога по distribution:**
   - Собрать топ-1 скоры всех rerank-хитов из нескольких прогонов → построить гистограмму.
   - Порог = percentile 10–15 (отсекаем худшие 10–15%, сохраняем остальное).
