### 2. fullEvalRun-11102026-retrievalFilters

**Дата:** 10 ноября 2026, 22:45 UTC  
**Причина:** retrievalFilters — внедрение фильтрации rerank по минимальному скору  
**Папка:** `fullEvalRun-11102026-retrievalFilters/`
- `README.md` — подробный отчёт с анализом trade-off
- `eval-results.json` — полный JSON результатов

**Главные изменения:**
- Новый шаг filter-rerank между rerank и expand
- Фильтр отсекает хиты с rerank-скором < 0.25
- Pipeline: `vector → FTS → RRF → rerank → filter → expand`
- Новое поле в counters: `filtered` (количество хитов после фильтра, ≤5)

**Результаты:**
```
Total questions:      29 (1 упал из-за Jina rate limit)
Hit rate:             79.3%   ⚠️ -17.4% vs eval-improve
Perfect matches:      17 (58.6%)   ⚠️ -8 вопросов vs eval-improve
Average Recall:       66.2%   ⚠️ -22.1% vs eval-improve
Average Precision:    61.5%   ✅ +40.2% vs eval-improve
Average MRR:          0.733

По сложности:
  Easy (15):   recall 77.8%, precision 68.3%, perfect 11/15 ⚠️
  Medium (10): recall 72.0%, precision 65.8%, perfect 6/10 ⚠️
  Hard (4):    recall 8.3%, precision 25.0%, perfect 0/4 🔴
```

**Ключевое наблюдение: Trade-off**

| Метрика | eval-improve | retrievalFilters | Изменение |
|---------|--------------|------------------|-----------|
| Recall | 88.3% | 66.2% | **-22.1%** ⚠️ |
| Precision | 21.3% | 61.5% | **+40.2%** ✅ |

**Что это значит:**
- ✅ **Precision вырос почти втрое** — в контекст попадает гораздо меньше шума.
- ✅ **Токен-экономия ~50–70%** — меньше чанков в контексте (1–3 вместо 5–8).
- ⚠️ **Recall упал на 22%** — фильтр отсекает не только шум, но и нужный контекст.
- 🔴 **6 вопросов из 29 не нашли ничего** (filtered=0) — все rerank-хиты отсечены фильтром.
- 🔴 **Hard-вопросы сломались** — recall 8% vs 57% (eval-improve), edge cases не решаются.

**Вердикт:** порог 0.25 **слишком агрессивен** для production.

**Рекомендации (CRITICAL):**
1. Понизить порог до 0.15–0.20 и перезапустить eval.
2. Добавить fallback: если filtered=0 → вернуть топ-1 из rerank независимо от скора.
3. Адаптивный порог по типу вопроса: easy/medium 0.22, hard 0.15.
4. Логировать `filtered` counts в production для калибровки.

**Проблемные вопросы (новые miss):**
- q-niche-06, q-niche-07, q-niche-21: filtered=0 или filtered=3, но не те блоки
- q-hard-02, q-hard-03, q-hard-06: filtered=0 или 1 — недостаточно для покрытия

**Успешные вопросы:**
- 17 из 29: recall 100%, precision 100% — фильтр оставил только нужное

## Как читать прогоны

### Основные метрики

- **Recall** — доля найденного из нужного. **Главная метрика:** показывает, насколько полно система находит ответ.
- **Precision** — доля правильного среди найденного. Измеряет шум: низкий precision → много лишнего в контексте.
- **Hit rate** — доля вопросов, по которым найдена хотя бы одна expected-часть. Грубый «попал/не попал».
- **MRR** (Mean Reciprocal Rank) — ранговая метрика: на какой позиции rerank первое правильное. 1.0 = на 1-м месте, 0.5 = на 2-м, 0.33 = на 3-м.
- **Perfect match** — вопрос решён полностью (recall ≥ 0.9). Счётчик идеальных решений.

### Разрезы

- **По сложности:** easy / medium / hard — показывает, где система справляется, а где проседает.
- **По группам:** niche / hard — нишевые вопросы vs edge cases.

### Counters

- `vector`, `fts` — кандидаты из каждого плеча поиска.
- `rrf` — кандидаты после слияния.
- `rerank` — хиты после переранжирования (обычно 5).
- `filtered` — хиты после фильтра (≤ rerank, **новое в retrievalFilters**).
- `groups` — группы блоков после expand.

### Интерпретация

- **Recall высокий, precision низкий** → система находит нужное, но тащит много шума. Токены расходуются неэффективно.
- **Recall низкий, precision высокий** → система уверена в найденном, но теряет часть ответа. LLM получает чистый, но неполный контекст.
- **Hit rate < 90%** → заметная доля вопросов не находит ничего релевантного. Проблема в search/rerank/фильтре.
- **MRR < 0.5** → правильное глубоко в выдаче (3-е место и ниже). Проблема в rerank-модели.

## Roadmap тестирования

### Следующие прогоны

1. **retrievalFilters-018** — порог 0.18 (vs текущий 0.25)
   - Цель: найти sweet spot между recall (≥80%) и precision (≥40%).
2. **retrievalFilters-fallback** — порог 0.25 + fallback (если filtered=0 → топ-1 из rerank)
   - Цель: устранить полные miss, сохранив высокий precision на остальных вопросах.
3. **queryDecomposition** — разбиение multi-fact вопросов на подзапросы
   - Цель: покрыть q-hard-02, q-hard-06, q-niche-04 (double-barrel, кросс-секционные).

### Калибровка порогов

- Собрать топ-1 скоры всех rerank-хитов из нескольких прогонов → построить гистограмму.
- Порог = percentile 10–15: отсекаем худшие 10–15%, сохраняем остальное.
- Цель: data-driven выбор порога, а не на глаз.

## Инструкция: как запустить eval

```bash
# Полный прогон всех 30 вопросов с сохранением JSON
npm run eval:json

# Ограничить количество вопросов (для быстрой проверки)
npm run eval:limit 5

# Только вывод в stdout, без JSON
npm run eval
```

**Требования:**
- `DATABASE_URL` — подключение к Postgres
- `EMBEDING_API_JINA` — ключ Jina для эмбеддингов
- `RERANKER_API_JINA` — ключ Jina для rerank (опционален, но без него rerank не работает)
- `ZAI_API_KEY` — ключ для классификатора ниши (опционален, но без него null-ниши падают)

**Результаты:**
- Вывод в stdout: агрегированные метрики + per-question детали
- JSON: `retrieval/eval/eval-results.json` (timestamp, aggregated, per-question results)

## Как добавить новый прогон

1. Запустить `npm run eval:json`.
2. Создать подпапку `fullEvalRun-DDMMYYYY-<причина>/` в `docs/eval/`.
3. Написать `README.md` в подпапке:
   - Контекст изменений
   - Агрегированные метрики
   - Сравнение с предыдущим прогоном
   - Детальный разбор проблемных вопросов
   - Выводы и рекомендации
4. Скопировать `retrieval/eval/eval-results.json` в подпапку.
5. Обновить этот README: добавить новый прогон в список и в сравнительную таблицу.
