# Требования к файлам для чанкования. Как добавить или улучшить файл и нарезать его заново

Этот документ — контракт между входным файлом и скриптом чанкования (`scripts/chunking/`, план 3 в `docs/plan/03-chunking-plan.md`). Если файл соответствует требованиям ниже — скрипт нарежет его без изменений кода. Если нет — скрипт упадёт с понятной ошибкой, а не выдаст мусор.

## 1. Требования к структуре входного файла

Файл — markdown, прошедший очистку по плану 2 (`docs/plan/02-text-cleanup-plan.md`). Грамматика заголовков:

| Элемент | Формат | Правило |
|---|---|---|
| Название документа | `# Название` | Ровно один на файл. Всё до первого H2 — преамбула |
| Ниша | `## N. НАЗВАНИЕ` | N от 1 до 10. Меняет текущую нишу |
| Подгруппа (основная группа) | `## N.M. НАЗВАНИЕ` | Ровно 8 на нишу: `N.1`–`N.8`. Чанкование идёт внутри них |
| Сквозной раздел | `## 0. …`, `## 11. …` | Секции без дочерних блоков: тело целиком = один блок-чанк |
| Регуляторика | `## B0. …`, `## B0.M. …` | Сквозная группа `B0` с дочерними секциями `B0.1`–`B0.6` |
| Смысловой блок | `## ЗАГОЛОВОК` внутри текущей `N.M` | Кейс, SOP, лист финмодели, чек-лист и т.п. Один блок = основа одного чанка |
| Подзаголовки | `### …` | Границами **не являются**, остаются внутри блока |

Требования к содержимому:

1. **Нумерация сквозная и непрерывная**: ниши идут по порядку 1→10, внутри ниши подгруппы `N.1`→`N.8`. Пропуски и дубли кодов недопустимы — валидатор проверяет структуру «10 ниш × 8 подгрупп».
2. **Таблицы** — markdown с шапкой и строкой-разделителем `|---|`. Таблица без шапки бессмысленна после нарезки: шапка повторяется в каждом куске.
3. **Кейсы** живут только в подгруппе `N.2`. Служебные (не кейсовые) заголовки `N.2` — фиксированный список в конфиге скрипта: `Рыночный фон`, `Примеры смены стратегии (pivot)`, `Типовые сценарии закрытия в первые 6–12 месяцев`. Новый служебный заголовок → добавить в конфиг вручную после проверки, скрипт сам не угадывает.
4. **SOP** — заголовок вида `## SOP N. Текст`, только в подгруппе `N.6`. Чек-листы — слово «Чек-лист» в заголовке блока, тоже в `N.6`.
5. **Перекрёстные ссылки** на разделы — фразами «см. раздел X» / «раздел X», где X — код из белого списка: `0`, `11`, `B0`, `B0.1`–`B0.6`. Ссылки вне белого списка игнорируются.
6. **Никакого мусора очистки**: HTML-сущностей, разметки не-markdown, оглавления-дубля, пустых таблиц.

## 2. Как добавить новый файл на чанкование

1. Прогнать файл через очистку (план 2) — на чанкование попадает только очищенный файл.
2. Проверить файл по разделу 1 этого документа (грамматика заголовков, нумерация, таблицы).
3. Если в файле новые ниши — дописать маппинг в конфиг: номер ниши → slug папки и `business_type` (например, `1 → coffee / coffee_shop`). Существующие ниши трогать не нужно.
4. Запустить нарезку: `npm run chunk`. Результат — дерево папок в `data/chunks/` + отчёт `data/chunking-report.md`.
5. Запустить валидатор: `npm run chunk:validate`. Зелёные проверки обязательны.
6. Просмотреть 10–15 случайных чанков глазами (кейс, кусок таблицы, родительский чанк). Правки — руками в JSON-файлах, затем снова `chunk:validate`.
7. Загрузка в БД — вручную и отдельно: `npm run chunk:load` (сначала `--dry-run`, потом `--apply`). Скрипт читает `DATABASE_URL` из `.env`.

## 3. Как улучшить существующий файл и нарезать заново

Два сценария.

**Точечная правка текста** (сформулировать абзац, поправить цифру) — правьте сразу JSON-файл чанка в `data/chunks/`: быстрее, чем перерезать весь документ. После правки — `npm run chunk:validate`. Поля `line_start`/`line_end` информационные, на них валидатор в этом случае не падает.

**Содержательное изменение документа** (новая ниша, новые блоки, переработка раздела) — правьте исходный markdown и запускайте полный цикл из раздела 2. Полный прогон **перезаписывает** `data/chunks/` целиком — ручные правки старого дерева будут потеряны, это ожидаемо.

Версионирование:

- Поле `source_id` в конфиге — версия документа (по дате актуальности, например `busiverse-2026-10-13`). При существенной переработке документа обновите дату — новая нарезка получит новый `source_id`.
- Загрузка в БД идемпотентна: строки с тем же `(source_id, chunk_id)` обновляются, дубликатов не появляется. Строки с другим `source_id` — отдельная версия; замену старой версии в БД решает тот, кто запускает `chunk:load --apply`.

## 4. Что гарантирует скрипт, а что проверяет человек

| Гарантирует скрипт (валидатор) | Проверяет человек |
|---|---|
| Ни один заголовок не потерян и не классифицирован дважды | Осмысленность границ чанков (глазами по папкам) |
| Каждая строка файла внутри ровно одного чанка | Качество дробления крупных таблиц и прозы |
| Структура «10 ниш × 8 подгрупп» + сквозные разделы | Полнота служебного списка заголовков `N.2` |
| Бюджет 500–700 токенов (исключения — только кейсы/SOP/чек-листы) | Корректность правок текста в JSON |
| Шапка в каждом куске таблицы, уникальность id, целостность родителей | Решение о запуске `chunk:load --apply` |

Скрипт универсален ровно настолько, насколько файл следует конвенциям раздела 1. Новый файл того же формата — без изменений кода (кроме, возможно, одной строки маппинга ниш в конфиге).
