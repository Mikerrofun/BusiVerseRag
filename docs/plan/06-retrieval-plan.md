# План 6. Retrieval-система BusiVerse

## 0. О чём этот план

Собрать **переносимую retrieval-систему**: на вход — запрос пользователя, на выход — собранный контекст (чанки + родители + ссылки + метаданные), готовый к подстановке в промпт модели.

**Что это и что это не есть:**

- Это **система сбора информации**, а не ассистент. Модель-генератор сюда не подключается. Единственный вызов LLM внутри системы — классификатор ниши (он часть конвейера).
- Система живёт в **отдельной папке** этого репозитория и спроектирована так, чтобы позже целиком переехать в основной проект (сайт) и вызываться оттуда по API. Поэтому: строгая структура по FSD, вся типизация в файлах типов, все настройки в конфигах, публичный API — одна точка входа.
- Чанки в БД уже есть (443 шт., эмбеддинги проставлены). Ингест, чанкинг, эмбеддинг-прогон — сделаны ранее, этот план их не трогает.

**Кто и как выполняет план.** План отдаётся агенту. Агент пишет код и по завершении проверяет его **только** типизацией (`npx tsc --noEmit`). Никаких запусков пайплайна, обращений к БД и внешним API агент не делает — финальную проверку «запрос → контекст» выполняет владелец вручную через CLI-скрипт (задача 8) и потом полностью рефакторит код.

**Не входит в этот план (осознанно отложено):**

| Что | Почему |
|---|---|
| Eval-раннер | Владелец реализует отдельно позже (план 05 остаётся в силе) |
| Документация | Владелец напишет её после своего рефакторинга |
| Region-фильтр | Поля `region` в БД нет; Москва/регион — разные блоки, их находит сам поиск. Вернуться можно добавлением одной колонки + одного фильтра |
| `topics` | Поле в БД есть, но остаётся пустым; на поиск не влияет. Подключается позже без изменения архитектуры |
| Подключение основной модели, стриминг | Забота проекта ассистента |

## 2. Фиксированные решения

| Что | Решение |
|---|---|
| Расположение | Отдельная папка `retrieval/` в корне репозитория, структура по FSD |
| Доступ к БД | Прямой SQL через `@neondatabase/serverless` Pool. Без ORM |
| Эмбеддинги запроса | Jina `jina-embeddings-v5-omni-small`, 1024, `normalized: true`, `task: retrieval.query` |
| Reranker | Jina `jina-reranker-v3.5` |
| Классификатор ниши | `glm-5.3-flash` через z.ai, reasoning `low`, маленький контекст, ответ — JSON |
| Основная модель | Не подключается. Коннектор к GLM пишется один — его же позже переиспользует ассистент |
| Числа конвейера | vector top-40 + FTS top-40 → RRF (k=60) → top-20 → rerank → top-8 → small-to-big + ссылки → контекст |
| Токен-бюджет контекста | 12 000 токенов, конфигурируемый |
| Порог классификатора | 0.6; ниже — поиск без фильтра по всему корпусу |
| Переменные окружения | `DATABASE_URL`, `EMBEDING_API_JINA` (эмбеддинги + rerank, ключ один), `RERANKER_API_JINA` (опциональный override), `ZAI_API_KEY` |
| Зависимости | Никаких новых. Нужное уже есть: `@neondatabase/serverless`, `dotenv`, `js-tiktoken` (подсчёт токенов для бюджета) |
| FTS | Встроенная конфигурация `russian`, разбор запроса через `websearch_to_tsquery` + префикс-матчинг для окончаний |
| Region, topics | Не входят в v1 (см. раздел 0) |

## 3. Архитектура папки

Структура по FSD-принципу: слои изолированы, зависимости направлены вниз (оркестратор → lib → config/types). Логика — только в `lib/`, настройки — только в `config/`, типы — только в `types/`. Снаружи папка видна через единственную точку входа.

```
retrieval/
  index.ts                  # публичный API: единственная функция retrieve(query, options) → RetrievalResult
  run.ts                    # CLI-точка входа для ручной проверки (npm run retrieve)
  config/
    retrieval.config.ts     # числа конвейера: top-k, RRF k, порог классификатора, токен-бюджет
    models.config.ts        # URL и имена моделей, названия env-переменных, размеры батчей, паузы
    niches.config.ts        # словарь ниш: код → список ключевых слов для fulltext-пробы
  types/
    retrieval.types.ts      # все типы системы: вход, выход, чанк, скоринг, классификация
  lib/
    db.ts                   # подключение к Neon (по паттерну db/config), SQL-запросы поиска
    embed-query.ts          # эмбеддинг запроса через Jina (task: retrieval.query)
    fts.ts                  # полнотекстовый поиск: разбор запроса, ранжирование
    vector-search.ts        # векторный поиск: cosine distance по HNSW
    rrf.ts                  # слияние двух ранжирований
    rerank.ts               # переранжирование через jina-reranker-v3.5
    classifier.ts           # определение ниши: fulltext-проба → LLM-классификатор
    llm-client.ts           # коннектор к GLM по паттерну embed.ts (переиспользуется ассистентом позже)
    expand.ts               # small-to-big: родители, соседние куски, chunk_links
    assemble.ts             # сборка финального контекста: порядок, заголовки, дедуп, токен-бюджет
    pipeline.ts             # оркестратор: связывает все шаги в порядке конвейера
```

**Правила структуры (жёсткие):**

1. Типы не живут в файлах логики. Любой интерфейс/тип — в `types/retrieval.types.ts`. Файлы `lib/` импортируют типы оттуда.
2. Константы и настройки не живут в файлах логики. Любое число, URL, имя модели, имя env-переменной — в `config/`. Файлы `lib/` импортируют значения оттуда.
3. `lib/`-модули не импортируют друг друга поперёк, где это можно избежать: оркестратор (`pipeline.ts`) знает порядок шагов, шаги знают только свои входы/выходы из типов.
4. Наружу торчит только `index.ts`. Будущий основной проект импортирует одну функцию — и это весь контракт.
5. Комментарии в коде — только там, где решение неочевидно с первого взгляда (почему RRF k=60, почему override ключа, почему дедуп именно тут). Комментарий на каждую строку — запрещён.

## 4. Контракт системы

**Вход** (объект):

- `query` — текст запроса пользователя, непустая строка.
- `niche` — опционально, код ниши из селектора UI (`coffee_shop`, `pickup_point`, … — полный список в `config/niches.config.ts`). Если передана — классификатор не вызывается вообще.

**Выход** (объект `RetrievalResult`) — ровно то, что будущий ассистент положит в промпт:

- `context` — готовый текстовый блок для подстановки в промпт: чанки с заголовками-источниками, в стабильном порядке.
- `chunks` — структурированный список использованных чанков: `chunk_id`, `heading_path`, `section_title`, `block_title`, `chunk_type`, `score` (после rerank), признак «родитель/кусок/ссылка».
- `meta` — служебное: определённая ниша и способ её определения (`ui` / `fulltext-probe` / `llm` / `none`), уверенность классификатора, счётчики по этапам (сколько нашёл vector, FTS, после RRF, после rerank, сколько вошло в контекст), флаг обрезки по токен-бюджету.

Контракт фиксируется типами в `types/retrieval.types.ts`. Поле `meta` обязательно — без него владелец не сможет вручную проверять систему и позже настраивать eval-раннер.

## 5. Конвейер — флоу по шагам

Единый порядок шагов, реализуемый в `pipeline.ts`. Ниже — что делает каждый шаг и на что ссылаться.

**Шаг 1. Валидация входа.** Пустой/непустой `query`, опциональный `niche` сверяется со списком кодов из `config/niches.config.ts`. Невалидный вход — понятная ошибка, не падение.

**Шаг 2. Определение ниши** (`lib/classifier.ts`). Три уровня, по возрастанию стоимости:

1. Ниша передана на входе → используем, метка `ui`.
2. **Fulltext-проба.** Запрос сверяется со словарём ключевых слов ниш из `config/niches.config.ts` (по одному-два слова на нишу: «кофейня», «ПВЗ», «пекарня», «маникюр», «автосервис», «селлер/маркетплейс», «онлайн-школа», «SMM», «интернет-магазин», «бухгалтерия»). Ровно одна ниша совпала → используем её, метка `fulltext-probe`, LLM не вызывается. Совпало несколько или ни одной → уровень 3.
3. **LLM-классификатор.** Вызов `glm-5.3-flash` (reasoning `low`) через `lib/llm-client.ts`: в системном промпте — список 10 ниш с короткими описаниями, на выходе требуется строго JSON `{"niche": "<код>", "confidence": <0..1>}`. Ответ парсится, мусорный ответ = «ниша не определена». Уверенность ≥ 0.6 → фильтр по нише, метка `llm`. Ниже порога или парсинг не удался → **поиск без фильтра по всему корпусу**, метка `none`. Лучше отдать чанки из нескольких ниш, чем отфильтровать правильную.

**Шаг 3. Эмбеддинг запроса** (`lib/embed-query.ts`). Текст запроса → Jina, модель и размерность из `config/models.config.ts`, `task: retrieval.query`, `normalized: true`. Вектор нормализован — сходство считается скалярным произведением / косинусом, как при ингесте. Ссылка на паттерн: `scripts/embeddings/embed.ts`, функция `fetchEmbeddings` — тот же URL, та же обработка ошибок и `withRetry`, отличие только в `task`.

**Шаг 4. Два поиска параллельно** (`lib/vector-search.ts`, `lib/fts.ts`). Оба с одним фильтром: `WHERE business_type = $1 OR scope = 'global'` (если ниша не определена — фильтра нет). Каждый возвращает до 40 чанков; если нашлось меньше — как есть, это не ошибка.

- **Vector:** сортировка по `embedding <=> $вектор` (косинусное расстояние), индекс HNSW уже построен. В SQL выбираются и текст, и все метаполя, нужные контракту (см. `docs/db/schema.md`).
- **FTS:** `tsv @@ websearch_to_tsquery('russian', ...)` с префикс-матчингом (окончания: «кофейн*» найдёт «кофейни», «кофейням»). Ранжирование через `ts_rank`. Префиксация терминов запроса делается на стороне приложения перед передачей в запрос — в конфиге задаётся, какие термины префиксовать (все, кроме чисел и латиницы-артикулов вроде «152-ФЗ»).

**Шаг 5. RRF** (`lib/rrf.ts`). Слияние двух списков: `score = Σ 1/(60 + rank)` по каждому списку, где rank начинается с 1. Константа 60 — в конфиг. На выходе единый список до 20 чанков, отсортированный по суммарному скору. Дубликаты (чанк найден обоими поисками) сливаются с суммированием вклада — в этом смысл RRF.

**Шаг 6. Rerank** (`lib/rerank.ts`). Топ-20 после RRF уходит в Jina `jina-reranker-v3.5`: документы — тексты чанков, query — исходный запрос. На выходе — переупорядоченный список с relevance-скорами; берём топ-8 (конфиг). Ошибка API rerank'а не роняет пайплайн: логируем и продолжаем с RRF-порядком — поиск хуже, но рабочий.

**Шаг 7. Small-to-big, всегда** (`lib/expand.ts`). Для каждого из топ-8:

1. **Родительская секция.** У блочного чанка есть `parent_id` — подтягивается чанк-секция (он компактный, ~300–500 токенов, см. план 01 раздел 3.7).
2. **Соседние куски дроблёного блока.** Если чанк — кусок (`-pN`), докатываются все куски его блока: один запрос по `parent_id` с сортировкой по `part_index` (см. `docs/feature/chunking-pipeline.md`, раздел про id). Куски склеиваются конкатенацией `text` по порядку — шапка таблицы в каждом куске уже есть.
3. **Дедуп.** Если несколько хитов указывают на один и тот же блок/родителя — блок и родитель включаются один раз. Это обязательный шаг: без него 8 хитов из одной секции раздуют контекст восьмью копиями родителя.

**Шаг 8. Ссылки, всегда** (`lib/expand.ts`, продолжение). Для каждого вошедшего чанка берутся его записи из `chunk_links` (`to_section`), и подтягивается чанк-секция с `section_code = to_section` (приоритет: та же ниша; если секция сквозная — `scope = 'global'`). Дедуп по `chunk_id`. Сейчас все ссылки ведут на B0 — поведение простое и детерминированное.

**Шаг 9. Сборка контекста** (`lib/assemble.ts`).

1. Порядок блоков — по убыванию rerank-скора лучшего хита блока (самое релевантное — первым).
2. Каждый блок предваряется заголовком-источником из `heading_path` (ниша → секция → блок) — модель видит, откуда данные, а ассистент позже сможет строить цитаты.
3. Подсчёт токенов через `js-tiktoken`. Бюджет 12 000 (конфиг): блоки добавляются, пока влезают; не влезающий блок целиком пропускается, в `meta` ставится флаг обрезки. Хиты одного блока не разрезаются посреди — атомарность блока важнее точного попадания в бюджет.
4. Родители и ссылки помечаются в тексте контекста соответствующим маркером (например, «Контекст секции:», «Связанный раздел:») — чтобы модель отличала основной хит от фонового материала.

**Шаг 10. Возврат `RetrievalResult`** — контракт из раздела 4.

## 6. Задачи

Порядок жёсткий. В задачах — флоу и ссылки, не код.

### Задача 1. Каркас папки `retrieval/`

Создать структуру из раздела 3: `config/` (три файла-конфига с содержимым из разделов 2 и 5), `types/retrieval.types.ts` (все типы контракта из раздела 4 плюс внутренние типы шагов), `lib/db.ts` (подключение по паттерну `db/config/index.ts` + dotenv-загрузка из `scripts/embeddings/embed.ts`), пустые `index.ts` и `run.ts`.

- Ссылки: `scripts/embeddings/embed.ts` (dotenv-блок), `db/config/index.ts`, `docs/db/schema.md` (поля для типов).
- В `config/niches.config.ts` — 10 кодов ниш из плана 01 раздел 2.2 + по 1–3 ключевых слова на нишу для fulltext-пробы.
- **Готово, когда:** структура существует, типы покрывают весь контракт раздела 4, `npx tsc --noEmit` чистый.

### Задача 2. Коннекторы к внешним API

Три модуля в `lib/`, каждый — по паттерну `scripts/embeddings/embed.ts` (конфиг + типы + `withRetry` + явная ошибка с телом ответа при не-2xx):

1. `embed-query.ts` — тот же вызов Jina, что в embed.ts, но `task: retrieval.query` и один вход (запрос), не батч.
2. `rerank.ts` — вызов Jina reranker: `model`, `query`, `documents`, чтение `results` (индекс + score), восстановление порядка по индексам (Jina может вернуть не по порядку — как с эмбеддингами в embed.ts).
3. `llm-client.ts` — вызов chat-completions z.ai: URL и модель из `config/models.config.ts`, ключ из `ZAI_API_KEY`, параметр reasoning-уровня из конфига (`low` для классификатора). Формат параметра reasoning сверить с актуальной документацией z.ai при реализации. Клиент универсальный: принимает системный промпт и пользовательское сообщение, возвращает текст — его позже переиспользует ассистент.

- **Готово, когда:** три модуля компилируются, ключи берутся только из env через конфиг, `npx tsc --noEmit` чистый.

### Задача 3. Два поиска + RRF

`lib/vector-search.ts`, `lib/fts.ts`, `lib/rrf.ts` по флоу шагов 4–5. SQL-запросы — параметризованные, фильтр ниши опциональный (одна и та же функция поиска работает с фильтром и без). В выборке — все поля контракта. Префиксация FTS-терминов — по правилу из шага 4.

- Ссылки: `docs/db/schema.md` (индексы), план 01 раздел 7 (обоснование гибрида и RRF).
- **Готово, когда:** функции чистые (вход → список чанков со скорами), RRF сливает два списка без дубликатов, `npx tsc --noEmit` чистый.

### Задача 4. Классификатор ниши

`lib/classifier.ts` по флоу шага 2: переданная ниша → fulltext-проба по `config/niches.config.ts` → LLM через `lib/llm-client.ts` с JSON-ответом и порогом из конфига. Промпт классификатора хранится в `config/` (это настройка, не логика). Мусорный/непарсящийся ответ трактуется как «не определено».

- **Готово, когда:** все четыре исхода покрыты (`ui` / `fulltext-probe` / `llm` / `none`), ни один путь не вызывает LLM лишний раз, `npx tsc --noEmit` чистый.

### Задача 5. Small-to-big + ссылки

## 7. Ручная проверка владельца (не задача агента)

После рефакторинга владелец проверяет системой CLI:

```bash
npm run retrieve -- "Какая выручка у кофейни в Москве?"
npm run retrieve -- "Какие лимиты у НПД в 2026 году?" --json
npm run retrieve -- "Сколько стоит открыть точку?"          # без ниши → классификатор
```

Ожидания: контекст содержит правильные секции (финмодель кофейни; раздел 0; несколько ниш при неопределённой классификации), `meta` показывает путь определения ниши и счётчики этапов, обрезка по бюджету работает на «жирных» запросах.
