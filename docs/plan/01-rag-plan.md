# План 1. RAG-система BusiVerse

## 0. О чём этот план

Как из одного markdown-файла получить работающий поиск по базе знаний для ИИ-ассистента на сайте.

**Порядок работ жёсткий:**

```
1. Очистить текст        → отдельный план: 02-text-cleanup-plan.md
2. Спроектировать БД     → раздел 5 этого плана
3. Нарезать на чанки     → раздел 3 этого плана
4. Собрать eval-набор    → раздел 8
5. Выбрать модель        → раздел 6
6. Посчитать эмбеддинги  → раздел 6
7. Собрать retrieval     → раздел 7
8. Ингестить xlsx        → разделы 2.6 и 3.9
```

Очистка текста **не входит в пайплайн**. Это подготовительный этап: он делается один раз руками и глазами, а не выполняется при каждом ре-ингесте. Поэтому он вынесен в отдельный план.

**Почему eval раньше эмбеддингов.** Модель эмбеддингов выбирается по метрикам, а метрики нельзя посчитать без набора вопросов. Поэтому eval-набор собирается до того, как размерность вектора зафиксирована в схеме БД.

## 1. Фиксированные решения

| Что | Решение |
|---|---|
| Хранилище | Neon Postgres + pgvector |
| Нарезка | Структурная: дерево заголовков + добор по размеру |
| Эмбеддинги | Провайдер по API-ключу. Модель выбирается позже, по метрикам eval. Размерность фиксируется при проектировании БД |
| Reranker | Любой рабочий. На схему БД не влияет, выбирается позже |
| Поиск | Фильтр → vector + full-text → RRF → rerank |
| Источник правды | `RAG-документация_BusiVerse.md` + `financial_models_10_niches.xlsx` |
| Очищенный текст | пишем в тот же файл, дубликат не нужен |
| Эмбеддинги в git | нет, только в БД |
| Ассистент | Отдельный проект, читает ту же Neon-базу. Схема БД — контракт между репозиториями |
| Выбор ниши | Селектор в UI + классификатор как fallback |

### 2.6 Второй источник: xlsx

В строке 3 документ ссылается на приложение — `financial_models_10_niches.xlsx`. Дисклеймер «цифры раздела совпадают с файлом financial_models_10_niches.xlsx» повторяется 10 раз, по одному в каждой нише. Самого файла в репозитории нет.

**Что в нём.** Лист «Сводка» плюс 13 листов по нишам. У кофейни, мини-пекарни и маникюрной студии — отдельные варианты «Москва» и «регион», отсюда 13 вместо 10. На каждом листе: стартовые вложения (CapEx), ежемесячные расходы, три сценария выручки, окупаемость, точка безубыточности, движение денег на 24 месяца.

**Зачем ингестить.** В markdown эти цифры уже есть, но только как снимок при исходных допущениях. xlsx — это пересчитываемая модель. Без него ассистент не ответит на «а если средний чек будет 300 ₽ вместо 250?». С ним — сможет, если добавить инструмент пересчёта.

**Как ингестить.** Каждый лист → один чанк типа `table` с `business_type` из имени листа и `scope = "business"`. Лист «Сводка» → `scope = "global"`. Плюс отдельный чанк-описание структуры модели: какие входные допущения есть и что можно пересчитывать.

**Важно.** xlsx не заменяет markdown, а дополняет его. Если цифры разойдутся, источником правды остаётся markdown — он версионируется в git и проходит очистку. Расхождение — это сигнал, что файл устарел, а не повод переписать markdown.

## 3. Алгоритм нарезки на чанки

Это главный раздел. Ниже — как именно документ превращается в чанки.

### 3.1 Идея

Документ уже размечен заголовками. Не надо угадывать границы — надо прочитать структуру и разрезать по ней. Это называется **структурный чанкинг**.

Правило простое:

> **Один смысловой блок = один чанк.**
> Смысловой блок — это либо нумерованный раздел `N.M`, либо заголовок H2 внутри него.

### 3.2 Два уровня

Получается два уровня чанков:

| Уровень | Что это | Роль |
|---|---|---|
| **Секция** | `## N.M. Название` | Родитель. В поиске не участвует, отдаётся в LLM как контекст |
| **Блок** | любой H2 внутри секции | Ребёнок. Именно он индексируется и ищется |

Это схема **small-to-big**: ищем по мелким блокам, а в модель отдаём родительскую секцию, если нужен контекст.

### 3.3 Как строится дерево

Идём по файлу сверху вниз и ведём указатель на «текущую секцию»:

1. Встретили H2 вида `## 1.3. Финансовая модель` → это **новая секция**. Запоминаем её как текущую.
2. Встретили H2 вида `## 1. ОФЛАЙН — КОФЕЙНЯ` → это **новая ниша**. Меняем `business_type`.
3. Встретили H2 вида `## B0.2. Маркировка интернет-рекламы` → это **сквозная секция**. `scope = global`.
4. Встретили любой другой H2 (`## Лист «Кофейня (Москва)»`, `## SOP 1. Открытие смены`, `## Coffee Bull — Барнаул`) → это **блок внутри текущей секции**.
5. Всё, что идёт до первого H2 внутри блока, — тело блока.

Ключевой момен��: **уровень заголовка не важен, важен шаблон нумерации.** `## 1.3.` — секция, `## Лист «Кофейня (Москва)»` — блок, хотя оба H2.

### 3.4 Пример на реальном куске

Вот как выглядит ниша 1, секция `1.3` (строки 207–327):

```
## 1.3. Финансовая модель          ← СЕКЦИЯ (родитель)
## Лист «Кофейня (Москва)»        ← БЛОК → чанк типа table
|Параметр|Значение| ...
## Лист «Кофейня (регион)»        ← БЛОК → чанк типа table
|Параметр|Значение| ...
## Скрытые расходы                ← БЛОК → чанк типа prose
## Отраслевые бенчмарки           ← БЛОК → чанк типа table
|Показатель|Значение| ...
```

На выходе — 4 чанка-блока с `parent_id = "coffee_shop-1.3"` и 1 чанк-секция.

А вот секция `1.2` (кейсы, строки 52–206):

```
## 1.2. Кейсы                      ← СЕКЦИЯ
## Coffee Bull — Барнаул          ← БЛОК → чанк типа case
## Setterʼs — Ростов-на-Дону      ← БЛОК → чанк типа case
## Follow to feel — Люберцы       ← БЛОК → чанк типа case
## «Ароматный дом» — Новосибирск  ← БЛОК → чанк типа case
## Семейные кофейни «Мами» — Пермь ← БЛОК → чанк типа case
## Рыночный фон                   ← БЛОК → чанк типа prose
## Примеры смены стратегии (pivot) ← БЛОК → чанк типа table
## Закрытия в первые 6–12 месяцев  ← БЛОК → чанк типа prose
```

На выходе — 8 чанков-блоков. Каждый кейс целиком, не разрезанный.

### 3.5 Правила по типам блоков

| `chunk_type` | Где встречается | Правило |
|---|---|---|
| `case` | `N.2`, заголовки с названием компании | Один кейс = один чанк. **Никогда не резать** |
| `sop` | `N.6`, заголовки `SOP N.` | Один SOP = один чанк. **Никогда не резать** |
| `table` | `N.3`, `N.4`, `N.5`, `N.8` | Таблица атомарна. Резать только если не влезает в бюджет |
| `checklist` | `N.6`, `Чек-лист сотрудника` | Список целиком |
| `prose` | `N.1`, `N.7`, `Рыночный фон`, `Скрытые расходы` | Группы абзацев, перекрытие 15% |

### 3.6 Что делать с большими блоками

Бюджет чанка: **500–700 токенов**. Если блок больше:

**Для таблиц.** Режем по группам строк, но **в каждом куске повторяем шапку**. Иначе кусок без шапки бессмысленен.

```
Кусок 1: |Роль|Оклад|...|   ← шапка
         |Бариста|...|
         |Управляющий|...|

Кусок 2: |Роль|Оклад|...|   ← та же шапка
         |Смена|...|
         |Курьер|...|
```

**Для прозы.** Режем по границам абзацев, перекрытие 15% (последний абзац куска попадает и в следующий). Перекрытие нужно, чтобы мысль, разорванная границей, нашлась из обеих половин.

**Для кейсов и SOP — не режем вообще.** Если кейс на 1200 токенов, он остаётся одним чанком. Разрезанный кейс теряет смысл: вывод в конце, а причина в начале.

### 3.7 Что попадает в чанк-секцию

Родительский чанк — это не весь текст секции (он может быть 12K символов). Это:

1. Текст, который идёт прямо под `## N.M` до первого дочернего H2 (обычно 1–3 абзаца введения).
2. Плюс список названий дочерних блоков — чтобы модель понимала, что внутри.

Так родитель остаётся компактным (~300–500 токенов) и при этом даёт контекст.

### 3.8 Итоговые числа

| Что | Сколько |
|---|---|
| Секций `N.M` | 79 (10 ниш × 8, минус пропавший `4.2`) |
| Сквозных секций | 8 (`0`, `B0`, `B0.1`–`B0.6`, `11`) |
| Блоков внутри секций | ~190 |
| **Чанков-блоков** | **~270** |
| Дробление крупных блоков | +100–150 |
| **Чанков-секций** | **~87** |
| **Итого записей** | **~500–600** |

Это очень мало. Весь корпус влезает в pgvector с гигантским запасом, и это позволяет не экономить на качестве.

### 3.9 Нарезка xlsx

Для xlsx правило другое: там нет заголовков, есть листы и ячейки.

| Что | Как режем |
|---|---|
| Лист «Сводка» | Один чанк. Сравнение всех ниш по CapEx, окупаемости, точке безубыточности |
| Лист ниши | Один чанк на лист. `business_type` из имени листа |
| Варианты «Москва» / «регион» | Отдельные чанки, различаются полем `region` |
| Блок входных допущений | Отдельный чанк — это то, что нужно для пересчёта |
| Движение денег на 24 месяца | Отдельный чанк типа `table`, если не влезает в бюджет |

Дополнительное поле метаданных для xlsx-чанков: `region` (`moscow` / `region` / `null`). В markdown-чанках его тоже стоит заполнить — в документе есть отдельные листы «Кофейня (Москва)» и «Кофейня (регион)».

## 4. Обогащение метаданных

После нарезки каждый чанк получает метаданные.

| Поле | Откуда берётся |
|---|---|
| `business_type` | Из номера ниши. `1` → `coffee_shop` |
| `block` | `offline` для ниш 1–5, `online` для 6–10, `global` для сквозных |
| `section_code` | `1.3`, `B0.2`, `0`, `11` |
| `section_title` | Заголовок секции |
| `block_title` | Заголовок блока внутри секции |
| `heading_path` | Массив: `["1. ОФЛАЙН — КОФЕЙНЯ", "1.3. Финансовая модель", "Лист «Кофейня (Москва)»"]` |
| `chunk_type` | По правилам из 3.5 |
| `scope` | `global` для `0`, `B0`, `11`; иначе `business` |
| `topics` | Из содержания: частотные термины + LLM-нормализация |
| `parent_id` | `coffee_shop-1.3` |
| `chunk_index` | Порядковый номер внутри секции |
| `line_start` / `line_end` | Номера строк в исходном файле |
| `token_count` | Считается при нарезке |
| `region` | `moscow` / `region` / `null` — из заголовка листа или имени листа xlsx |
| `content_hash` | sha256 текста, для идемпотентного ре-ингеста |

**Почему `heading_path` обязателен.** Без него нельзя показать пользователю «Источник: Кофейня → Финансовая модель → Лист «Кофейня (Москва)»» и нельзя дать модели понять, о чём чанк. Это самый ценный метафилд.

**Почему `section_code` надёжнее заголовка.** Заголовки в документе дрейфуют: `Типовые сценарии закрытия в первые 6–12 месяцев` встречается 8 раз, а `Закрытия в первые 6–12 месяцев работы` — 2 раза. Это один и тот же подраздел. Номер `N.M` стабилен, текст заголовка — нет.

## 5. Схема БД

```sql
create extension if not exists vector;

create table sources (
  source_id     text primary key,
  title         text not null,
  doc_version   text not null,
  valid_from    date not null,
  content_hash  text not null
);

create table chunks (
  chunk_id      text primary key,
  source_id     text not null references sources(source_id),
  business_type text not null,
  block         text not null,
  section_code  text,
  section_title text,
  block_title   text,
  heading_path  text[] not null default '{}',
  chunk_type    text not null,
  topics        text[] not null default '{}',
  scope         text not null default 'business',
  parent_id     text,
  chunk_index   int  not null default 0,
  line_start    int,
  line_end      int,
  token_count   int  not null,
  text          text not null,
  content_hash  text not null,
  tsv           tsvector generated always as (to_tsvector('russian', text)) stored,
  embedding     vector(1024)
);

create index chunks_embedding_idx on chunks using hnsw (embedding vector_cosine_ops);
create index chunks_tsv_idx       on chunks using gin (tsv);
create index chunks_filter_idx    on chunks (business_type, section_code);
create index chunks_scope_idx     on chunks (scope);
create index chunks_parent_idx    on chunks (parent_id);
```

**Отдельная таблица для внутренних ссылок.** В документе есть ссылки «см. раздел B0». Их надо разрешать при поиске:

```sql
create table chunk_links (
  from_chunk_id text not null references chunks(chunk_id),
  to_section    text not null,
  primary key (from_chunk_id, to_section)
);
```

Postgres имеет встроенную конфигурацию `russian` — полнотекстовый поиск по русскому работает из коробки, без внешних сервисов.

### 5.1 Размерность вектора — решение, которое надо принять здесь

`vector(1024)` в схеме выше — заглушка. Реальная размерность зависит от модели эмбеддингов, а модель ты решишь позже. Это единственное место, где выбор модели протекает в схему БД.

Что важно знать:

- **Размерность фиксируется в DDL.** `vector(N)` — не переменная. Сменить модель на другую размерность = `ALTER TABLE` + переэмбеддить всё.
- **Переэмбеддить дёшево.** У нас ~600 чанков. Это минуты и копейки. Так что ошибиться не страшно.
- **Matryoshka-модели дают свободу.** Если модель поддерживает усечение (например, 2048 → 1024 → 512), можно зафиксировать 1024 и позже урезать без смены схемы.
- **HNSW-индекс перестраивается** при смене размерности. На 600 записях это мгновенно.

**Рекомендация:** зафиксировать `vector(1024)` — это самая распространённая размерность, её поддерживают почти все современные модели, и она не мешает ничему. Если позже выбранная модель окажется 768 или 1536 — переделать схему на 600 чанках займёт минуты.

### 5.2 Контракт с проектом ассистента

Ассистент живёт в отдельном проекте и читает ту же Neon-базу. Значит схема БД — это контракт между двумя репозиториями, и его надо зафиксировать явно.

**Что должен знать проект ассистента:**

| Что | Значение |
|---|---|
| Таблицы для чтения | `chunks`, `sources`, `chunk_links` |
| Поля для фильтра | `business_type`, `scope`, `region`, `section_code` |
| Поле для векторного поиска | `embedding` |
| Поле для полнотекстового поиска | `tsv` |
| Поля для цитат | `heading_path`, `section_title`, `block_title`, `line_start`, `line_end` |
| Модель эмбеддингов | Должна совпадать с той, что использовалась при ингесте. Иначе поиск не работает |

**Главный риск контракта.** Модель эмбеддингов для запроса и для чанков должна быть одна и та же. Если проект ассистента возьмёт другую модель, векторный поиск вернёт мусор без единой ошибки в логах. Это надо записать в README обоих проектов.

**Как передавать контракт.** Варианты:

1. **Общая миграция в отдельном репозитории.** Схема живёт в третьем месте, оба проекта её применяют. Чисто, но лишний репозиторий.
2. **Этот репозиторий владеет схемой.** Миграции лежат здесь, проект ассистента только читает. Проще всего, и логично: база знаний — источник правды.
3. **Drizzle-схема как npm-пакет.** Типы шарятся между проектами. Удобно, но нужен приватный реестр.

**Рекомендация:** вариант 2. Миграции в этом репозитории, проект ассистента читает. Если позже понадобятся общие типы — вынести в пакет.

## 6. Эмбеддинги

Модель выбирается позже. Провайдер — по API-ключу. Ниже — требования к модели и то, что не зависит от выбора.

### 6.1 Требования к модели

| Требование | Почему |
|---|---|
| Русский язык | Весь корпус на русском, включая юридическую и налоговую лексику |
| Размерность 1024 или усекаемая до неё | Чтобы не менять схему БД |
| Разделение query / passage | Модели с task-адаптерами дают заметно лучший поиск |
| Батчинг | 600 чанков надо залить одним прогоном |
| Стабильность версии | Смена версии модели = переэмбеддить всё |

### 6.2 Что не зависит от выбора модели

- **Что эмбеддить.** Не только `text`, а `heading_path.join(" > ") + "\n\n" + text`. Это даёт модели понять, что «Лист «Кофейня (Москва)»» относится к кофейне, а не к пекарне. Приём называется **contextual retrieval** — см. раздел 9.
- **Кэш по `content_hash`.** Повторный прогон не жжёт токены.
- **Идемпотентность.** Upsert по `chunk_id`. Хэш не изменился — пропускаем, изменился — переэмбеддим.
- **Одна модель для запроса и для чанков.** Если разойдутся — поиск вернёт мусор без ошибок в логах.

### 6.3 Как выбрать

Прогнать eval-набор (раздел 8) на 2–3 моделях и сравнить `recall@5` и `MRR`. На 600 чанках это стоит копейки и занимает минуты. Выбирать модель по описанию, а не по метрикам на своих данных — самая частая ошибка в RAG.

**Что проверить в первую очередь:** как модель ведёт себя на точных терминах — «ст. 14.5 КоАП», «Правила № 2463», «152-ФЗ». Если путает номера статей, это не лечится rerank'ом, только гибридным поиском.

## 7. Retrieval

```
запрос пользователя
  │
  ├─ 1. Определить business_type
  │     селектор в UI → если не выбран, классификатор по запросу
  │     если классификатор не уверен → искать без фильтра
  │
  ├─ 2. Фильтр в SQL
  │     WHERE business_type = $1 OR scope = 'global'
  │
  ├─ 3. Два поиска параллельно
  │     vector:  top-50 по cosine
  │     fulltext: top-50 по to_tsquery('russian', ...)
  │
  ├─ 4. Слияние через RRF → top-20
  │
  ├─ 5. Rerank → top-5..8
  │
  ├─ 6. Small-to-big
  │     подтянуть parent-чанк, если нужен контекст
  │
  ├─ 7. Разрешить ссылки
  │     если в тексте «см. раздел B0» → добавить чанк B0
  │
  └─ 8. Собрать промпт с цитатами из heading_path
```

**Почему фильтр по `business_type` обязателен.** Без него «сколько стоит открыть кофейню» и «сколько стоит открыть ПВЗ» смешаются в выдаче. Это то, что делает мультинишевого ассистента рабочим.

**Как определяется ниша.** Два уровня:

1. **Селектор в UI — основной путь.** Пользователь сам выбирает нишу, фильтр применяется точно, ошибок нет. Это же даёт бесплатный сигнал: если человек выбрал «Кофейня», а спрашивает про ПВЗ, это видно в логах.
2. **Классификатор — fallback.** Если ниша не выбрана, LLM определяет её по тексту запроса. Обязательно с порогом уверенности: если модель не уверена, фильтр не применяется вообще и поиск идёт по всему корпусу. Лучше вернуть результаты из нескольких ниш, чем отфильтровать правильную.

**Почему не только классификатор.** Ошибка классификации тихо ломает выдачу: пользователь спросил про пекарню, классификатор решил «кофейня», фильтр отсёк правильные чанки, ассистент ответил уверенно и неправильно. Селектор в UI убирает этот класс ошибок полностью.

**Почему гибрид обязателен.** В документе очень много точных терминов: «ст. 14.5 КоАП», «Правила № 2463», «152-ФЗ», «ст. 18.1 Закона о рекламе». Чистый vector-поиск на них проваливается — эмбеддинг не различает номера статей. Полнотекстовый поиск вытягивает их точно.

**Почему RRF, а не веса.** Reciprocal Rank Fusion складывает обратные ранги: `score = Σ 1/(60 + rank)`. Не надо подбирать веса между vector и fulltext — работает из коробки. Стандарт с 2009 года.

## 8. Eval — по ключевым шагам

Без этого нельзя узнать, стало ли лучше от смены чанкинга или модели. Самый пропускаемый и самый важный пункт.

### Шаг 1. Собрать 40 вопросов

Разбивка:

| Группа | Сколько | Пример |
|---|---|---|
| По нишам | 30 (по 3 на нишу) | «Какая выручка у кофейни в Москве?» |
| По сквозным разделам | 10 | «Какие лимиты у НПД в 2026 году?» |

Внутри каждой ниши 3 вопроса должны бить по разным типам контента:

- 1 вопрос по **таблице** — «Какая ставка налога заложена в финмодели кофейни?»
- 1 вопрос по **кейсу** — «Почему закрылась кофейня в Барнауле?»
- 1 вопрос по **SOP или ловушкам** — «Что делать, если клиент жалуется на напиток?»

Для сквозных разделов:

- 3 вопроса по налогам (`0`)
- 4 вопроса по онлайн-регуляторике (`B0.1`–`B0.6`)
- 3 вопроса по сводке финмоделей (`11`)

**Отдельно добавить 5 «сложных» вопросов**, которые проверяют именно то, что легко сломать:

- Вопрос с точным номером статьи: «Что грозит за отсутствие маркировки интернет-рекламы?» → должен найти `B0.2`
- Вопрос, требующий двух разделов: «Какие налоги у онлайн-школы и что говорит B0 про НПД?»
- Вопрос, где ниши легко перепутать: «Сколько стоит открыть точку?» без указания ниши
- Вопрос про регион: «Чем отличается финмодель кофейни в Москве и в регионе?»
- Вопрос, ответа на который в документе нет — проверить, что ассистент не выдумывает

### Шаг 2. Разметить ожидаемые чанки

Для каждого вопроса вручную указать `chunk_id`, которые должны попасть в выдачу. Это самая трудоёмкая часть, но без неё метрики бессмысленны.

Формат:

```json
{
  "qid": "q-coffee-01",
  "question": "Какая выручка у кофейни в Москве?",
  "business_type": "coffee_shop",
  "expected_chunk_ids": ["coffee_shop-1.3-finmodel-moscow"],
  "expected_section": "1.3",
  "difficulty": "easy"
}
```

### Шаг 3. Выбрать метрики

| Метрика | Что показывает |
|---|---|
| `recall@5` | Доля вопросов, где нужный чанк попал в топ-5 |
| `recall@10` | То же для топ-10 |
| `MRR` | Насколько высоко в среднем стоит первый правильный чанк |
| `nDCG@10` | Качество ранжирования с учётом порядка |

Целевые значения для старта: `recall@5 ≥ 0.85`, `MRR ≥ 0.7`. Если ниже — проблема в чанкинге или в фильтре, а не в модели.

### Шаг 4. Зафиксировать baseline

Сравнивать надо не «RAG vs RAG», а с альтернативой. На таком объёме (25–30K токенов на нишу) длинн��й контекст может обогнать RAG по качеству.

| Вариант | Что делаем |
|---|---|
| A. RAG | Наш пайплайн |
| B. Long-context | Отфильтровали нишу → положили весь раздел в контекст |
| C. Vector-only | Без fulltext и без rerank |

Прогнать все три на одном наборе вопросов. Это даст честный ответ, нужен ли RAG вообще.

### Шаг 5. Прогнать и записать результаты

Скрипт `scripts/eval.ts` прогоняет 40 вопросов через каждый вариант и пишет отчёт в `eval/results/` (gitignored). Отчёт — таблица: вопрос, вариант, найденные чанки, метрики.

### Шаг 6. Оценить качество ответа

Метрики поиска не говорят, выдумывает ли модель. Нужен LLM-as-judge:

- **Faithfulness** — есть ли в ответе утверждения, которых нет в найденных чанках
- **Answer relevancy** — отвечает ли на заданный вопрос
- **Citation accuracy** — правильные ли `heading_path` указаны как источник

### Шаг 7. Итерировать

Меняем один параметр за раз и смотрим на метрики:

- размер чанка (500 / 700 / 1000 токенов)
- перекрытие (0% / 15% / 25%)
- модель эмбеддингов
- наличие rerank
- `top-k` до и после rerank

## 9. Что делают другие разработчики

Полезные референсы, на которых основаны решения выше.

**Anthropic — Contextual Retrieval.** Перед эмбеддингом к каждому чанку приклеивают 1–2 предложения контекста, сгенерированные LLM. По их публичным замерам это снижает долю провалов поиска примерно на треть, а вместе с BM25 — почти вдвое. У нас контекст уже есть в структуре документа, поэтому генерировать его не нужно — берём `heading_path`.

**LangChain — ParentDocumentRetriever.** Каноническая реализация small-to-big: индексируем мелкие чанки, в LLM отдаём родителя. Ровно наша схема из раздела 3.2.

**LlamaIndex — SentenceWindowNodeParser и AutoMergingRetriever.** То же самое, другой реализацией. Полезно посмотреть, как они решают проблему «сколько соседей подтягивать».

**Cormack, Clarke, Buettcher (2009) — Reciprocal Rank Fusion.** Оригинальная статья про RRF. Стандартный способ слить два ранжирования без подбора весов.

**pgvector — Hybrid Search.** Типовой SQL-паттерн: `ts_rank` + оператор `<=>` + RRF в одном запросе. Есть готовые примеры в документации pgvector.

**Jina — Late Chunking.** Альтернатива contextual retrieval: эмбеддим весь документ целиком, потом пулим по чанкам, чтобы каждый чанк «видел» соседей. Стоит попробовать, если решим не полагаться на `heading_path`.

**RAGAS и TruLens.** Фреймворки для eval. Дают готовые метрики faithfulness, answer relevancy, context precision/recall. Можно не писать свои.

**Unstructured и LlamaParse.** Парсинг таблиц из PDF и DOCX. Нам не нужно — у нас уже markdown. Но полезно понимать, откуда в документе взялись 11 расплющенных OCR-таблиц: это следы автоконвертации.

**Что можно делать параллельно.** Фазы 1 и 4 независимы друг от друга и от БД. Фаза 8 (xlsx) независима от 5–7 и может идти в любой момент после 2.
