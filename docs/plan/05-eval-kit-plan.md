# План 5. Eval-кит: набор вопросов, валидатор и раннер

## 0. О чём этот план

Как получить измеримый eval-набор для RAG-системы BusiVerse и обвязку, которой можно прогонять вопросы через поиск и GLM локально.

Этот план закрывает **фазу 3** из плана 1 (`eval/questions.jsonl`) и добавляет к ней минимум обвязки, чтобы набор можно было сразу подключать к тестам.

**Что входит:**

1. Датасет: 45 вопросов в JSONL + JSON Schema.
2. Валидатор: проверка схемы, ссылочной целостности и покрытия.
3. Раннер: обёртка «вопрос → retrieval из БД → GLM → сохранённый результат».

**Что НЕ входит (сознательно):**

- Метрики `recall@5` / `MRR` / `nDCG@10` — это шаги 3–5 раздела 8 плана 1, они имеют смысл только после загрузки эмбеддингов в БД (фазы 4–5).
- LLM-as-judge (faithfulness, relevancy, citation accuracy) — шаг 6 раздела 8, отдельный план.
- Baseline A/B/C (RAG vs long-context vs vector-only) — шаг 4 раздела 8, тоже после выбора модели.

Раннер проектируется так, чтобы всё это потом **подключилось без переделки**: он уже сейчас сохраняет ранги найденных чанков и полный снимок конфига прогона.

**Порядок работ:**

```
A. Собрать датасет 45 вопросов + разметка   → разделы 3–5
B. JSON Schema + валидатор                  → раздел 6
C. Раннер                                   → раздел 7
D. Метрики + judge (вне этого плана)        → отдельный план после фаз 4–5
```

## 1. Фиксированные решения

| Что | Решение |
|---|---|
| Формат датасета | JSONL: одна строка = один вопрос. Плюс `eval/schema.json` (JSON Schema Draft 2020-12) |
| Объём | 40 вопросов по плану 1 + 5 сложных = 45 |
| Разметка ожидаемого | `expected_chunk_ids` (реальные id из `data/chunks`) + `expected_section` |
| Стиль вопросов | Смешанный: часть разговорные от новичка, часть с терминами документа |
| Раннер и валидатор | TypeScript, запуск через `npx tsx scripts/eval/...` |
| Retrieval в раннере | Прямой SQL к Neon: pgvector + tsvector + RRF. Без запущенного приложения |
| Генерация ответа | Zhipu OpenAI-совместимый API (`https://open.bigmodel.cn/api/paas/v4`), ключ в `GLM_API_KEY` |
| Модель GLM | Через env `GLM_MODEL`. **Точный id модели уточнить у Zhipu до реализации** — см. раздел 9 |
| Уровень рассуждения | Env `GLM_REASONING` = `high` / `low`. Рабочий прогон — `high`, черновой — `low`. Маппинг на параметр `thinking` в API Zhipu проверить по документации |
| Эмбеддинги запроса | Провайдер настраивается через env (`EMBEDDING_*`). Никакого провайдера не зашиваем в код |
| Ключи | Только локально в `.env` пользователя. В git попадает `.env.example` без секретов |
| Метрики и judge | Не в этом плане. Формат результатов уже хранит всё нужное для них |
| Где живут результаты | `eval/results/` — gitignored |

## 2. Точка старта: что уже есть

План опирается на уже сделанные фазы 0–2. Факты, от которых считаем:

| Факт | Значение |
|---|---|
| Чанков на диске | 430 файлов в `data/chunks/<niche>/<section>/<chunk_id>.json` |
| Формат `chunk_id` | `<business_type>-<section_code>-bNN`, у дроблёных блоков суффикс `-pN`: `coffee_shop-1.3-b01-p1` |
| Чанк-секция | `parent_id = null`, `chunk_type = prose`, компактная (~30–500 токенов) |
| Чанк-блок | `parent_id = <business_type>-<section_code>` |
| Типы чанков | `prose`, `table`, `case`, `sop`, `checklist` |
| Метаданные чанка | `business_type`, `block`, `section_code`, `section_title`, `block_title`, `heading_path`, `chunk_type`, `scope`, `topics`, `region`, `part_index`/`part_total`, `line_start`/`line_end`, `token_count`, `content_hash` |
| Внутренние ссылки | `data/chunks/_links.json`: `from_chunk_id → to_section` («см. раздел B0») |
| БД | Neon Postgres, схема из раздела 5 плана 1: `chunks.embedding vector(1024)`, `tsv`, индексы HNSW + GIN |

**Важно:** в `data/chunks` лежат JSON-файлы по одному чанку — это рабочая копия. Источник правды для раннера — БД. Валидатор сверяет датасет с файлами на диске (они есть в git), раннер работает с БД.

## 3. Формат датасета

`eval/questions.jsonl` — одна строка JSON на вопрос. Схема полей:

| Поле | Тип | Обязательное | Что это |
|---|---|---|---|
| `qid` | string | да | Стабильный id: `q-<niche|global|hard>-NN`. Менять нельзя — на него ссылаются результаты прогонов |
| `group` | enum | да | `niche` / `global` / `hard` |
| `business_type` | string \| null | да | Код ниши (`coffee_shop`, ...). `null` для сквозных и для hard-вопроса без ниши |
| `question` | string | да | Текст вопроса на русском |
| `question_style` | enum | да | `colloquial` (разговорный) / `terminology` (с терминами документа) |
| `content_type` | enum | да | `table` / `case` / `sop` / `checklist` / `prose` / `mixed` — какой тип чанка должен ответить |
| `expected_chunk_ids` | string[] | да | 1–3 реальных `chunk_id`. Пустой массив только для `unanswerable` |
| `expected_section` | string \| null | да | Основной `section_code` (`"1.3"`, `"B0.2"`). Для hard-вопроса с двумя разделами — основной из двух |
| `expected_sections` | string[] | да | Все секции, релевантные ответу (для двух-разделных — обе) |
| `difficulty` | enum | да | `easy` / `medium` / `hard` |
| `unanswerable` | boolean | да | `true` — ответа в документе нет, ассистент должен это распознать |
| `notes` | string | нет | Почему размечено именно так, подводный камень |

Пример строки:

```json
{"qid":"q-niche-01","group":"niche","business_type":"coffee_shop","question":"Какая выручка у кофейни в Москве по финмодели?","question_style":"colloquial","content_type":"table","expected_chunk_ids":["coffee_shop-1.3-b01"],"expected_section":"1.3","expected_sections":["1.3"],"difficulty":"easy","unanswerable":false,"notes":"Лист «Кофейня (Москва)» — таблица финмодели"}
```

**Почему `expected_sections` отдельно от `expected_section`.** Метрики по чанкам хрупки к пересборке чанкинга (id меняются при передроблении), метрики по секциям — нет. Храним оба уровня сразу: чанк для точных метрик сейчас, секцию для устойчивых сравнений потом.

**Почему `question_style` в датасете.** Позволяет потом посчитать метрики раздельно для разговорных и терминологических вопросов и увидеть, где retrieval проседает сильнее.

## 4. Состав набора: 45 вопросов

### 4.1 Разбивка

| Группа | Сколько | Разметка |
|---|---|---|
| По нишам | 30 (по 3 на каждую из 10 ниш) | 1 вопрос по **таблице** (финмодель/кадры/поставки/штрафы), 1 по **кейсу** (`N.2`), 1 по **SOP или ловушкам** (`N.6`/`N.7`) |
| По сквозным разделам | 10 | 3 по налогам (`0`), 4 по онлайн-регуляторике (`B0.1`–`B0.6`), 3 по сводке финмоделей (`11`) |
| Сложные | 5 | См. 4.3 |

### 4.2 Правила стиля

Смешанный стиль — в каждой тройке вопросов ниши минимум один разговорный и один с точным термином:

- **Разговорный** — как спрашивает человек без знаний: «сколько штраф, если нет кассы?», «сколько стоит открыть точку?»
- **Терминологический** — с формулировками документа: «ст. 14.5 КоАП», «Правила № 2463», «152-ФЗ», «НПД», «ОКВЭД»

Это сознательная пара к гибридному поиску: разговорные вопросы проверяют vector-плечо, терминологические — fulltext-плечо. Если обе половины гибрида не тестируются раздельно, деградацию одной из них не заметить.

### 4.3 Пять сложных вопросов

| № | Тип | Пример | Что проверяет |
|---|---|---|---|
| H1 | Точный номер статьи | «Что грозит за отсутствие маркировки интернет-рекламы?» | Попадание в `B0.2` через fulltext |
| H2 | Два раздела | «Какие налоги у онлайн-школы и что говорит B0 про НПД?» | `expected_sections` из двух элементов, сборка ответа из двух мест |
| H3 | Без ниши | «Сколько стоит открыть точку?» (`business_type: null`) | Поведение без фильтра: не должен смешать ниши |
| H4 | Регион | «Чем отличается финмодель кофейни в Москве и в регионе?» | Чанки с `region = moscow` / `region` — фильтр по региону |
| H5 | Ответа нет | Вопрос по теме, которой в документе нет | `unanswerable: true`, пустой `expected_chunk_ids`. Проверка, что ассистент не выдумывает |

### 4.4 Как размечать `expected_chunk_ids`

Разметка делается по файлам `data/chunks/`, вручную, с опорой на метаданные:

1. По вопросу определить секцию (`N.M`) и тип контента → найти блок в `data/chunks/<niche>/<section>/`.
2. Записать `chunk_id` блока. Если блок дроблёный (`-p1`, `-p2`) — указать ту часть, где ответ, или обе.
3. Проверить `_links.json`: если в найденном чанке есть ссылка «см. раздел B0» и она нужна для полного ответа — добавить целевой чанк в `expected_chunk_ids`.
4. Заполнить `expected_section` / `expected_sections`.

Правила:

- 1–3 `chunk_id` на вопрос. Больше трёх — вопрос сформулирован слишком широко, переформулировать.
- `business_type` вопроса должен совпадать с `business_type` каждого ожидаемого чанка (кроме сквозных: у них `scope = global`).
- Для H4 (регион) в `expected_chunk_ids` — оба листа: Москва и регион.

### 4.5 Процесс сборки

Датасет собирается в два прохода:

1. **Черновик.** По дереву чанков (`data/chunks`) сгенерировать кандидатов: на каждую нишу выбрать по одному репрезентативному блоку каждого типа (таблица/кейс/SOP), на сквозные — по разделам. Формулировки — по правилам 4.2.
2. **Верификация.** Каждый вопрос вручную сверить с текстом ожидаемого чанка: ответ там действительно есть, формулировка не подсказывает `section_code` дословно (иначе тест подыгрывает fulltext-плечу).

Итог — 45 строк в `eval/questions.jsonl`, каждая проходит валидатор из раздела 6.

### 4.6 Чек-лист покрытия

Валидатор считает и падает, если не выполнено:

- каждая из 10 ниш имеет ровно 3 вопроса, и среди них есть `table`, `case` и (`sop` или `prose`-ловушки);
- сквозные: ≥3 вопроса с `expected_section = "0"`, ≥4 с `B0.*`, ≥3 с `"11"`;
- среди 45 есть минимум по одному вопросу каждого `content_type`;
- ровно 5 вопросов с `group = hard`, среди них ровно 1 `unanswerable`;
- `question_style`: доля `colloquial` между 30% и 70%.

## 5. JSON Schema (`eval/schema.json`)

JSON Schema Draft 2020-12 для одной строки JSONL. Ключевые ограничения:

- `required`: все поля из раздела 3, кроме `notes`.
- `qid`: `pattern: ^q-(niche|global|hard)-[0-9]{2}$`.
- `business_type`: `enum` из 10 кодов ниш или `null`.
- `expected_chunk_ids`: `items.pattern: ^[a-z_]+-[0-9B]+(\.[0-9]+)?(-b[0-9]{2}(-p[0-9]+)?)?$` — формат id из чанкера.
- `expected_chunk_ids`: `maxItems: 3`; при `unanswerable: true` — `maxItems: 0`.
- `expected_section`: `pattern: ^([0-9]+(\.[0-9]+)?|B0(\.[0-9]+)?|11)$`.
- `difficulty`, `group`, `question_style`, `content_type`: enum'ы из раздела 3.

Схема — контракт для тестов: любой consumer датасета валидируется одной командой, без собственного парсера.

## 6. Валидатор (`scripts/eval/validate.ts`)

Одна команда: `npx tsx scripts/eval/validate.ts`. Выход — отчёт в stdout, код возврата 0/1 (чтобы подключить в CI или pre-commit).

### 6.1 Проверки

| # | Проверка | Уровень |
|---|---|---|
| 1 | Каждая строка валидна по `eval/schema.json` | блокирует |
| 2 | `qid` уникальны | блокирует |
| 3 | Каждый `expected_chunk_ids[*]` существует в `data/chunks/**` | блокирует |
| 4 | `business_type` вопроса совпадает с `business_type` ожидаемого чанка (или чанк `scope = global`) | блокирует |
| 5 | `expected_section` совпадает с `section_code` ожидаемых чанков | блокирует |
| 6 | `unanswerable` вопросы: пустой `expected_chunk_ids`, непустой `question` | блокирует |
| 7 | Чек-лист покрытия из 4.6 | блокирует |
| 8 | Дубликаты вопросов: нормализованный текст вопроса не повторяется | предупреждение |
| 9 | Сходство разметки: cosine между эмбеддингом вопроса и эмбеддингами ожидаемых чанков | предупреждение, только если в БД уже есть эмбеддинги |

**Про проверку 9.** Это те «проверки на схожести»: валидатор эмбеддит вопрос через настроенный провайдер и сравнивает с векторами ожидаемых чанков в БД. Если ожидаемый чанк не попадает в топ-50 по косинусу — почти наверняка разметка ошибочна или вопрос сформулирован слишком далеко от текста. Это предупреждение, а не блокер: гибридный поиск может достать чанк полнотекстом, который vector-плечо не видит. До загрузки эмбеддингов в БД проверка молча пропускается.

### 6.2 Отчёт

Валидатор печатает: число вопросов, разбивку по группам/типам/стилям, список ошибок с номером строки JSONL и список предупреждений. Ничего не пишет в датасет.

## 7. Раннер (`scripts/eval/run.ts`)

Обёртка, которую пользователь запускает локально: `npx tsx scripts/eval/run.ts [--limit N] [--group niche|global|hard] [--qid q-...]`.

### 7.1 Поток одного вопроса

```
вопрос из questions.jsonl
  │
  ├─ 1. Эмбеддинг запроса          embed.ts, провайдер из env
  │
  ├─ 2. Гибридный SQL к Neon       retrieve.ts
  │     vector top-50 + tsv top-50 → RRF → top-20
  │     фильтр: business_type = $1 OR scope = 'global'
  │     (для вопросов с business_type = null — без фильтра по нише)
  │
  ├─ 3. Small-to-big               подтянуть parent-чанк найденных блоков
  │
  ├─ 4. Промпт                     системный промпт + чанки с heading_path
  │
  ├─ 5. GLM                        glm.ts, Zhipu OpenAI-совместимый API
  │
  └─ 6. Запись результата          eval/results/<run_id>/results.jsonl
```

Rerank в раннере **выключен по умолчанию** — его ещё нет. Точка подключения зарезервирована (шаг между 3 и 4), включается флагом, когда будет выбран.

### 7.2 Конфигурация через env

Все параметры — через env, никаких значений провайдеров в коде:

| Переменная | Что | Дефолт |
|---|---|---|
| `DATABASE_URL` | Строка подключения к Neon | нет, обязателен |
| `GLM_API_KEY` | Ключ Zhipu | нет, обязателен |
| `GLM_BASE_URL` | База API | `https://open.bigmodel.cn/api/paas/v4` |
| `GLM_MODEL` | id модели | нет, обязателен. **Точный id уточнить** (раздел 9) |
| `GLM_REASONING` | `high` / `low` | `high` |
| `EMBEDDING_PROVIDER` | Маркер провайдера для логов и совместимости | нет, обязателен |
| `EMBEDDING_MODEL` | id модели эмбеддингов | нет, обязателен |
| `EMBEDDING_API_KEY` | Ключ провайдера | нет, обязателен |
| `EMBEDDING_BASE_URL` | Если провайдер не официальный OpenAI | нет |
| `EMBEDDING_DIMS` | Размерность, приводится к 1024 если провайдер умеет усечение | 1024 |

В git попадает `.env.example` с именами переменных и пустыми значениями. Реальные ключи — только в локальном `.env` пользователя.

**Критическое правило (из плана 1, раздел 6.2):** модель эмбеддингов запроса должна совпадать с моделью, которой эмбеддированы чанки в БД. Раннер при старте читает из БД метаданные ингеста (или сверяет `EMBEDDING_MODEL` с записанным при ингесте значением) и падает с понятной ошибкой при несовпадении — векторный поиск с чужой моделью возвращает мусор без единой ошибки в логах.

### 7.3 Гибридный SQL (эскиз)

Один запрос, два плеча, RRF в SQL:

```sql
with vec as (
  select chunk_id, row_number() over (order by embedding <=> $1::vector) as rank
  from chunks
  where business_type = $2 or scope = 'global'
  order by embedding <=> $1::vector
  limit 50
),
fts as (
  select chunk_id, row_number() over (order by tsv rank $3) as rank
  from chunks
  where business_type = $2 or scope = 'global'
    and tsv @@ websearch_to_tsquery('russian', $4)
  order by tsv rank $3
  limit 50
)
select c.*, coalesce(1.0/(60+v.rank),0) + coalesce(1.0/(60+f.rank),0) as rrf_score
from vec v full outer join fts f using (chunk_id)
join chunks c using (chunk_id)
order by rrf_score desc
limit 20;
```

Эскиз, не финал: точные веса RRF, обработку `websearch_to_tsquery` для разговорных вопросов и пагинацию уточнить при реализации. Логика сознательно дублирует раздел 7 плана 1 — раннер тестирует тот же путь, что потом будет в проде.

### 7.4 Системный промпт

Фиксируется в `eval/README.md` и в коде как константа — прогоны сравнимы только при одинаковом промпте:

- отвечай только на основе переданных чанков;
- указывай источник по `heading_path`;
- если ответа в чанках нет — прямо скажи «в документе нет данных» (это условие тестируется вопросом H5);
- не смешивай ниши: отвечай в контексте указанной `business_type`.

### 7.5 Формат результата

`eval/results/<run_id>/results.jsonl` — одна строка на вопрос:

```json
{
  "run_id": "2026-11-01T14-30-05",
  "qid": "q-niche-01",
  "question": "...",
  "retrieved": [{"chunk_id":"coffee_shop-1.3-b01","rank":1,"score":0.0132,"source":"rrf"}],
  "parent_chunk_ids": ["coffee_shop-1.3"],
  "answer": "...",
  "model": "<GLM_MODEL>",
  "reasoning": "high",
  "embedding_model": "<EMBEDDING_MODEL>",
  "latency_ms": {"retrieval": 120, "generation": 3400},
  "usage": {"prompt_tokens": 0, "completion_tokens": 0},
  "error": null
}
```

Рядом `summary.json`: снимок конфига (все env-имена без секретов), число вопросов, ошибки, тайминги.

**Почему результат такой подробный.** Поля `retrieved[].rank` и `expected_chunk_ids` из датасета — это ровно то, на чём считаются `recall@5` / `MRR` / `nDCG@10` в будущем плане метрик. Метрики посчитаются постфактум по сохранённым прогонам — перезапускать генерацию не придётся.

### 7.6 Стоимость и идемпотентность

- 45 вопросов × 1 прогон: retrieval по 430 чанкам — миллисекунды, генерация — основной расход. Прогон с `GLM_REASONING=low` — черновой, с `high` — контрольный.
- `run_id` = timestamp, прогоны не перезаписывают друг друга.
- Кэш эмбеддингов запросов не нужен: 45 коротких строк.
- Повторный прогон того же `qid` с теми же параметрами — детерминирован настолько, насколько позволяет модель; для сравнения конфигураций использовать `temperature = 0`, если API Zhipu это поддерживает (проверить при реализации).

## 9. Открытые вопросы

1. **Точный id GLM-модели.** Рабочее название «5.3 flash» не совпадает с публичными id Zhipu (`glm-4-flash`, `glm-4.5-flash`, `glm-4.6`). Перед реализацией уточнить точную строку модели в API Zhipu и параметр уровня рассуждения (`high`/`low` — как именно передаётся: поле `thinking`, `reasoning_effort` или иначе). До уточнения раннер требует `GLM_MODEL` из env и не имеет дефолта.
2. **Провайдер эмбеддингов.** Пользователь настраивает через env. Выбор конкретной модели — фаза 4 плана 1, по метрикам на этом датасете. Валидатор (проверка 9) заработает в полном объёме только после загрузки эмбеддингов чанков в БД.
3. **`DATABASE_URL`.** Пользователь подставляет свой ключ Neon локально. Убедиться, что переменная не попадает в git (`.env` в `.gitignore`).
4. **`temperature = 0` в API Zhipu.** Проверить поддержку при реализации; если нет — зафиксировать в отчёте прогона фактическое значение.
5. **Владелец датасета.** Кто правит `questions.jsonl` при изменении чанкинга: перегенерация черновика или ручная правка id. Предварительно — ручная правка, чанкер стабилен, id меняются редко.

## 10. Фазы работ

| Фаза | Что делаем | Результат |
|---|---|---|
| A | Датасет: 45 вопросов, разметка по `data/chunks`, стиль по 4.2 | `eval/questions.jsonl` |
| B | JSON Schema + валидатор, прогон на датасете | `eval/schema.json`, `scripts/eval/validate.ts`, зелёный отчёт |
| C | Раннер: env-конфиг, embed, гибридный SQL, GLM, запись результатов | `scripts/eval/run.ts` + `lib/`, `.env.example`, первый прогон на 2–3 вопросах |
| D | Метрики + judge + baseline | **Вне этого плана** — отдельный план после фаз 4–5 плана 1 |

**Почему валидатор до раннера.** Раннер читает датасет как вход. Если в разметке битый `chunk_id`, прогон молча выдаст мусорные метрики. Валидатор — единственная защита, и он должен существовать до первого прогона.

**Почему раннер без метрик.** Метрики без эмбеддингов в БД посчитать не на чем, а датасет и раннер от них не зависят. Разделение позволяет собрать и проверить кит сейчас, а метрики подключить одной командой позже.
