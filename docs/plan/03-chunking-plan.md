# План 3. Чанкование

Статус: черновик для согласования.
Предыдущие этапы: очистка текста (план 2, выполнен), схема БД (`docs/db/schema.md`, спроектирована).

## 0. О чём этот план

Детальный план этапа 3 из `01-rag-plan.md`: превращение очищенного markdown-файла в чанки.

Главный принцип — уже зафиксирован в плане 1 и повторяется здесь как требование:

> **Нарезка идёт по осмысленным блокам структуры документа, а не «разбить на кучу файлов».**
> Структура документа: **10 ниш (подгруппы), в каждой — 8 основных групп-подразделов `N.1`–`N.8`, плюс сквозные разделы `0`, `B0`, `11`.**
> Чанк = осмысленный блок внутри этой структуры (кейс, SOP, лист финмодели, чек-лист, группа абзацев). Границы не угадываются — они читаются из нумерации заголовков.

## 1. Фиксированные решения

Зафиксированы по ответам на вопросы, ничего сверх этого не вводится.

| Что | Решение |
|---|---|
| Язык скрипта | **TypeScript**, запуск через `tsx` (уже есть в devDependencies) |
| Куда пишем результат | **JSONL-файл** → просмотр глазами → отдельным шагом (не в этом плане) заливка в Neon |
| Подсчёт токенов | **tiktoken** (пакет `js-tiktoken`, см. 6.1) |
| Поле `topics` | **Не извлекаем на этом этапе.** В JSONL пишем `topics: []` — заполнится позже отдельным шагом (частотные термины + LLM-нормализация) |
| Принцип нарезки | Структурный: 10 ниш × 8 подразделов + сквозные разделы; один смысловой блок = один чанк |
| Бюджет чанка | 500–700 токенов (из плана 1) |
| Эмбеддинги | Не в этом плане. В JSONL поля `embedding` нет |

## 3. Классификатор заголовков

Уровень заголовка не важен, важен шаблон. Один проход по файлу, каждый H2 попадает ровно в одну категорию. Порядок проверок важен — сверху вниз, первое совпадение выигрывает:

| № | Шаблон (regex) | Категория | Пример |
|---|---|---|---|
| 1 | `^## (\d+)\.(\d+)\.\s` | **Секция** `N.M` | `## 1.3. Финансовая модель` |
| 2 | `^## B0\.(\d+)\.\s` | **Секция** `B0.M`, scope = global | `## B0.2. Маркировка интернет-рекламы…` |
| 3 | `^## B0\.\s` | **Группа** `B0`, scope = global | `## B0. ОБЩАЯ РЕГУЛЯТОРИКА…` |
| 4 | `^## 0\.\s` и `^## 11\.\s` | **Группа**-секция без детей, scope = global | `## 0. ОБЩИЕ ПОЛОЖЕНИЯ…` |
| 5 | `^## (\d+)\.\s` (2–10) | **Группа**-ниша, меняет текущую нишу | `## 2. ОФЛАЙН — ПУНКТ ВЫДАЧИ ЗАКАЗОВ…` |
| 6 | всё остальное H2 | **Блок** внутри текущей секции | `## Лист «Кофейня (Москва)»`, `## SOP 1. …`, `## Coffee Bull — Барнаул` |

H1 (`# …`) встречается один раз — это преамбула. H3 игнорируются как границы.

**Категория 4 — почему отдельная строка.** `## 0.` и `## 11.` совпадают с шаблоном ниши (№5), но нишами не являются. Они обрабатываются как сквозные секции: тело секции = один блок-чанк (см. 7.3).

**Валидатор обязан проверять:** после разбора не осталось ни одного неклассифицированного H2. Это критерий приёмки, а не пожелание.

## 4. Алгоритм прохода

Один проход сверху вниз, конечный автомат с состоянием:

```
state = { currentNiche: null, currentSection: null }

для каждой строки файла:
  если H2:
    категория = classify(строка)
    секция?      → закрыть текущий блок, создать секцию, state.currentSection = секция
    группа-ниша? → закрыть текущий блок и секцию, state.currentNiche = ниша
    группа B0/0/11? → то же + scope = global
    блок?        → закрыть предыдущий блок, начать новый внутри state.currentSection
  иначе:
    строка дописывается в тело текущего открытого контейнера
    (секция, если блок ещё не открыт; иначе в блок)
```

Правила накопления текста:

- Строки между заголовком секции и первым дочерним H2 — **введение секции** (идёт в родительский чанк, см. 7).
- Строки внутри блока — тело блока, включая его заголовок.
- Пустые строки по краям тел обрезаются; внутри остаются как есть.

Ошибки, при которых скрипт падает (а не молча выдаёт мусор):

- блок встретился до первой секции (state.currentSection = null);
- заголовок не классифицировался;
- секция `N.M` встретилась при currentNiche = null (кроме `B0.*`, `0`, `11`).

## 5. Типы блоков и правила нарезки

Типы из плана 1 (раздел 3.5), здесь — как именно каждый определяется и режется.

### 5.1 Определение `chunk_type`

| `chunk_type` | Как определяется |
|---|---|
| `sop` | Заголовок блока матчится `^SOP \d+\.` — только внутри секции `N.6` |
| `checklist` | Заголовок содержит «Чек-лист» — внутри `N.6` |
| `case` | Блок внутри `N.2`, заголовок которого **не** входит в список служебных (см. ниже) |
| `table` | Секции `N.3`, `N.4`, `N.5`, `N.8` целиком; блок «Матрица сбоев» в `N.6`; блоки в `N.2` из списка служебных, если их тело — таблица |
| `prose` | Секции `N.1`, `N.7`; служебные блоки `N.2`; тело секций `0` и `11`; преамбула |

Список служебных заголовков `N.2` (не кейсы) — фиксированный, проверяется валидатором по всем 10 нишам:

- `Рыночный фон`
- `Примеры смены стратегии (pivot)`
- `Типовые сценарии закрытия в первые 6–12 месяцев`

Если в какой-то нише у `N.2` встретится служебный заголовок, которого нет в списке, — скрипт падает со списком найденных заголовков. Список пополняется руками, после человеческой проверки.

### 5.2 Правила дробления по типам

Бюджет: **500–700 токенов**. Блок ≤ 700 токенов → один чанк. Блок > 700 → дробится по правилам типа:

| Тип | Правило дробления |
|---|---|
| `table` | По группам строк. **Шапка таблицы повторяется в каждом куске.** Кусок без шапки бессмысленен. Группы строк подбираются так, чтобы кусок попадал в 500–700 |
| `prose` | По границам абзацев, перекрытие 15% (последний абзац куска повторяется первым абзацем следующего) |
| `case` | **Не режется никогда.** Кейс на 1200 токенов остаётся одним чанком: вывод в конце, причина в начале |
| `sop` | **Не режется никогда** |
| `checklist` | Список целиком; не режется |

Дробление таблицы — по строкам данных между разделителями `|---|`; шапка = строки до разделителя + сам разделитель.

Перекрытие прозы считается в абзацах, не в токенах: берём последний абзац куска целиком. 15% — ориентир по плану 1; если последний абзац сам больше 15% бюджета, берём его всё равно целиком (резать абзацы запрещено).

## 6. Подсчёт токенов

### 6.1 Инструмент

Пакет **`js-tiktoken`** (чистый JS, без WASM-бинарников — важно для воспроизводимости). Энкодинг — **`o200k_base`**.

Почему o200k_base, а не cl100k_base: он новее и заметно лучше работает с кириллицей (меньше токенов на русское слово). Точная оценка для русского важна вдвое: занижение бюджета разорвёт контекст у эмбеддинг-модели, завышение — уложит чанк мимо окна реранкера.

Важно понимать: реальная модель эмбеддингов ещё не выбрана, и её токенизатор не обязан совпадать с tiktoken. tiktoken здесь — **прокси-метрика для бюджета**, а не гарантия. Это осознанное упрощение из плана 1; после выбора модели, если она заметно отличается, бюджет пересчитывается одной константой.

### 6.2 Что считается

- `token_count` чанка = токены поля `text` (без метаданных).
- Бюджетные решения (резать/не резать) принимаются по токенам тела блока.

## 7. Чанки-секции (родители)

Схема small-to-big из плана 1: ищем по блокам, в LLM отдаём родителя.

### 7.1 Состав родительского чанка

1. Введение секции — текст прямо под `## N.M` до первого дочернего H2 (обычно 1–3 абзаца).
2. Список названий дочерних блоков — чтобы модель понимала, что внутри:

```
## 1.3. Финансовая модель

[введение секции, если есть]

Содержит блоки:
- Лист «Кофейня (Москва)»
- Лист «Кофейня (регион)»
- Скрытые расходы
- Отраслевые бенчмарки
```

### 7.2 Особые случаи

| Случай | Правило |
|---|---|
| Секция без введения (`B0`) | Родительский чанк = только список дочерних блоков |
| Секция без дочерних блоков (`0`, `11`) | Тело секции становится **одним блок-чанком** (тип `prose`/`table` по содержимому), родительский чанк всё равно создаётся — с введением и списком из одного блока |
| Секция без введения и без детей | Не встречается в файле; валидатор падает, если встретится |

### 7.3 Ожидаемый объём

~88 родительских чанков (80 + 8 сквозных), ~203 блока до дробления, +100–150 после дробления крупных. Итого **~500–600 записей** — сходится с оценкой плана 1.

## 8. Преамбула

Строки 1–12 (до `## 0.`) — один чанк:

- `scope = "global"`, `business_type = "global"`, `section_code = null`, `chunk_type = "prose"`, `parent_id = null`;
- в `heading_path` — только название документа.

Это служебный чанк: в нём правила расчётов («налог по умолчанию — УСН 6%…»), на которые ссылается весь документ.

## 9. Метаданные и формат JSONL

### 9.1 Поля записи

Каждая строка JSONL — одна запись, по составу полей совпадает с будущей строкой таблицы `chunks` (кроме `tsv` и `embedding` — их считает БД и следующий этап):

| Поле | Откуда |
|---|---|
| `chunk_id` | См. 9.2 |
| `source_id` | Константа, например `busiverse-2026-10-13` (дата актуальности из документа) |
| `business_type` | Из номера ниши (`1` → `coffee_shop`); для сквозных и преамбулы — `global` |
| `block` | `offline` (ниши 1–5) / `online` (6–10) / `global` |
| `section_code` | `1.3`, `B0.2`, `0`, `11`; у преамбулы `null` |
| `section_title` | Заголовок секции без `## ` |
| `block_title` | Заголовок блока без `## `; у родительского чанка `null` |
| `heading_path` | `["1. ОФЛАЙН — КОФЕЙНЯ", "1.3. Финансовая модель", "Лист «Кофейня (Москва)»"]` |
| `chunk_type` | По 5.1 |
| `topics` | Всегда `[]` — заполняется отдельным этапом позже |
| `scope` | `global` / `business` |
| `parent_id` | У блоков — id секции; у родительских чанков `null` |
| `chunk_index` | Порядковый номер внутри секции (родители не нумеруются, у них 0) |
| `part_index` / `part_total` | Номер куска и всего кусков, если блок дробился; иначе 1/1 |
| `line_start` / `line_end` | Номера строк **очищенного** файла |
| `token_count` | tiktoken, по 6.2 |
| `text` | Текст чанка |
| `content_hash` | sha256 текста |

### 9.2 Формат `chunk_id`

Родительский чанк секции — `{business_type}-{section_code}`:

```
coffee_shop-1.3        global-B0.2        global-0
```

Совпадает с примером `parent_id` из плана 1 (`coffee_shop-1.3`) — контракт не ломается.

Блок-чанк — `{parent_id}-b{NN}` где NN — порядковый номер блока внутри секции, в порядке следования в документе, с ведущим нулём:

```
coffee_shop-1.3-b01    ← Лист «Кофейня (Москва)»
coffee_shop-1.3-b02    ← Лист «Кофейня (регион)»
```

Кусок дроблёного блока — суффикс `-p{N}`:

```
coffee_shop-1.4-b01-p2
```

Индексы, а не slug'и из названий: названия блоков дрейфуют (план 1, раздел 4 — «Типовые сценарии закрытия…» встречается в 8 вариантах), номера стабильны. Идемпотентность ре-ингеста обеспечивает `content_hash`, а не человекочитаемость id.

### 9.3 Файлы вывода

```
data/
  chunks.jsonl         ← все чанки: блоки + родители + преамбула
  chunk_links.jsonl    ← внутренние ссылки (см. 10)
  chunking-report.md   ← отчёт прогона: счётчики, статистика токенов, отклонения
```

JSONL пишется целиком за прогон; прогон повторяем и детерминирован (без LLM, без сети, кроме загрузки энкодинга).

## 10. Внутренние ссылки (`chunk_links`)

В нишах 6–10 есть ссылки вида «см. раздел B0». Таблица `chunk_links` уже есть в схеме БД, поэтому ссылки вытаскиваются здесь — это механический шаг, не LLM.

- Regex по тексту блока: `см\. раздел ([A-Z0-9.]+)` и `раздел ([A-Z0-9.]+)` с белым списком кодов (`0`, `11`, `B0`, `B0.1`–`B0.6`).
- Результат: `{ from_chunk_id, to_section }`, дедупликация по паре.
- Каждое найденное сечение пишется в отчёт с номером строки — проверяется глазами перед загрузкой в БД.

## 11. Скрипт

```
scripts/chunking/
  config.ts        ← константы: бюджет, перекрытие, списки служебных заголовков, маппинг ниш
  classify.ts      ← классификатор заголовков (раздел 3)
  parse.ts         ← проход по файлу, секции и блоки (раздел 4)
  split.ts         ← дробление по типам (раздел 5)
  tokens.ts        ← обёртка над js-tiktoken
  emit.ts          ← метаданные, chunk_id, запись JSONL
  chunk.ts         ← входная точка: собирает пайплайн, пишет отчёт
  validate.ts      ← валидатор (раздел 12), запускается отдельной командой
```

- Зависимость: `js-tiktoken` (добавить в dependencies).
- npm-скрипты: `"chunk": "tsx scripts/chunking/chunk.ts"`, `"chunk:validate": "tsx scripts/chunking/validate.ts"`.
- Скрипт читает очищенный файл и пишет JSONL; ничего в исходнике не меняет.
- Все пороги и списки — только в `config.ts`, в коде магических чисел нет.

## 12. Валидатор и критерии приёмки

`validate.ts` читает JSONL и очищенный файл, проверяет:

| Проверка | Критерий |
|---|---|
| Покрытие заголовков | Каждый H2 файла классифицирован ровно один раз; 0 неклассифицированных |
| Структура | 10 ниш; в каждой ровно 8 секций `N.1`–`N.8`; всего 80 секций; 7 секций `B0.*`; секции `0`, `11` на месте |
| Блоки | 203 блока распределены по секциям; ни один блок не остался без секции |
| Покрытие строк | Диапазоны `line_start–line_end` чанков покрывают файл без дыр и перекрытий (кроме перекрытия прозы при дроблении — оно разрешено и проверяется отдельно) |
| Идентификаторы | Все `chunk_id` уникальны; у каждого блока `parent_id` указывает на существующий родительский чанк |
| Бюджет | Статистика токенов: min / max / среднее; список чанков вне бюджета 500–700 — **только кейсы, SOP и чек-листы имеют право превышать 700**, всё остальное — ошибка |
| Таблицы | В каждом куске дроблёной таблицы есть шапка (первая строка куска = шапка) |
| JSONL | Каждая строка парсится; набор полей одинаков во всех записях; `topics: []` везде |
| Ссылки | Каждый `to_section` из белого списка кодов |

Отчёт валидатора попадает в `data/chunking-report.md` и в консоль.

После валидатора — **ручной просмотр глазами**: 10–15 случайных чанков из разных типов (кейс целиком, кусок таблицы с шапкой, родительский чанк, чанк из сквозного раздела). Только после этого JSONL считается готовым к загрузке в БД (отдельный план).

## 13. Порядок работ

1. Добавить `js-tiktoken`, создать каркас `scripts/chunking/` с `config.ts`.
2. `classify.ts` + `parse.ts`: проход по файлу, на выходе дерево «ниша → секция → блоки». Прогнать на файле, сверить счётчики из раздела 2.
3. `split.ts`: дробление по типам с бюджетом tiktoken.
4. Родительские чанки (раздел 7) и преамбула (раздел 8).
5. `emit.ts`: метаданные, `chunk_id`, запись `data/chunks.jsonl`.
