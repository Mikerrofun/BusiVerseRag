## 1. О чём этот план

Детальный план этапа 3 из `01-rag-plan.md`: превращение очищенного markdown-файла в чанки.

Главный принцип — зафиксирован в плане 1 и повторяется здесь как требование:

> **Нарезка идёт по осмысленным блокам структуры документа, а не «разбить на кучу файлов».**
> Структура документа: **10 ниш, в каждой — 8 основных групп-подразделов `N.1`–`N.8`, плюс сквозные разделы `0`, `B0`, `11`.**
> Чанк = осмысленный блок внутри этой структуры (кейс, SOP, лист финмодели, чек-лист, группа абзацев). Границы не угадываются — они читаются из нумерации заголовков.

Результат этапа — **дерево папок с JSON-файлами**, которое человек просматривает и правит руками, а затем отдельным ручным скриптом загружает в БД.

## 4. Классификатор заголовков

Уровень заголовка не важен, важен шаблон. Один проход по файлу, каждый H2 попадает ровно в одну категорию. Порядок проверок важен — сверху вниз, первое совпадение выигрывает:

| № | Шаблон | Категория | Пример |
|---|---|---|---|
| 1 | `## N.M.` (два числа через точку) | **Секция** `N.M` | `## 1.3. Финансовая модель` |
| 2 | `## B0.M.` | **Секция** `B0.M`, scope = global | `## B0.2. Маркировка интернет-рекламы…` |
| 3 | `## B0.` | **Группа** `B0`, scope = global | `## B0. ОБЩАЯ РЕГУЛЯТОРИКА…` |
| 4 | `## 0.` и `## 11.` | **Группа**-секция без детей, scope = global | `## 0. ОБЩИЕ ПОЛОЖЕНИЯ…` |
| 5 | `## N.` (2–10) | **Группа**-ниша, меняет текущую нишу | `## 2. ОФЛАЙН — ПУНКТ ВЫДАЧИ ЗАКАЗОВ…` |
| 6 | всё остальное H2 | **Блок** внутри текущей секции | `## Лист «Кофейня (Москва)»`, `## SOP 1. …`, `## Coffee Bull — Барнаул` |

H1 (`# …`) встречается один раз — это преамбула. H3 игнорируются как границы.

**Категория 4 — почему отдельная строка.** `## 0.` и `## 11.` совпадают с шаблоном ниши (№5), но нишами не являются. Они обрабатываются как сквозные секции: тело секции = один блок-чанк (см. 8.2).

**Валидатор обязан проверять:** после разбора не осталось ни одного неклассифицированного H2. Это критерий приёмки, а не пожелание.

## 5. Алгоритм прохода

Один проход сверху вниз, конечный автомат с состоянием «текущая ниша + текущая секция»:

- встретили H2 → классифицируем по разделу 4:
  - секция → закрыть текущий блок, открыть секцию внутри текущей ниши;
  - группа-ниша → закрыть текущий блок и секцию, сменить нишу;
  - группа B0/0/11 → то же + scope = global;
  - блок → закрыть предыдущий блок, открыть новый внутри текущей секции;
- любая другая строка → дописывается в тело текущего открытого контейнера (в секцию, если блок ещё не открыт; иначе в блок).

Правила накопления текста:

- Строки между заголовком секции и первым дочерним H2 — **введение секции** (идёт в родительский чанк, раздел 8).
- Строки внутри блока — тело блока, включая его заголовок.
- Пустые строки по краям тел обрезаются; внутри остаются как есть.

Ошибки, при которых скрипт падает (а не молча выдаёт мусор):

- блок встретился до первой секции;
- заголовок не классифицировался;
- секция `N.M` встретилась до первой ниши (кроме `B0.*`, `0`, `11`).

## 6. Типы блоков и правила нарезки

Типы из плана 1 (раздел 3.5), здесь — как именно каждый определяется и режется.

### 6.1 Определение `chunk_type`

| `chunk_type` | Как определяется |
|---|---|
| `sop` | Заголовок блока вида `SOP N.` — только внутри секции `N.6` |
| `checklist` | Заголовок содержит «Чек-лист» — внутри `N.6` |
| `case` | Блок внутри `N.2`, заголовок которого **не** входит в список служебных (см. ниже) |
| `table` | Секции `N.3`, `N.4`, `N.5`, `N.8` целиком; блок «Матрица сбоев» в `N.6`; служебные блоки `N.2`, если их тело — таблица |
| `prose` | Секции `N.1`, `N.7`; служебные блоки `N.2`; тело секций `0` и `11`; преамбула |

Список служебных заголовков `N.2` (не кейсы) — фиксированный, проверяется валидатором по всем 10 нишам:

- `Рыночный фон`
- `Примеры смены стратегии (pivot)`
- `Типовые сценарии закрытия в первые 6–12 месяцев`

Если в какой-то нише у `N.2` встретится служебный заголовок, которого нет в списке, — скрипт падает со списком найденных заголовков. Список пополняется руками, после человеческой проверки.

### 6.2 Правила дробления по типам

Бюджет: **500–700 токенов**. Блок ≤ 700 токенов → один чанк. Блок > 700 → дробится по правилам типа:

| Тип | Правило дробления |
|---|---|
| `table` | По группам строк. **Шапка таблицы повторяется в каждом куске.** Кусок без шапки бессмысленен. Группы строк подбираются так, чтобы кусок попадал в 500–700 |
| `prose` | По границам абзацев, перекрытие 15% (последний абзац куска повторяется первым абзацем следующего) |
| `case` | **Не режется никогда.** Кейс на 1200 токенов остаётся одним чанком: вывод в конце, причина в начале |
| `sop` | **Не режется никогда** |
| `checklist` | Список целиком; не режется |

Дробление таблицы — по строкам данных между разделителями `|---|`; шапка = строки до разделителя + сам разделитель.

Перекрытие прозы считается в абзацах, не в токенах: берём последний абзац куска целиком. 15% — ориентир из плана 1; если последний абзац сам больше 15% бюджета, берём его всё равно целиком (резать абзацы запрещено).

## 7. Подсчёт токенов

### 7.1 Инструмент

Пакет **`js-tiktoken`** — это **не модель и не API**, а офлайн-счётчик: функция «текст → число токенов». Ставится одной командой из npm, работает локально, **не требует ключей, аккаунтов и сети**. Нужен только для одного — честно измерять бюджет 500–700, потому что оценка «по символам» для русского текста врёт в разы.

Энкодинг по умолчанию — **`o200k_base`**: он новее и заметно лучше работает с кириллицей (меньше токенов на русское слово). Энкодинг — поле конфига, меняется одной строкой.

Важно понимать: у заказчика уже есть модель эмбеддингов, но её токенизатор не обязан совпадать с tiktoken. tiktoken здесь — **прокси-метрика для бюджета**, а не гарантия. Если название модели эмбеддингов уточнят и её счётчик заметно расходится с tiktoken, счётчик меняется в конфиге — бюджет пересчитывается автоматически. Название модели — открытый вопрос (раздел 15).

### 7.2 Что считается

- `token_count` чанка = токены поля `text` (без метаданных).
- Бюджетные решения (резать/не резать) принимаются по токенам тела блока.

## 8. Чанки-секции (родители) и преамбула

### 8.1 Схема small-to-big

Из плана 1: ищем по блокам, в LLM отдаём родителя. Родительский чанк секции состоит из:

1. Введения секции — текст прямо под `## N.M` до первого дочернего H2 (обычно 1–3 абзаца).
2. Списка названий дочерних блоков — чтобы модель понимала, что внутри:

```
## 1.3. Финансовая модель

[введение секции, если есть]

Содержит блоки:
- Лист «Кофейня (Москва)»
- Лист «Кофейня (регион)»
- Скрытые расходы
- Отраслевые бенчмарки
```

### 8.2 Особые случаи

| Случай | Правило |
|---|---|
| Секция без введения (`B0`) | Родительский чанк = только список дочерних блоков |
| Секция без дочерних блоков (`0`, `11`) | Тело секции становится **одним блок-чанком** (тип `prose`/`table` по содержимому), родительский чанк всё равно создаётся — с введением и списком из одного блока |
| Секция без введения и без детей | Не встречается в файле; валидатор падает, если встретится |

### 8.3 Преамбула

Строки 1–12 (до `## 0.`) — один чанк: `scope = "global"`, `business_type = "global"`, `section_code = null`, `chunk_type = "prose"`, `parent_id = null`; в `heading_path` — только название документа.

Это служебный чанк: в нём правила расчётов («налог по умолчанию — УСН 6%…»), на которые ссылается весь документ.

### 8.4 Ожидаемый объём

~88 родительских чанков (80 + 8 сквозных), ~203 блока до дробления, +100–150 после дробления крупных. Итого **~500–600 JSON-файлов** — сходится с оценкой плана 1.

## 9. Метаданные и формат результата

### 9.1 Поля JSON-файла чанка

По составу полей совпадает с будущей строкой таблицы `chunks` (кроме `tsv` и `embedding` — их считает БД и следующий этап):

| Поле | Откуда |
|---|---|
| `chunk_id` | См. 9.2 |
| `source_id` | Константа из конфига, например `busiverse-2026-10-13` (дата актуальности из документа) |
| `business_type` | Из номера ниши (`1` → `coffee_shop`); для сквозных и преамбулы — `global` |
| `block` | `offline` (ниши 1–5) / `online` (6–10) / `global` |
| `section_code` | `1.3`, `B0.2`, `0`, `11`; у преамбулы `null` |
| `section_title` | Заголовок секции без `## ` |
| `block_title` | Заголовок блока без `## `; у родительского чанка `null` |
| `heading_path` | `["1. ОФЛАЙН — КОФЕЙНЯ", "1.3. Финансовая модель", "Лист «Кофейня (Москва)»"]` |
| `chunk_type` | По 6.1 |
| `topics` | Всегда `[]` — заполняется отдельным этапом позже |
| `scope` | `global` / `business` |
| `parent_id` | У блоков — id секции; у родительских чанков `null` |
| `chunk_index` | Порядковый номер внутри секции (родители не нумеруются, у них 0) |
| `part_index` / `part_total` | Номер куска и всего кусков, если блок дробился; иначе 1/1 |
| `line_start` / `line_end` | Номера строк **очищенного** файла. Информационные: после ручных правок текста могут не совпадать — валидатор на это не падает (см. 12) |
| `token_count` | tiktoken, по 7.2 |
| `text` | Текст чанка |
| `content_hash` | sha256 текста |

Порядок соседей (`prev`/`next`) в файлах **не хранится** — при ручных правках такие ссылки протухают. Порядок и соседство считаются из сортировки путей при загрузке в БД.

### 9.2 Формат `chunk_id`

Родительский чанк секции — `{business_type}-{section_code}`:

```
coffee_shop-1.3        global-B0.2        global-0
```

Совпадает с примером `parent_id` из плана 1 (`coffee_shop-1.3`) — контракт не ломается.

Блок-чанк — `{parent_id}-b{NN}`, где NN — порядковый номер блока внутри секции в порядке следования в документе, с ведущим нулём:

```
coffee_shop-1.3-b01    ← Лист «Кофейня (Москва)»
coffee_shop-1.3-b02    ← Лист «Кофейня (регион)»
```

Кусок дроблёного блока — суффикс `-p{N}`:

```
coffee_shop-1.4-b01-p2
```

Индексы, а не slug'и из названий: названия блоков дрейфуют (план 1, раздел 4 — «Типовые сценарии закрытия…» встречается в 8 вариантах), номера стабильны. Идемпотентность загрузки в БД обеспечивает `content_hash` + уникальность `(source_id, chunk_id)`, а не человекочитаемость id.

### 9.3 Дерево папок результата

```
data/
  chunks/
    global/                      ← сквозное: преамбула, 0, 11, B0
      preamble/
        global-preamble.json
      0/
        global-0.json            ← родитель
        global-0-b01.json        ← тело секции как один блок
      11/
        ...
      b0/
        global-B0.json
        global-B0.1/
          global-B0.1-b01.json
          ...
    coffee/                      ← slug ниши 1 из конфига
      1-1/                       ← код подраздела
        coffee_shop-1.1.json     ← родительский чанк
        coffee_shop-1.1-b01.json
        ...
      1-2/
        ...
    pickup/                      ← slug ниши 2
      ...
    ...
    _links.json                  ← внутренние ссылки (раздел 10)
  chunking-report.md             ← отчёт прогона: счётчики, статистика токенов, отклонения
```

Правила дерева:

- Папка ниши — slug из конфига (`1` → `coffee`, полный маппинг в разделе 11.1). Папка подраздела — код `N-M` без названия: название внутри JSON, а коды стабильны.
- Имя JSON-файла = `chunk_id`. Дубликаты id невозможны физически — файловая система не даст two files с одним именем в одной папке.
- Файлы и папки с префиксом `_` служебные, загрузчик в БД их пропускает.
- Прогон повторяем и детерминирован: без LLM, без сети (кроме разовой загрузки энкодинга tiktoken при установке).

### 9.4 Ручные правки после прогона

Дерево папок существует именно для этого. Разрешено и ожидается:

- поправить `text` в любом JSON (например, смять границу абзаца);
- удалить бессмысленный чанк (файл);
- добавить чанк — новый JSON-файл по тому же формату полей, с id по схеме 9.2 (следующий свободный индекс `bNN`).

После любых правок — снова запустить `chunk:validate` (раздел 12), он перепроверит структуру, бюджеты и ссылки.

## 10. Внутренние ссылки (`chunk_links`)

В нишах 6–10 есть ссылки вида «см. раздел B0». Таблица `chunk_links` уже есть в схеме БД, поэтому ссылки вытаскиваются здесь — это механический шаг, не LLM.

- Поиск по тексту блока: фразы «см. раздел X» и «раздел X», где X — код из белого списка (`0`, `11`, `B0`, `B0.1`–`B0.6`).
- Результат: `{ from_chunk_id, to_section }`, дедупликация по паре.
- Пишется в `data/chunks/_links.json`.
- Каждое найденное вхождение попадает в отчёт с номером строки — проверяется глазами перед загрузкой в БД.

## 11. Скрипт

### 11.1 Структура (FSD)

Вся типизация — в файлах типов, все константы и списки — в конфиге, логика не содержит ни того ни другого. Никаких магических чисел и инлайн-типов внутри логики.

```
scripts/chunking/
  types/
    chunking.types.ts       ← ВСЕ типы: Chunk, ChunkMeta, Section, Block, HeadCategory, ReportStats...
  config/
    chunking.config.ts      ← ВСЕ константы: бюджет, перекрытие, энкодинг tiktoken, маппинг ниш
                            ←   (1 → coffee, 2 → pickup, ...), служебные заголовки N.2,
                            ←   белый список кодов ссылок, source_id, пути
  lib/
    classify.ts             ← классификатор заголовков (раздел 4)
    parse.ts                ← проход по файлу, секции и блоки (раздел 5)
    split.ts                ← дробление по типам (раздел 6)
    tokens.ts               ← обёртка над js-tiktoken
    emit.ts                 ← метаданные, chunk_id, запись дерева папок
    links.ts                ← извлечение ссылок (раздел 10)
    validate.ts             ← валидатор (раздел 12)
  chunk.ts                  ← точка входа: собирает пайплайн, пишет отчёт
  load.ts                   ← загрузка в БД (раздел 11.2), запускается ТОЛЬКО пользователем
  test/
    chunking.test.ts        ← минимальные тесты (раздел 13)
```

Зависимость: `js-tiktoken` (добавить в dependencies).

npm-скрипты:

- `"chunk": "tsx scripts/chunking/chunk.ts"` — нарезка → дерево папок + отчёт;
- `"chunk:validate": "tsx scripts/chunking/lib/validate.ts"` — валидация дерева;
- `"chunk:load": "tsx scripts/chunking/load.ts"` — загрузка в БД, вручную;
- `"test:chunking": "tsx --test scripts/chunking/test/chunking.test.ts"`.

Скрипт читает очищенный файл и пишет `data/chunks/`; ничего в исходнике не меняет.

### 11.2 `chunk:load` — загрузка в БД (ручной шаг)

Отдельный скрипт. Пользователь запускает его сам, когда сочтёт дерево папок готовым. Агент **не запускает** его против реальной БД.

Флоу скрипта:

1. Читает `DATABASE_URL` из `.env` через dotenv — так же, как это делает `scripts/database/migrate.ts` (образец из раздела 0.6).
2. Обходит `data/chunks/` рекурсивно, сортирует пути — из сортировки получаются порядок и соседство чанков.
3. В режиме `--dry-run` (по умолчанию): валидирует всё и печатает план — сколько чанков по нишам и типам полетит в БД, — не открывая соединение. Этого достаточно, чтобы заранее убедиться, что скрипт рабочий.
4. В режиме `--apply`: вставляет строки в `chunks` с `embedding = NULL` (эмбеддинги — следующий этап) и заполняет `chunk_links`. Повторный запуск безопасен: конфликт по `(source_id, chunk_id)` — обновление, а не дубликат.

## 12. Валидатор и критерии приёмки

`validate.ts` работает в двух режимах.

**Режим «после прогона»** (дерево только что создано скриптом) — полная проверка:

| Проверка | Критерий |
|---|---|
| Покрытие заголовков | Каждый H2 файла классифицирован ровно один раз; 0 неклассифицированных |
| Структура | 10 ниш; в каждой ровно 8 секций `N.1`–`N.8`; всего 80 секций; 7 секций `B0.*`; секции `0`, `11` на месте |
| Блоки | 203 блока распределены по секциям; ни один блок не остался без секции |
| Покрытие строк | Диапазоны `line_start–line_end` чанков покрывают файл без дыр и перекрытий (кроме разрешённого перекрытия прозы при дроблении — оно проверяется отдельно) |
| Идентификаторы | Все `chunk_id` уникальны; у каждого блока `parent_id` указывает на существующий родительский файл |
| Бюджет | Статистика токенов: min / max / среднее; список чанков вне бюджета 500–700 — **только кейсы, SOP и чек-листы имеют право превышать 700**, всё остальное — ошибка |
| Таблицы | В каждом куске дроблёной таблицы есть шапка (первая строка куска = шапка) |
| Формат файлов | Каждый JSON парсится; набор полей одинаков во всех файлах; `topics: []` везде |
| Ссылки | Каждый `to_section` из белого списка кодов |

**Режим «после ручных правок»** — те же проверки, кроме покрытия строк: диапазоны строк информационные и после правки текста руками могут не совпадать (это не ошибка). Структура, бюджеты, id, родители, шапки таблиц и ссылки проверяются всегда.

Отчёт валидатора попадает в `data/chunking-report.md` и в консоль.

После валидатора — **ручной просмотр глазами**: 10–15 случайных чанков из разных типов (кейс целиком, кусок таблицы с шапкой, родительский чанк, чанк из сквозного раздела). Только после этого дерево считается готовым к `chunk:load`.

## 13. Тесты (минимальные)

Один файл `test/chunking.test.ts`, без тестовых фреймворков — встроенный раннер `tsx --test`. Проверяют только чистые функции на маленьких строках-фикстурах, без чтения реального файла:

1. Классификатор: по одному примеру на каждую из 6 категорий раздела 4 (включая ловушку `## 0.` / `## 11.`).
2. Дробление таблицы: у каждого куска первая строка — шапка.
3. Дробление прозы: перекрытие — последний абзац предыдущего куска = первый абзац следующего.
4. Кейс/SOP/чек-лист не дробятся даже при превышении бюджета.
5. Генерация `chunk_id`: родитель, блок, кусок — по схеме 9.2.
6. Извлечение ссылок: находит «см. раздел B0.2», игнорирует код вне белого списка.

Этого достаточно: основная гарантия корректности — валидатор на реальном файле (раздел 12), а не юнит-тесты.

## 14. Порядок работ

Задачи описаны как флоу — код не пишется заранее, агент опирается на разделы плана.

1. **Каркас.** Добавить `js-tiktoken` в dependencies. Создать структуру `scripts/chunking/` по разделу 11.1: сначала `types/` и `config/` (все типы и константы из разделов 2, 4, 6, 9, 10), npm-скрипты из 11.1. Логика пока пустая.
2. **Классификатор и проход.** Реализовать `classify.ts` и `parse.ts` по разделам 4–5. Прогнать на реальном файле и сверить счётчики с разделом 3 (302 H2, 80 секций, 203 блока, 64 SOP) — расхождение означает ошибку классификации.
3. **Дробление.** Реализовать `split.ts` по разделу 6: правила по типам, бюджет через `tokens.ts` (раздел 7).
4. **Родители и преамбула.** Собрать родительские чанки по разделу 8, включая особые случаи `B0`, `0`, `11` и преамбулу.
5. **Вывод.** Реализовать `emit.ts` по разделу 9: метаданные, `chunk_id`, запись дерева папок и `chunking-report.md`. Затем `links.ts` по разделу 10 → `_links.json`.
6. **Валидатор.** Реализовать `validate.ts` по разделу 12 (оба режима). Добиться зелёных проверок на реальном файле.
7. **Тесты.** Написать минимальный `test/chunking.test.ts` по разделу 13, добиться прохождения.
8. **Загрузчик.** Реализовать `load.ts` по разделу 11.2. Проверить только `--dry-run` — против реальной БД не запускать.
9. **Ручная приёмка.** Пользователь просматривает чанки глазами (раздел 12), при правках — правит JSON в папках и перезапускает `chunk:validate`. Затем пользователь сам запускает `chunk:load --apply`, когда готов.
